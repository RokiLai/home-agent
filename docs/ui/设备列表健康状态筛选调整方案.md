# 设备列表健康状态筛选调整方案

## 1. 状态与范围

| 维度 | 状态 | 说明 |
|---|---|---|
| 设计 | 已审查确认 | 用户已确认“异常”严格匹配 `degraded`，“离线”严格匹配 `offline`，并授权实施。 |
| 实施 | 实施完成 | 已完成前端筛选、测试与服务端 UI 版本更新。 |
| 验收 | 验收通过 | 已通过针对性测试、真实浏览器、全量 `-race` 回归、范围检查与 Diff Coverage 门禁。 |

- 编写日期：2026-09-21。
- 任务：`device-list-health-status-filter`。
- 变更清单：`../../changes/device-list-health-status-filter.yaml`。
- 关联方案：《控制台信息架构与核心任务流设计方案》第 5.2、6.2 与 9 节。

本方案只调整“已接入设备矩阵”的**互斥健康状态筛选**。目标筛选顺序固定为：**全部、健康、异常、离线**。不改变设备健康评估、同步能力、设备卡片内容、搜索条件、权限模型、API 或路由。

## 2. 现状证据与问题

| 位置 | 已核实事实 |
|---|---|
| `internal/ui/static/index.html` | `#deviceFilterPills` 当前依次包含 `all`（全部）、`healthy`（健康）、`degraded`（异常）、`synced`（已同步）、`pending`（待同步）五项。 |
| `internal/ui/static/js/app.js` | 点击筛选项会将其 `data-filter` 写入 `state.currentFilter` 后调用 `renderDevices()`。 |
| `internal/ui/static/js/devices/render.js` | `renderDevices()` 当前允许五个筛选值，并分别按 `health.status` 与同步适配函数 `isDeviceSynced()` 过滤。 |
| `internal/health/model.go` | 权威健康枚举包括 `healthy`、`degraded`、`offline`、`unknown`。 |

当前同一互斥按钮组混合了两个独立维度：健康状态与配置同步状态。用户指定的分类是健康维度，因此“已同步／待同步”不应继续出现在该组；“离线”应使用已有健康状态 `offline`，不以连接徽标、最近联系时间或同步结果推断。

## 3. 功能契约

### 3.1 筛选项与状态映射

| 顺序 | 可见文案 | 前端筛选值 | 精确匹配条件 | 不包含 |
|---:|---|---|---|---|
| 1 | 全部 | `all` | 不按健康状态排除任何设备 | 无健康快照、未知、健康、异常、离线均保留 |
| 2 | 健康 | `healthy` | `device.health.status === 'healthy'` | `degraded`、`offline`、`unknown`、健康数据缺失 |
| 3 | 异常 | `degraded` | `device.health.status === 'degraded'` | `healthy`、`offline`、`unknown`、健康数据缺失 |
| 4 | 离线 | `offline` | `device.health.status === 'offline'` | `healthy`、`degraded`、`unknown`、健康数据缺失 |

“异常”与“离线”互斥：离线设备只能进入“离线”，即使其原因列表中也包含异常规则。`unknown` 与缺失健康数据不冒充健康、异常或离线；它们仅在“全部”中可见。这与现有健康四态契约保持一致。

### 3.2 交互与搜索

初始筛选仍为“全部”。点击任一项时，该项成为唯一激活项，列表立即按上表刷新；随后输入或清空搜索条件时，搜索必须在当前健康筛选结果上继续收窄或恢复，不能重置筛选。没有匹配设备时沿用现有空状态，不以空结果暗示接口失败。

移除 `synced` 与 `pending` 作为设备矩阵筛选值及其 UI 入口。设备同步状态仍可在既有卡片、详情或同步操作流程中展示；本方案不删除同步状态计算、同步接口或任何数据字段。

## 4. 状态与失败路径

| 输入或情形 | 预期行为 | 禁止行为 |
|---|---|---|
| `health.status` 为已知四态 | 严格按第 3.1 节过滤 | 根据 `connected`、`last_seen_at` 或同步字段重写健康结论 |
| `health` 缺失或状态未知 | 仅“全部”展示 | 归类为健康、异常或离线 |
| 内存中残留旧值 `synced` / `pending` | 前端安全回退至 `all`，并同步激活“全部” | 保持无入口的筛选状态，或抛出异常 |
| 筛选后无匹配项 | 展示现有空结果状态 | 清空原始设备数据、伪造加载失败 |
| 页面刷新或重新加载数据 | 默认由现有状态初始化逻辑决定；本变更不增加持久化 | 将旧同步筛选写入 URL、本地存储或服务端 |

## 6. 测试与验收设计

测试先于实现，断言应直接来自本方案：

| 成功标准 | 验证方式 | 必须包含的负例 |
|---|---|---|
| 筛选入口正确 | 解析真实 `#deviceFilterPills`，断言文案和 `data-filter` 顺序仅为四项 | 断言页面不再含 `synced`、`pending` 筛选入口 |
| 过滤语义准确 | 使用同时包含四态、缺失健康和未知健康的 API 契约数据，验证渲染结果 | `offline` 不出现在“异常”；`unknown` 与缺失健康不出现在三个具体状态 |
| 交互闭环 | 真实浏览器执行点击：响应 → 解析 → 状态 → 渲染 → 回调 | 点击“离线”后无未捕获异常，且不激活其他筛选按钮 |
| 搜索叠加正确 | 选定每个健康状态后输入/清空搜索词 | 搜索不重置已选筛选，也不让不匹配健康状态的设备出现 |
| 兼容旧内存状态 | 令 `state.currentFilter` 为 `synced` 或 `pending` 后渲染 | 必须回退“全部”，不存在脏激活状态或异常 |
| 布局和可访问性 | 在现有桌面与移动端真实浏览器基线下检查四项按钮均可见、可点击且状态文字可辨识 | 不以静态字符串测试替代点击命中或窄屏溢出验证 |

实施完成后，按仓库门禁执行变更范围与架构依赖检查、相关模块测试、基于真实端口和协议的 `go test -race ./...`、`./scripts/check-diff-coverage.sh HEAD 60`、UTF-8 无 BOM、`git diff --check` 以及实际文件清单检查。浏览器验收须记录实际视口、测试数据与控制台错误结果。

1. “异常”严格仅指 `degraded`，离线不并入异常筛选。
2. 源码已确认前端设备响应消费 `health.status`；实施验收将以真实端口 API 响应再次验证字段结构。
3. 实施变更清单已列明前端、测试与服务端 UI 版本文件。
