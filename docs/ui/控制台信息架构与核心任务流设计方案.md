## 2. 现状证据与问题边界

本次依据仓库源码梳理结构，尚未完成运行页面截图与真实交互审计。以下结构事实不代表已确认像素布局、遮挡、点击命中或可访问性故障。

| 源码证据 | 当前结构 | 设计处理 |
|---|---|---|
| `internal/ui/static/index.html`、`js/router.js` | 七个页面：dashboard、devices、onboarding、github、commands、users、settings | 按设备操作频率组织导航，保留旧地址兼容 |
| `index.html` 的 `.stats-grid` | 全局统计处于具体页面外，包含同步状态及配置 Hash | 统计归属首页；技术诊断信息进入详情 |
| `#pageDashboard` | 健康概览、安装命令、GitHub 小组件、动态日志并存 | 首屏聚焦异常与最近结果 |
| `#pageDevices`、`js/devices/render.js` | 批量控制置顶；设备卡同时包含健康、SSH、GitHub、地址及操作 | 列表保留摘要，详情页容纳深入管理 |
| `#deviceHealthModal` | 指标、异常原因、健康历史集中在弹窗 | 迁入可直接访问的设备详情 |
| `js/commands.js` | 拉取最近 100 条记录，直接显示协议状态字符串 | 中文映射、按设备定位、分页与范围说明 |
| `internal/command/model.go` | 有 dispatching、timed_out、interrupted、legacy_untracked 等状态 | 使用完整枚举，不能套用简化路线图状态 |
| `internal/api/api.go` | 已有多用户权限、共享、任务、告警接口；部分网络接口使用不同认证包装 | 不将所有读接口视为浏览器会话可直接调用 |

上一轮讨论的调整记录：

1. “自动化”暂不设一级导航。SSH ACL、DDNS、升级策略缺少已核实的完整 Web 配置读写契约，不能用空页面承诺能力。
2. 健康状态采用现有四态，不新增“警告、严重”作为健康枚举；原因若带严重度，只用于解释与排序。
3. 设备卡已经有部分下拉操作，后续应合并现有入口，不能把“所有操作都外露”当作已证实事实。
4. 唤醒不在现有 Command.Kind 枚举内，不能假定它具备与升级相同的最终执行回执。

## 3. 功能边界与取舍

本次改版优先改善现有能力的查找、理解及操作闭环，不新增任意 Shell、计划任务、后台调度、ACL 编辑器、DDNS 配置器或新的授权模型。

保留原生 HTML、CSS、ES Modules 与 Go embed 交付方式，不增加生产依赖。逻辑按路由、数据适配、设备详情和任务展示分离，页面不直接依赖 Go 内部模块；沿用 HTTP 契约。

客户端未修改时不升级客户端版本。服务端升级源、Agent 安装和升级协议保持现有语义；如果后续发现必须修改这些协议，须单独设计并验证真实外部链路及上一正式版本升级路径。

## 4. 信息架构与地址兼容

一级导航建议为“首页、设备、操作记录、系统设置”。添加设备作为设备页主按钮；GitHub 归入系统设置下的“集成”。有权限的用户可访问对应设置分区，无权限分区不展示。

| 页面归属 | 内容 | 入口与兼容 |
|---|---|---|
| 首页 | 健康统计、异常设备、最近操作 | 保留 `#/dashboard` |
| 设备 | 搜索、分类、摘要列表、批量操作 | 保留 `#/devices` |
| 添加设备 | 操作系统选择、临时凭据、安装说明、接入结果 | 保留 `#/onboarding`，一级菜单入口改为设备页按钮 |
| 设备详情 | 概览、健康、SSH 与访问、网络、操作记录、设备设置 | 拟新增 `#/devices/<编码后的设备ID>/<分区>` |
| 操作记录 | 任务列表、筛选、任务详情、最终结果 | 保留 `#/commands`；拟新增 `#/commands/<编码后的任务ID>` |
| 系统设置 | 连接设置、账号密码、用户权限、GitHub 集成、关于 | 保留 `#/settings`；旧 `#/users`、`#/github` 显示对应分区并选中系统导航 |

新增地址是提案，不是已存在路由。实施时沿用 hash 路由，刷新不依赖新的 HTTP 页面路由。设备名和别名不得用作标识；编码、解码失败显示无效地址，不发出写请求。未知地址显示可返回首页的提示。

设备详情的分区切换、浏览器前进后退和刷新保持一致；回到列表恢复搜索、筛选和滚动位置。仅将非敏感展示偏好放入会话内存；凭据不得写入 URL。首期不承诺跨浏览器持久化偏好。

## 5. 页面与交互契约

### 5.1 首页

页面顺序为健康统计、待处理设备、最近操作。统计仅包含当前用户有权查看的设备，使用“总数、正常、异常、离线、未知”；无数据或加载失败不显示为零台正常。

待处理区列出异常和离线设备，每台设备一条摘要，显示主要原因及其余原因数量；无严重度依据时按离线、异常、设备 ID 稳定排序。未知状态单独提示数据不足，不自动当作正常或严重故障。首批最多显示 10 台，提供查看全部入口。

最近操作最多展示 5 条，并注明这是最近记录；不能根据分页中的任务数声称全系统正在执行任务总数。失败任务与设备当前异常不直接累加为同一统计。安装命令、GitHub 绑定卡片和原始日志退出首页。

无设备时展示添加入口；无接入权限时展示“暂无可访问设备，请联系管理员”。已有设备且无异常时显示健康结论与更新时间，不能留下空白面板。

### 5.2 设备列表

列表保留设备名、系统、健康结论、主要地址、Agent 版本、最近联系时间、查看详情入口。健康与 SSH 同步分别筛选，避免“正常”和“已同步”混在一个互斥筛选组中。加载失败与搜索无结果分开呈现。

首期沿用紧凑卡片及现有响应式方式，不同时新增表格/卡片两套视图。设备名进入详情；只保留一个上下文快捷动作，例如离线设备在满足现有唤醒条件时显示“唤醒”。快捷动作的出现不改变后端执行条件。

主按钮为“添加设备”，批量操作为次级菜单。第一期保留现有全网接口的目标语义，确认界面明确范围；不得将当前筛选结果冒充后端实际目标。第二期才评估选中设备执行，需明确逐台提交、并发上限及恢复契约后再开放。

### 5.3 设备详情

标题区显示名称、系统、健康结论及最近更新时间。主要内容通过分区导航切换：

| 分区 | 信息与操作 |
|---|---|
| 概览 | 基本身份、当前异常摘要、最近任务结果、常用入口 |
| 健康 | 原因、建议、运行指标及健康变化历史 |
| SSH 与访问 | SSH 用户及端口、公钥同步状态、同步动作、现有设备共享；共享与设备间 SSH 授权明确分组 |
| 网络 | 已上报地址和 MAC；额外网络数据只有在认证契约验证后接入 |
| 操作记录 | 按该设备 ID 查询任务，进入全局同一个任务详情组件 |
| 设备设置 | 别名、所有权、删除；危险动作集中在独立区域 |

指标缺失显示“未上报”，不渲染为 0；显示采样时间。旧设备无健康数据时展示未知及说明。地址列表支持局部换行或滚动，复制失败给出可选中文本。

健康详情不再同时维护弹窗和详情页两份实现；原有健康按钮跳转到该设备健康分区。改名等短表单可继续使用弹窗。

### 5.4 操作与结果

执行路径固定为：选择动作 → 确认目标及影响 → 提交 → 展示已知的任务 ID 或受理结果 → 查询权威结果。升级、关机、解绑、删除及所有权转移继续保留明确确认。取消确认不发请求。

HTTP 成功仅表示相应请求成功，不能等同设备已执行。操作提交期间防止重复触发，沿用现有幂等键实现；网络超时显示“提交结果待确认”，不能自动换键重发关机等动作。

唤醒显示“唤醒请求已发送”及接口实际反馈，后续在线观测单独显示，不能以封包发送成功声称开机成功。客户端确认关机任务成功也不等于已证明物理断电。

全网操作逐台列出已知结果；分别计算成功、失败、处理中、结果未知和跳过。存在未知目标或未获得完整明细时显示“结果不完整”，不能显示“全部成功”。是否允许取消由服务端判定，不能因前端显示非终态就保证可取消。

### 5.5 设置与接入

保留现有账号、权限、共享和 GitHub 功能入口，不扩展角色权力。当前用户改密码与系统用户管理分组，避免所有人均看到“管理员密码”文案。

添加设备沿用安装及 Claim 流程，临时凭据仅在用户进入接入流程时按需申请，不因打开首页创建凭据。安装命令需明确系统、有效期、权限要求和目标服务；复制成功不代表安装成功，接入完成以真实设备记录确认。

GitHub 集成保留现有授权流程；从原导航迁移时保留可发现性。没有配置接口的通知通道、SSH 策略及 DDNS 编辑能力不展示可保存表单。原始动态日志保留在诊断入口，注明其与持久操作记录的区别。

## 6. 数据与状态契约

### 6.1 已核实的接口与扩展点

接口存在性依据 `internal/api/api.go`，实际响应、权限和失败码仍须在每期实施前逐项运行验证。

| 用途 | 现有接口 | 边界 |
|---|---|---|
| 会话 | `GET /api/v1/auth/me` | 失效时清理用户关联缓存 |
| 设备 | `GET /api/v1/devices`、`GET /api/v1/devices/{id}` | 详情使用唯一 ID，不从别名猜测 |
| 健康 | `GET /api/v1/health/summary`、`GET /api/v1/devices/{id}/health`、`GET /api/v1/devices/{id}/health/events` | 尊重权限与缺失数据 |
| 任务 | `GET /api/v1/commands`、`GET /api/v1/commands/{id}` | 模型提供 device_id、kind、status、limit、cursor 筛选和 next_cursor；实施前核对处理器解析 |
| 设备动作 | `POST /api/v1/devices/{id}/sync`、`/wake`、`/shutdown`、`/upgrade` | 不统一假设所有响应都包含 command_id |
| 批量动作 | `POST /api/v1/sync`、`POST /api/v1/devices/upgrade-all` | 保留实际目标与独立结果语义 |
| 网络 | `GET /api/v1/devices/{id}/network-state` | 使用 requireAdminOrDevice，不能默认会话认证适用；首期可仅展示设备已有地址 |

设备响应与 Command 模型不能混用：设备中的 `sync_status`、`applied_hash`、`runtime` 是不同维度；Command 的 `id`、`device_id`、`status`、`revision`、`error_message`、`created_at` 用于独立任务展示。设备 SSE 是 Agent 控制通道，不让 Web 冒用 Device Token 订阅。

### 6.2 业务状态映射

| 协议领域 | 原始值 | 显示 |
|---|---|---|
| 健康 | healthy / degraded / offline / unknown | 正常 / 异常 / 离线 / 未知 |
| 任务 | queued / dispatching / dispatched | 排队中 / 正在下发 / 已下发 |
| 任务 | accepted | 设备已接受（等待完成） |
| 任务 | succeeded / failed / timed_out | 成功 / 失败 / 超时 |
| 任务 | canceled / interrupted | 已取消 / 已中断 |
| 任务 | legacy_untracked | 旧客户端，结果无法关联 |
| 任意领域 | 缺失或未识别枚举 | 未知状态，保留诊断原值，禁止呈现成功 |

任务终态严格使用 `internal/command/model.go` 的 Terminal 定义，包括 legacy_untracked，但后者不是成功。前端只展示服务端允许的状态变化，不建立独立业务推进规则。较旧 revision 不覆盖较新任务；终态后晚到信息只按服务器权威记录展示。

SSH 同步状态单独建立适配函数，保留当前 succeeded → synced 兼容；完整输入集合须从处理器与测试核实后写入实施设计，不能将其他字段的 status 当作同步结果。

### 6.3 页面状态与异步矩阵

| 情况 | 可见结果 | 数据和动作约束 |
|---|---|---|
| 首次加载 | 局部加载态 | 不闪现零设备或正常结论 |
| 成功但为空 | 空状态及适用入口 | 与请求失败区分 |
| 刷新失败 | 错误、重试、上次成功时间 | 可保留旧数据，但标明非最新；不据旧数据自动操作 |
| 401 | 登录提示 | 清理用户、设备、任务及凭据状态，关闭敏感弹窗 |
| 403 | 无权限提示 | 不继续读取该资源，不将其解释为无数据 |
| 404 | 不存在或不可访问 | 停止该详情轮询，允许返回列表 |
| 非 JSON、字段缺失或未知状态 | 局部格式错误或未知 | 不崩溃、不推导成功、不执行自动重试写操作 |
| A 设备切换到 B 后 A 请求返回 | 仍显示 B | 使用会话、设备 ID 与请求序号重新校验上下文 |
| 账号切换或退出后请求返回 | 不恢复旧会话数据 | 会话代次失配则丢弃 |
| 批次重叠 | 分别显示各目标任务 | 按 command.id 隔离，不共享单个“操作成功”字段 |
| 刷新或服务重启 | 从服务端恢复可查询任务 | 不持久化前端虚构终态，不自动重新提交动作 |

轮询复用现有机制，离开页面释放订阅及计时器，防止重复注册。需要新增刷新策略时，在实施方案中给出间隔、并发边界、退避和暂停条件。任务取消与执行竞态、超时晚到回执均以服务器最终状态为准。

## 7. 布局、视觉与可访问性交付契约

沿用现有暗色设计变量和响应式断点；先调整信息层级，不引入另一套主题。容器层级固定为应用外壳 → 导航与内容区 → 页头 → 页面主体 → 内容分区。统计仅在首页主体内；设备详情标题、分区导航及内容共享左右基准线。

- 大于 900px 保留侧栏，小于等于 900px 使用现有抽屉；详情正文按可用宽度重排，640px 以下单栏。
- 移动端页面左右基准内边距为 16px，安全区额外计入；不叠加父面板内边距压缩子卡片。基准线测量误差不超过 1 CSS px。
- 主要正文至少 14px，辅助信息至少 12px，表单输入至少 16px；可交互目标至少 44 × 44 CSS px。
- 每个操作区域至多一个主要强调按钮；红色用于危险动作和错误，状态同时使用文字，不能只靠颜色。
- 窄屏标题换行，长地址及任务 ID 可换行或局部滚动；页面本身不产生横向滚动。保留语义标题和表格字段关联。
- 弹窗仅用于短事务；标题、关闭和主操作保持可达，内容独立滚动。打开移入焦点、Tab 循环、Esc 关闭、结束后归还焦点；触发元素已移除则返回页面标题。
- 路由变化将焦点移动到新页面标题，后台刷新不抢焦点。危险确认不因刷新自行关闭或重新触发。

真实布局要求沿用《服务端Web页面移动端适配方案》的有效门禁；其中旧页面数量和批量操作位置以本次源码证据修正，不在本任务中改写该旧文档。所有新增选择器在实施设计中标注为新增，并提供与既有 `#pageDevices`、`#deviceContainer`、`#deviceHealthModal` 等真实标识的迁移表，不声称新增标识已存在。

## 8. 分期与实施准入

| 阶段 | 交付 | 明确不包含 | 准入要求 |
|---|---|---|---|
| 第一期 | 四项一级导航、首页减法、紧凑列表、设备概览与健康详情、旧入口兼容 | 新策略编辑、选中设备批量执行 | 完成真实页面基线、选定页面布局、核对角色及健康响应 |
| 第二期 | 设备其余分区、任务详情与分页、危险操作统一确认 | 改变执行协议或持久任务模型 | 完整动作响应及权限矩阵、幂等与恢复测试；选择批量执行另行确认 |
| 第三期 | 设置归档、GitHub 迁移、接入反馈整理、诊断入口 | 尚无契约的自动化能力 | 安装与 GitHub 真实协议核验；若改变用户路径执行适用升级验收 |

每一期实施清单必须逐文件列出 allowed_paths；预计涉及 `internal/ui` 内路由、渲染、数据适配及测试，但这里的目录描述不构成修改授权。新增接口或依赖需要补充公开契约、必要性及设计确认。

## 9. 测试与验收证据

量化体验目标：从首页异常摘要到对应设备健康原因最多一次激活；设备详情到对应任务结果最多两次导航激活，不计危险确认及任务执行等待。用真实浏览器路径计数断言，不以主观“更简洁”作为验收。

测试数据优先由隔离测试服务通过真实处理器生成并脱敏保存，记录接口、角色、版本、字段结构及采集日期。GitHub、下载、重定向等外部替身必须注明真实请求来源及已知差异，并至少覆盖一个关键假设失效反例；本次文档编写未执行外部协议验证。

涉及代码后执行范围检查、架构依赖检查、新模块测试、真实端口与协议的全量 `-race` 回归及 `./scripts/check-diff-coverage.sh HEAD 60`。浏览器证据不足不能以静态 DOM 检查代替，也不能降级为非阻断风险。

纯文档本任务依仓库规则免测试，只检查允许路径、UTF-8 无 BOM、空白与完整文件清单。各期验收时在对应实施文档记录命令、版本、结果与截图位置；失败项不勾选。
