## 背景与范围

存量数据无需物理重排；关系数据库在未声明 `ORDER BY` 时不承诺返回顺序，内存 map 遍历同样不承诺顺序。本次只固定当前已有“返回多条记录”的存储与 API 路径，不修改表结构、业务主键、公开请求/响应字段、分页令牌或任何已有记录。

`commands` 文件仓库已使用 `created_at DESC, id DESC` 及匹配游标，不在本次修改范围。没有列表读取接口的 MySQL 表也不添加无调用方的查询。

## 排序契约

所有纳入范围的列表均为最新优先：先按 `created_at` 降序；时间相同再以稳定且唯一的既有标识降序。具体如下：

| 列表 | 主排序 | 次排序 | 覆盖实现 |
| --- | --- | --- | --- |
| 用户 | `created_at DESC` | `id DESC` | `SessionManager`、`FileStore`、MySQL |
| 设备 | `created_at DESC` | `id DESC` | `Registry`、`FileStore`、MySQL |
| 设备授权 | `created_at DESC` | `user_id DESC`（已按 `device_id` 过滤） | `Registry`、`FileStore`、MySQL |
| 认领令牌 | `created_at DESC` | `token_hash DESC` | `FileStore`、MySQL |
| 审计日志 | `created_at DESC` | 数据库自增 `id DESC` | MySQL |

对于 MySQL，排序必须在 SQL 中表达。对于文件或内存存储，先复制返回值，再排序，不能改变内部 map、泄露用户密码哈希或改变并发锁语义。审计日志的 `id` 仅作为 SQL 排序次键，不新增至现有 API 响应。

## 失败与兼容性

排序只改变同一记录集合的数组顺序。查询、扫描或复制错误时保持原有错误返回，禁止退回未排序结果。不存在数据迁移、外部协议依赖或新增依赖。时间完全相同的反例必须证明次排序键仍产生确定顺序。

## 验收

测试应使用乱序插入及相同 `created_at` 的记录，断言每类列表多次调用都返回完全相同的降序序列；用户列表还须断言密码哈希继续被移除。MySQL 集成测试在本地 MySQL 可用时验证 SQL 返回顺序；不可用时维持其现有跳过行为。代码实施后执行变更范围/架构依赖检查、定向测试、`go test -race ./...` 与 `./scripts/check-diff-coverage.sh HEAD 60`。

## 实施与验证记录

  - 用户、设备、设备授权、认领令牌、审计日志列表均已在对应存储层（`SessionManager`、`Registry`、`FileStore`、`MySQLStore`）中统一按 `created_at DESC` 及确定性唯一次键排序。
