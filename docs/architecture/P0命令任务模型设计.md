# P0 统一任务与回执模型开发方案

## 1. 文档状态

- 状态：Draft
- 目标版本：v0.5
- 任务来源：[HomeAgent 产品迭代路线图](homeagent-product-roadmap.md)
- 适用范围：SSH 密钥同步、自升级、远程关机、GitHub 凭据同步与撤销
- 非目标：离线任务重放、SSE `Last-Event-ID` 恢复、通用告警、任意远程命令执行

## 2. 目标

建立独立于 Device 聚合的 Command 事实模型，使每次控制操作都具有唯一身份、合法状态机和可查询历史，并让服务端能够区分“请求已创建”“已投递”“Agent 已接受”和“执行已完成”。

本阶段必须满足：

- 每个控制操作生成唯一 `command_id`。
- SSE 事件和 Agent ACK 显式携带同一个 `command_id`。
- 不同模块不再共享或覆盖任务状态。
- 重复、乱序、跨设备和跨模块 ACK 安全失败或幂等处理。
- 现有公开 API 和旧 Agent 在兼容窗口内保持可用。
- Dashboard 能展示任务生命周期及最终结果。
- 服务端重启后保留历史；重启时未终结任务标记为 `interrupted`，本阶段不自动重放。

## 3. 现状与直接证据

### 3.1 当前执行链

```text
Admin API / CLI / UI
        │
        ▼
internal/api handler
        │ 构造各模块 payload
        ▼
internal/broker.Publish
        │ 仅投递到在线内存订阅者
        ▼
Agent handleEvent
        │ 执行模块逻辑
        ▼
POST /api/v1/devices/{id}/ack
        │ 按 module 分支
        ▼
Registry Device 字段 / 日志
```

### 3.2 已确认问题

| 证据 | 影响 |
|---|---|
| `broker.Event` 已定义 `ID`，但主要发布路径没有赋值 | SSE 事件无法与一次操作稳定关联 |
| `AckRequest` 只有 `module` 和模块结果，没有任务 ID | 服务端无法判断 ACK 属于哪次下发 |
| Agent 的 `sendAck` 不携带事件身份 | 重复、乱序或晚到 ACK 无法可靠识别 |
| `deviceAck` 按模块直接更新 Registry | Device 展示字段同时承担任务事实，曾出现跨模块覆盖 |
| API 响应使用 `ok`、`shutting_down` 等状态 | 调用方容易把“已尝试投递”误认为“执行成功” |
| Broker 为非阻塞内存通道，缓冲区满时静默跳过 | `Publish` 返回值只代表进入某个订阅通道，不代表 Agent 接受或执行 |
| SSE 建连时会主动发送快照事件 | 快照同步与管理员显式命令语义不同，不能简单共用一次性任务状态 |

上述证据能够确认缺少任务关联与独立状态模型；设备离线重放和可靠消息队列属于 P1，不在本阶段推断或实现。

## 4. 核心决策

### 4.1 新增独立业务模块 `internal/command`

`command` 是任务生命周期的唯一事实来源，不直接依赖 `api`、`broker`、`registry` 或各模块基础设施实现。

建议公开契约：

```go
type ID string

type Kind string

const (
    KindSSHKeys          Kind = "ssh_keys"
    KindUpgrade          Kind = "upgrade"
    KindShutdown         Kind = "shutdown"
    KindGitHubSync       Kind = "github_credentials_sync"
    KindGitHubRevoke     Kind = "github_credentials_revoke"
)

type Status string

const (
    StatusQueued      Status = "queued"
    StatusDispatching Status = "dispatching"
    StatusDispatched  Status = "dispatched"
    StatusAccepted    Status = "accepted"
    StatusSucceeded   Status = "succeeded"
    StatusFailed      Status = "failed"
    StatusTimedOut    Status = "timed_out"
    StatusCanceled    Status = "canceled"
    StatusInterrupted Status = "interrupted"
    StatusLegacyUntracked Status = "legacy_untracked"
)
```

禁止由 API handler 直接修改 Command 状态。状态迁移统一通过 `command.Service` 完成。

### 4.2 Command 与 Device 分离

- Command 保存一次操作的事实与结果。
- Device 保存当前设备事实和便于列表展示的模块投影。
- ACK 必须先写 Command，再由投影器按模块更新 Device 展示字段。
- 投影失败不得回滚已经合法落库的 ACK；记录错误并允许重建投影。
- `AppliedVersion`、`AppliedHash` 等 SSH 专属字段不得被其他 Command Kind 写入。

### 4.3 P0 使用持久历史，不做持久投递

P0 提供持久化 Command Repository，以支持操作历史和服务端重启后的审计：

- 创建任务后先持久化 `queued`，再尝试 Broker 投递。
- 投递到至少一个订阅者后迁移到 `dispatched`。
- 没有订阅者或通道满时，任务迁移到 `failed`，错误码为 `delivery_unavailable`。
- 服务端启动时将遗留的 `queued`、`dispatching`、`dispatched`、`accepted` 迁移为 `interrupted`。
- P0 不在重启或设备重连后自动重新投递。

P1 将在 Repository 契约之上增加租约、待投递查询、TTL 和重放，不改变 P0 的 Command 身份与 ACK 协议。

## 5. Command 数据模型

```go
type Command struct {
    ID             ID              `json:"id"`
    Kind           Kind            `json:"kind"`
    DeviceID       string          `json:"device_id"`
    Status         Status          `json:"status"`
    RequestedBy    Actor           `json:"requested_by"`
    IdempotencyKey string          `json:"idempotency_key,omitempty"`
    Request        json.RawMessage `json:"request,omitempty"`
    Result         json.RawMessage `json:"result,omitempty"`
    ErrorCode      string          `json:"error_code,omitempty"`
    ErrorMessage   string          `json:"error_message,omitempty"`
    CreatedAt      time.Time       `json:"created_at"`
    UpdatedAt      time.Time       `json:"updated_at"`
    DispatchedAt   *time.Time      `json:"dispatched_at,omitempty"`
    AcceptedAt     *time.Time      `json:"accepted_at,omitempty"`
    FinishedAt     *time.Time      `json:"finished_at,omitempty"`
    TimeoutPolicy  TimeoutPolicy   `json:"timeout_policy"`
    AcceptDeadline *time.Time      `json:"accept_deadline,omitempty"`
    FinishDeadline *time.Time      `json:"finish_deadline,omitempty"`
    FinalAckDigest string          `json:"final_ack_digest,omitempty"`
    LateAcks       []LateAck       `json:"late_acks,omitempty"`
    OutcomeRevision uint64         `json:"outcome_revision,omitempty"`
    ProjectionInputDigest string   `json:"projection_input_digest,omitempty"`
    Projection     ProjectionState `json:"projection"`
    Revision       uint64          `json:"revision"`
    Protocol       int             `json:"protocol"`
}
```

### 5.1 字段规则

- `ID`：服务端使用加密安全随机源生成，不包含设备、时间或用户信息。
- `Request`：保存经过筛选的非敏感参数；不得保存 OAuth Token、Device Token、Session Token、私钥或完整凭据。
- `Result`：仅保存结构化结果摘要，不保存任意日志正文。
- `RequestedBy`：记录主体类型、稳定 ID 和显示名；首期至少支持 `admin`、`system`、`legacy`。
- `Revision`：每次合法迁移递增，用于防止并发覆盖。
- `Protocol`：首期为 `1`，用于 Server/Agent 跨版本协商。
- `TimeoutPolicy`：创建时按 Kind 冻结接受与完成超时时长，不随运行时配置变化。
- `AcceptDeadline`：进入 `dispatching` 时按服务端时间计算；`FinishDeadline`：首次 `accepted` 时计算。它们是 P0 执行超时，不是 P1 离线投递 TTL。
- `FinalAckDigest`：由规范化最终 ACK 计算，用于判定终态重放与冲突。
- `LateAcks`：有界保存终态后到达的规范化 ACK 摘要、首次到达时间和冲突标记，不改写业务终态。
- `OutcomeRevision` 和 `ProjectionInputDigest`：最终业务结果生成时冻结；投影状态变化不得修改这两个幂等键。
- `Projection`：记录 `pending`、`applied` 或 `failed`、投影 Revision 与错误，支持崩溃恢复和重建。
- 时间统一由服务端以 UTC 记录，不信任 Agent 时间决定状态顺序。

### 5.2 敏感数据策略

GitHub 凭据同步的 Command 只能记录版本、哈希和目标设备，不得将 OAuth Token 写入 Command Store。事件 payload 仍按现有受保护设备通道发送，后续另行设计端到端加密。

## 6. 状态机

```text
queued ──开始投递──▶ dispatching ──投递成功──▶ dispatched ──Agent 接受──▶ accepted ──执行完成──▶ succeeded
   │                    │                   │                         │
   ├─取消────────────▶ canceled             │                         ├─执行失败──────▶ failed
   └─服务端重启──────▶ interrupted          │                         ├─超时────────▶ timed_out
                        └─投递失败────────▶ failed                     └─服务端重启──▶ interrupted

dispatched ──取消（尚未接受）──▶ canceled
dispatched ──超时────────────▶ timed_out
dispatched ──服务端重启──────▶ interrupted
dispatched ──legacy 设备─────▶ legacy_untracked
dispatching ──提前 ACK────────▶ accepted / succeeded / failed
```

终态为 `succeeded`、`failed`、`timed_out`、`canceled`、`interrupted`、`legacy_untracked`。

### 6.1 状态迁移规则

| 当前状态 | 输入 | 新状态 | 处理 |
|---|---|---|---|
| `queued` | 开始一次投递 | `dispatching` | 冻结 Attempt ID 和 `AcceptDeadline` 后再调用 Broker |
| `dispatching` | Broker 投递数 > 0 | `dispatched` | 记录 `DispatchedAt`；若 ACK 已推进则 CAS no-op |
| `dispatching` | Broker 不可用、无订阅者或队列满 | `failed` | `delivery_unavailable`；若 ACK 已推进则 CAS no-op |
| `dispatching` | `accepted` 或最终 ACK | `accepted` / 终态 | 记录 `DispatchedAt`，允许快速 Agent 在 Publish 返回前推进 |
| `dispatched` | 目标设备不支持协议 v1 | `legacy_untracked` | 已投递，但不声称结果可关联 |
| `dispatched` | `accepted` ACK | `accepted` | 记录 `AcceptedAt` |
| `dispatched` | 兼容客户端直接回最终 ACK | `succeeded` / `failed` | 允许跳过 `accepted` |
| `accepted` | 最终 ACK | `succeeded` / `failed` | 保存结果或错误 |
| 非终态 | 截止时间到达 | `timed_out` | 后续 ACK 写入 `LateAcks`，不改终态 |
| `queued` / `dispatching` / `dispatched` | 管理员取消 | `canceled` | 不再接受状态推进；Publish 回写 CAS no-op |
| `accepted` | 管理员取消 | 保持 `accepted` | 返回 `409 command_already_accepted` |
| `succeeded` / `failed` | 与 `FinalAckDigest` 相同的最终 ACK | 不变 | 返回 `200` 并标记幂等命中 |
| `succeeded` / `failed` | 与最终结果冲突的 ACK | 不变 | 返回 `409 invalid_transition` |
| `timed_out` / `canceled` / `interrupted` | 首次晚到 ACK | 不变 | 保存有界 `LateAck`，返回 `202 accepted_for_audit` |
| `timed_out` / `canceled` / `interrupted` | 重复晚到 ACK | 不变 | 摘要相同返回 `202`，冲突返回 `409` |
| `legacy_untracked` | 无 ID legacy ACK | 不变 | 不走 Command ACK 状态机，只更新兼容投影 |
| 任意非终态 | 服务端启动恢复 | `interrupted` | P0 不重放 |

### 6.2 模块完成语义

| Kind | `accepted` | `succeeded` |
|---|---|---|
| `ssh_keys` | 已通过载荷校验并开始应用 | 目标文件原子应用成功且哈希一致 |
| `upgrade` | 已通过版本、URL、SHA256 和平台预检 | 新二进制完成替换、最终结果已写本地账本且重启已唯一调度 |
| `shutdown` | 已通过权限和参数校验并进入调度 | OS 关机命令成功启动；不表示设备已物理断电 |
| `github_credentials_sync` | 已通过载荷校验并开始应用 | 凭据配置与 SSH 配置应用成功 |
| `github_credentials_revoke` | 已开始清理 | 受管凭据和配置清理成功 |

关机接口和 UI 必须使用“关机命令已启动”，不得显示“设备已关机”；物理离线确认属于后续健康状态能力。

## 7. 幂等与并发

### 7.1 创建幂等

- 管理 API 接受可选 `Idempotency-Key` 请求头。
- 唯一范围为 `requested_by + device_id + kind + idempotency_key`。
- 相同键和相同规范化请求返回原 Command，HTTP 状态不重复创建。
- 相同键但请求参数不同返回 `409 idempotency_conflict`。
- UI 每次用户确认生成一次键；网络重试复用同一个键。
- 系统自动同步使用可推导键，例如目标设备、Kind、配置版本与内容哈希组合。

### 7.2 ACK 幂等

- ACK 唯一关联 `command_id`，不以时间或“最近一条任务”猜测。
- ACK 先转换为规范化 `AckOutcome`：只包含 `command_id`、Kind、阶段、结果 schema、错误码和错误信息；忽略 JSON 字段顺序及 Agent 展示信息。
- `accepted` ACK 独立记录首次接受时间；重复 `accepted` 返回 `200`。
- 最终 ACK 对规范化结果计算 SHA-256 摘要并保存为 `FinalAckDigest`。
- 摘要相同的最终 ACK 重放返回 `200`，不重复投影或写历史。
- 相同 Command 的冲突终态返回 `409`。
- ACK 中的 `device_id` 取自鉴权上下文与 URL，两者必须等于 Command 的 `DeviceID`。
- ACK 的模块必须映射到 Command Kind；不一致返回 `409 command_kind_mismatch`。

### 7.3 同设备并发策略

- `ssh_keys`、`upgrade`、`shutdown`、GitHub 同步分别设置模块级并发槽。
- 同设备同 Kind 默认只允许一个非终态 Command；重复请求通过幂等键复用，其他请求返回 `409 command_in_progress`。
- `shutdown` 与 `upgrade` 在设备级互斥，避免关机打断二进制替换。
- SSH 与 GitHub 文件写入是否需要更强互斥，由各自模块锁保证，不在 API handler 中实现。

### 7.4 Agent 本地执行账本

P0 必须为全部 v1 Kind 提供统一的本地持久化账本，不能依赖“只有一个 SSE 连接”的假设：

- 账本阶段为 `prepared`、`side_effect_started`、`result_committed`、`ack_confirmed`；每次迁移先原子持久化再进入下一阶段。
- 收到指令后以 `command_id` 建立 `prepared` 记录，并以本地 single-flight 阻止并发重复执行。
- 执行副作用前先持久化 `side_effect_started`；执行完成后原子保存规范化最终结果及 ACK payload 为 `result_committed`，再发送最终 ACK。
- 重复收到 `prepared` 时允许开始执行；`result_committed` 或 `ack_confirmed` 直接重放/忽略已保存 ACK。
- `accepted` ACK 是尽力而为的观察信号；发送失败不阻止已经校验通过的指令执行。
- 最终 ACK 使用有界指数退避重试；进程重启后继续发送账本中未确认的最终 ACK。
- 账本覆盖 SSH、升级、关机、GitHub 同步与撤销，采用 `0600`、同目录原子替换和有界保留。
- P1 再把该账本扩展为离线任务拉取、投递 TTL 和通用重放机制；P0 只保证已收到的同一 Command 不重复执行。

#### 崩溃恢复规则

| Kind | 重启后发现 `side_effect_started` | 恢复结果 |
|---|---|---|
| `ssh_keys` | 读取受管区并计算目标哈希 | 匹配则提交成功；不匹配则按幂等写入流程继续 |
| `upgrade` | 校验当前目标二进制的版本与 SHA256 | 匹配则提交“已替换”并只调度一次重启；不匹配且无法证明未替换则 `outcome_uncertain` |
| `shutdown` | 不自动再次执行关机命令 | 提交失败 `outcome_uncertain`；由管理员结合设备状态决定是否创建新 Command |
| GitHub 同步/撤销 | 检查受管文件、密钥指纹和目标哈希 | 匹配则提交成功；否则按幂等应用/清理流程继续 |

必须对每个账本持久化边界注入崩溃测试。P0 的“最多执行一次”优先于不确定场景下自动补执行，尤其不得自动重发关机。

## 8. 协议设计

### 8.1 SSE 事件

保留现有事件名和模块 payload，在 payload 顶层增加可选协议字段；同时将 SSE `id:` 设置为 `command_id`：

```text
id: cmd_...
event: upgrade
data: {"command_id":"cmd_...","protocol":1,"ack_mode":"two_phase","target_version":"v0.5.0","url":"...","sha256":"..."}
```

所有受控事件新增：

```json
{
  "command_id": "cmd_...",
  "protocol": 1,
  "ack_mode": "two_phase"
}
```

Go JSON 默认忽略未知字段，因此旧 Agent 可以继续解析原 payload。实施前必须用上一正式版本 Agent 对候选 Server 做真实兼容验证。

SSE 建连时自动发送的 SSH 和 GitHub 快照属于状态协调，不是用户控制操作。P0 保留其 legacy/untracked 语义，不创建 Command；只有管理员显式同步和服务端明确触发的一次性同步创建 Command。P1 设计 desired-state generation 和重连收敛后再统一自动快照。`ping` 不创建 Command。

### 8.2 ACK v1

沿用 `POST /api/v1/devices/{id}/ack`，增加字段：

```json
{
  "command_id": "cmd_...",
  "protocol": 1,
  "ack_mode": "two_phase",
  "module": "upgrade",
  "status": "accepted",
  "result": {},
  "error_code": "",
  "error_message": "",
  "agent_version": "v0.5.0"
}
```

兼容保留 `applied_version`、`applied_hash`、`ssh_fingerprint` 等现有字段；首期由服务端适配器转换为模块结果。

### 8.3 ACK HTTP 语义

| 状态 | 含义 |
|---|---|
| `200` | ACK 首次应用或完全相同的幂等重放 |
| `202` | 晚到 ACK 已持久化用于审计，原 Command 终态不变；Agent 视为传输已确认、停止重试并将本地账本置为 `ack_confirmed` |
| `400` | JSON、字段或状态值无效 |
| `401` / `403` | 设备凭据无效或无权操作目标设备 |
| `404` | Command 不存在；响应不泄露其他设备 Command 是否存在 |
| `409` | Kind 不匹配、状态冲突或非法迁移 |

### 8.4 管理 API

保留现有触发端点，并以兼容方式扩展响应：

```json
{
  "command_id": "cmd_...",
  "device_id": "dev-...",
  "status": "dispatched",
  "legacy_status": "ok"
}
```

新增只读与取消端点：

```text
GET  /api/v1/commands?device_id=&kind=&status=&limit=&cursor=
GET  /api/v1/commands/{command_id}
POST /api/v1/commands/{command_id}/cancel
```

- 列表按 `created_at DESC, id DESC` 稳定排序并使用游标分页。
- 默认不返回完整 Request，只返回安全摘要。
- 单设备触发端点返回一个 Command。
- 批量触发为每台设备创建独立 Command，并返回 `commands` 列表；不使用一个共享终态代表所有设备。

## 9. 旧客户端兼容策略

### 9.1 兼容窗口

- Server v0.5 接受带或不带 `command_id` 的旧 ACK。
- Agent v0.5 能解析带或不带新字段的事件。
- 旧 ACK 继续更新现有 Device 投影，但不得通过“最近任务”猜测 Command。
- 服务端依据已持久化的 Device 协议能力，在投递后立即把旧 Agent 的 Command 标记为 `legacy_untracked` 并释放并发槽，不等待其超时。
- 对无法关联的旧 ACK 记录结构化 `legacy_unmatched_ack`，只更新兼容 Device 投影。
- 控制台明确显示“旧客户端：结果不可关联”，不把它显示为成功。
- 同设备同 Kind 的非终态限制可减少并发混淆，但不能作为关联旧 ACK 的依据。

### 9.2 协议协商

- Device Facts 增加可选 `control_protocols`；Registry 持久化排序去重后的能力集合，新 Agent 上报 `[1]`。
- 每次 Facts 上报以当前集合覆盖旧集合；字段缺失表示保持旧值，显式空数组表示降级为 legacy。
- 同一 Device ID 只允许一个逻辑 Agent 身份；多 SSE 连接共享 Registry 中最近一次认证 Facts 的能力，不能各自协商不同协议。
- 未上报能力的设备按 legacy 处理。
- 事件 payload 明确携带 `ack_mode: two_phase|legacy`，Server 只向声明支持协议 v1 的 Agent 要求两阶段 ACK。
- 删除 legacy ACK 支持必须另建任务，并以受支持最低 Agent 版本和真实升级验收作为门槛。

客户端协议发生修改，实施时必须同步升级客户端版本号。

## 10. 超时策略

P0 使用服务端单调计时调度、UTC Deadline 持久化；超时时长必须配置化并在创建 Command 时冻结为 `TimeoutPolicy`。进入 `dispatching` 时计算 `AcceptDeadline = now + AcceptTimeout`；首次 `accepted` 时计算 `FinishDeadline = now + FinishTimeout`。Command Service 依赖可替换的 Clock/Scheduler 端口，Repository 支持查询已到期非终态任务；超时处理和 ACK 通过 Revision CAS 竞争，只有一个终态胜出：

| Kind | 投递后等待接受 | 接受后等待完成 |
|---|---:|---:|
| `ssh_keys` | 15 秒 | 60 秒 |
| `upgrade` | 15 秒 | 10 分钟 |
| `shutdown` | 15 秒 | 30 秒 |
| GitHub 同步/撤销 | 15 秒 | 2 分钟 |

这些数值是首版候选值，实施前须通过 macOS、Linux、OpenWrt 和 Windows 的真实执行观察确认。服务端启动后先把遗留非终态标记为 `interrupted`，不会恢复旧计时器。P0 超时后不自动重试；管理员可以显式创建新 Command。P1 的 Delivery TTL 用于判断离线任务是否仍可投递，与此处执行 Deadline 分开。

## 11. Repository 与文件格式

### 11.1 端口

```go
type Repository interface {
    CreateOrGet(context.Context, CreateRequest) (Command, bool, error)
    Get(context.Context, ID) (Command, error)
    Transition(context.Context, ID, uint64, Transition) (Command, error)
    List(context.Context, Filter) (Page, error)
    ListExpired(context.Context, time.Time, int) ([]Command, error)
    ListProjectionPending(context.Context, int) ([]Command, error)
    InterruptNonTerminal(context.Context, time.Time) (int, error)
}
```

`CreateOrGet` 必须在同一临界区原子完成幂等键匹配、规范化请求摘要校验和并发槽占用，避免 `Find + Create` 竞态。`command.Service` 只依赖该接口。文件写入实现位于 `internal/command/file`，不允许其他业务模块直接读取存储文件。

### 11.2 首期存储

- 首期使用单独的 `commands.json`，不并入 `devices.json`。
- 文件包含 `schema_version` 和 Commands 集合。
- 写入采用同目录临时文件、`fsync`、原子替换和权限 `0600`。
- 更新使用 Revision 比较，冲突时重新读取并返回明确错误。
- 终态记录同时满足“超过 30 天”且“超出最近 1000 条”时才可删除；清理只删除终态记录。
- 幂等索引的保留期不得短于对应 Command 记录，且至少覆盖 UI/CLI 的最大重试窗口。
- 容量和保留策略配置化。
- P1 实现可靠投递前需评估 SQLite；不得在缺少真实规模数据时新增外部数据库服务。

### 11.3 Result 与投影契约

| Kind | 最小 Result | Device 投影 |
|---|---|---|
| `ssh_keys` | `applied_version`、`applied_hash`、`key_count` | `SyncStatus`、`AppliedVersion`、`AppliedHash`、`SyncError` |
| `upgrade` | `previous_version`、`target_version`、`binary_replaced`、`restart_scheduled` | 仅更新升级操作投影与 `LastSeenAt`；不得覆盖运行中的 `AgentVersion` |
| `shutdown` | `os_command_started`、`scheduled_delay_seconds` | `LastSeenAt`；不投影“已关机” |
| `github_credentials_sync` | `version`、`hash`、`ssh_fingerprint` | GitHub 状态、指纹与更新时间 |
| `github_credentials_revoke` | `credentials_removed`、`config_removed` | GitHub 状态与更新时间 |

每种 Result 使用具名 Go DTO 校验后再编码，不允许 API 将任意 JSON 直接写入 Device。Device 的 `AgentVersion` 只能由新进程启动后的认证 Facts/heartbeat 更新，不能从升级目标版本推断。投影键为冻结的 `command_id + outcome_revision + projection_input_digest`；Projection 自身状态迁移不得改变该键，Device 已更新但 `applied` 标记落库前崩溃时可安全重放。

#### 11.3.1 ACK 状态与 Device 投影状态映射矩阵

在两阶段指令协议中，Agent 上报的终态为 `succeeded` 或 `failed`；服务端在 `deviceAck` 实时处理与异步投影适配时，必须按以下契约规范化转换为设备事实状态，禁止直接透传原始 `req.Status`：

| 指令模块 (`module` / `Kind`) | Agent ACK 状态 (`req.Status`) | Device 事实状态 (`SyncStatus` / `GitHubStatus`) | 说明 |
|---|---|---|---|
| `ssh_keys` | `succeeded` / `synced` | `synced` | 公钥已原子写入且 Hash 一致 |
| `ssh_keys` | `failed` / `error` | `failed` | 公钥写入失败，记录 `SyncError` |
| `github_credentials` | `succeeded` / `synced` | `synced` | GitHub 凭据已部署且指纹匹配 |
| `github_credentials` | `failed` / `error` | `failed` | GitHub 凭据部署失败 |
| `upgrade` | `succeeded` / `failed` | 不修改 `SyncStatus` | 仅通过后续事实 Facts 更新 `AgentVersion` 与 `LastSeenAt` |
| `shutdown` | `succeeded` / `failed` | 不修改 `SyncStatus` | 仅更新 `LastSeenAt` |

## 12. 模块边界与依赖方向

```text
cmd/homeagent-server
        │ 组装依赖
        ▼
internal/api ─────▶ internal/command ◀──── internal/command/file
      │                    ▲
      │ delivery adapter   │ domain-owned projection port
      ▼                    │
internal/broker      api/cmd projection adapter ─────▶ internal/registry

internal/daemon ── HTTP/SSE protocol ── internal/api
```

- `internal/command`：模型、状态机、Repository/Projection/Clock 端口、Service 和领域错误；禁止 import `registry`、`broker` 或 `api`。
- `internal/api`：鉴权、DTO、协议兼容适配和用例编排。
- `internal/broker`：只负责在线投递，不保存 Command 业务状态。
- `internal/registry`：Device 当前状态投影，不保存操作历史；由 `api` 或装配层适配器调用。
- `internal/daemon`：解析命令身份、执行模块动作并发送两阶段 ACK。
- `internal/ui`：消费管理 API，不推导业务状态。

不新增外部依赖。随机 ID、JSON、HTTP 和原子文件操作均可使用 Go 标准库完成，避免为当前规模增加数据库或队列运维成本。

## 13. API 用例执行顺序

以单设备升级为例：

```text
1. API 完成鉴权、输入校验与设备查询
2. Command Service 检查幂等键和并发槽
3. 生成安全的模块 payload 摘要
4. 以 queued 状态持久化 Command
5. 迁移为 dispatching，冻结 Attempt ID 与 AcceptDeadline
6. 将 command_id 注入实际 SSE payload 和 Event.ID
7. Broker 尝试投递；ACK 可从 dispatching 提前推进状态
8. 根据投递数以 CAS 迁移为 dispatched 或 failed；若 ACK 已推进则 no-op
9. API 返回 Command DTO
10. Agent 校验后尽力发送 accepted ACK，不以响应成功作为执行前提
11. Agent 按本地账本执行并发送 succeeded/failed ACK
12. Command Service 校验身份、Kind 和状态迁移
13. 持久化 Command 结果并把 Projection 标记为 pending
14. 投影适配器按 Kind 的固定 Result schema 更新 Device
15. 将 Projection 标记为 applied；失败则保存错误并由启动扫描/管理入口重建
16. UI 通过轮询查询最终状态；实时管理端推送留待后续任务
```

若第 4 步成功而第 6 步进程崩溃，服务端重启后任务变为 `interrupted`；P0 不猜测是否已投递，也不重放。

## 17. 公开契约兼容性

| 契约 | 变更方式 | 兼容策略 |
|---|---|---|
| 现有触发 API | 响应增加字段 | 保留原路径和旧字段至少一个版本周期 |
| ACK API | 请求增加可选字段和新状态 | 旧字段继续接收，旧 ACK 不猜测关联 |
| SSE 事件 | 增加 `id:` 和 payload 字段 | 旧 Agent 忽略未知 JSON 字段 |
| Device JSON | 保留已有同步字段 | 改为投影来源，不立即删除 |
| Device Facts | 增加协议能力字段 | 从未上报能力时视为 legacy；已知设备后续省略字段则保持原值 |

任何删除、重命名或收紧公开字段的变更必须另行设计，不能包含在 P0 实施中的顺手重构。

## 18. 风险与缓解

| 风险 | 缓解措施 |
|---|---|
| 双写 Command 与 Device 投影不一致 | Command 先落库；投影可重建并记录失败 |
| ACK 在服务端落库前到达 | 必须先创建 Command 再投递事件 |
| 旧 ACK 错误关联新任务 | 禁止按设备、模块或时间窗口猜测 |
| 关机后无法确认物理状态 | 成功语义限定为 OS 命令已启动 |
| 升级替换成功但最终 ACK 丢失 | 任务超时；设备 Facts 版本仅作为证据，不自动改写任务终态 |
| JSON 文件随历史增长 | 有界保留；P1 前基于真实数据评估 SQLite |
| payload 中凭据进入历史 | Command 只存安全摘要并增加泄密反例测试 |
| 多 Server 同时写同一文件 | P0 明确不支持共享数据目录；多 Server 容灾仅指 Agent 地址故障转移 |
| Agent 多连接或 ACK 丢失导致重复高风险动作 | 本地持久账本、single-flight 与最终 ACK 重放 |
| 自动快照与显式同步竞争 | P0 自动快照不创建 Command；P1 以 desired-state generation 统一 |

### 18.1 实施前必须验证的既有执行链

- `PerformSelfUpgrade` 与 `Daemon.handleEvent` 当前都可能调度 `RestartCallback`。这是代码中的直接重复调用点；实施 P0 前必须通过调用计数测试确认并将重启职责收敛到唯一位置。

## 19. 实施验证记录（2026-08-24）

- 外部服务与关键假设：本轮协议验证仅使用本机真实 HTTP/SSE 服务；未调用 GitHub、CDN 或公开升级服务。候选 Server 必须让 v0.4.4 Agent 忽略新增 SSE 字段并把无 ID ACK 保持为 legacy；候选 Agent 必须在 v0.4.4 Server 拒绝 `control_protocols` 时去掉该字段重试。
- 真实请求链一：由 Git `HEAD` 源码构建的 v0.4.4 Agent 连接候选 v0.5.0 Server，经登录、设备注册、Facts、SSE 和 `POST /devices/{id}/sync` 完成同步。触发响应和查询结果均为 `legacy_untracked`，无 ID ACK 未关联 Command。
- 真实请求链二：候选 v0.5.0 Agent 连接由 Git `HEAD` 源码构建的 v0.4.4 Server。首次带 `control_protocols` 的 Facts 被旧 Server 以 HTTP 400 拒绝，Agent 去掉能力字段重试后成功；无 `command_id` 的 SSH 同步事件与 legacy ACK 完成。
- 重定向 / 响应链：上述本地端点均无 HTTP 重定向；管理登录、注册、同步与查询最终响应均为 HTTP 200。Facts 降级链为 HTTP 400 → 去除新字段重试 → HTTP 200。
- 测试替身：单元测试中的 Broker、HTTP RoundTripper 和临时文件仓储来自上述真实协议结构；差异是它们不覆盖网络中断、反向代理、CDN、OAuth 或真实操作系统关机/升级副作用。
- 关键反例：跨设备 Command 返回 404、Kind 不匹配返回 409、未知 ACK 状态返回 400、终态冲突返回 409、晚到 ACK 审计保持原终态、旧 Server 拒绝新 Facts 字段后显式降级。
- 未完成的正式验收：仓库没有 v0.4.4 tag 或正式发布制品，本轮使用的是 `HEAD` 源码快照；macOS 以外的 Linux、OpenWrt、Windows 真实执行观察，以及“上一正式版本 → 候选版本”的公开服务升级冒烟尚未执行，因此不能据此宣告发布完成。
- `ScheduleShutdown` 当前异步执行且不向调用方返回结果。必须改造成可观察的调度结果通道或回调，才能发送可靠的最终 ACK；不得把“已进入 goroutine”视为成功。

## 19. 开放决策

以下事项必须在编码前形成 ADR，不得由实现者临时决定：

- [ ] ADR-001：Command ID 格式、随机熵和日志展示长度。
- [ ] ADR-002：`commands.json` 文件布局、最大记录数与保留周期。
- [ ] ADR-003：各 Kind 的默认超时及真实平台测量结果。
- [ ] ADR-004：Device 投影失败后的重建入口和一致性检查。
- [ ] ADR-005：旧响应字段的具体保留周期与移除门槛。
- [ ] ADR-006：升级与关机互斥时的 API 错误语义。
- [ ] ADR-007：Agent 本地 Command 账本格式、保留期和崩溃恢复语义。
- [ ] ADR-008：各 Kind Result schema 与 Device 投影重建规则。

## 20. 完成定义

- [ ] 所有受控操作均通过 Command Service 创建并获得 `command_id`。
- [ ] 新 Agent 的每个 ACK 均能唯一关联 Command。
- [ ] Agent 对同一 `command_id` 的高风险动作最多执行一次，并可在重启后重放最终 ACK。
- [ ] Device Registry 不再作为任务生命周期事实来源。
- [ ] 重复、乱序、跨设备和跨模块 ACK 均通过测试验证。
- [ ] API 和 Dashboard 能区分创建、投递、接受、成功、失败、超时与中断。
- [ ] 批量操作按独立 Command 聚合每台设备状态，分别展示未创建任务、已分发、失败、超时及最终收敛；离线、无监听或投递不可用设备不得计为已分发，HTTP 请求受理成功不得展示为整体成功。
- [ ] 旧 Agent 兼容路径通过上一正式版本真实测试。
- [ ] 所有新增或修改的可执行逻辑具有对应测试。
- [ ] 客户端版本号已升级。
- [ ] 变更范围、架构依赖、新模块测试、全量回归与 Diff Coverage 全部通过。
- [ ] 交付记录列出外部假设、真实验证、测试替身差异和全部修改文件。
