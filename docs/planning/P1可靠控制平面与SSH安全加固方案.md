## 2. 当前代码基线

### 2.1 已有能力

当前代码提供以下可复用基础：

| 能力 | 代码证据 | 当前边界 |
| --- | --- | --- |
| Command 状态模型 | `internal/command/model.go` 的 `Command`、`Status`、`Transition` | 已有 `queued`、`dispatching`、`dispatched`、`accepted`、终态及 `Revision`；没有独立 Delivery 记录和离线租约 |
| Command 文件仓库 | `internal/command/file/repository.go` | 有 `schema_version=1`、原子写入、幂等键、截止时间查询和重启后读取；当前截止时间来自接受/完成超时策略，不是离线投递 TTL |
| Command 服务 | `internal/command/service.go` | 已有创建、投递、接受、完成、取消、超时和晚到 ACK 处理；没有重连恢复调度器 |
| SSE Broker | `internal/broker/broker.go` | 内存连接表、单播、广播和有限缓冲；无事件历史、稳定序号、断线补发和持久化 |
| SSE HTTP 接口 | `internal/api/api.go` 的设备事件路由与 ACK 处理 | 已有 `command_id`、ACK 关联和连接状态判断；需补 `Last-Event-ID` 语义及重连同步入口 |
| SSH 同步 | `internal/sshsync/managed.go`、`internal/sshsync/ssh.go` | 有托管区、算法+主体去重、设备锁和 SSH 兜底；公钥解析仍以字段数量为主，写入与 known_hosts 仍需更严格安全契约 |
| 健康与告警 | `internal/health`、`internal/alerting` | 已有文件仓库、健康事件、告警去重、恢复和 Webhook 投递；不负责离线任务恢复，也不替代安全审计 |

### 2.2 已知缺口

当前 `Broker.Publish` 没有连接时会返回 0，调用方可将任务标记为投递失败；这符合 P0 在线语义，但不能满足 P1 的“离线可延迟投递”。同时，Broker 缓冲区满时丢弃事件，没有可查询的事件日志，因此不能直接宣称支持 `Last-Event-ID` 恢复。

当前 `UpdateManagedBlock` 能拒绝多个或不完整托管区，但没有独立的严格公钥算法白名单、私钥内容分类、options 保留契约、文件权限/符号链接检查和同文件系统原子替换流程。`SyncDevice` 已有设备级互斥锁，但它只覆盖单一 Server 进程内的 SSH 操作，不能解决多进程或文件外部修改竞态。

## 3. 范围与非目标

### 3.1 本阶段范围

1. 为可延迟任务定义投递 TTL、租约、重连恢复和幂等语义。
2. 为 SSE 事件定义稳定 ID、保留窗口、`Last-Event-ID` 和无法补发时的重新同步语义。
3. 让服务端重启后能够恢复任务与投递状态，并安全处理在途任务。
4. 为 SSH 公钥输入、托管区、原子写入、备份和并发修改定义统一安全契约。
5. 让 SSE、SSH 兜底和本地离线应用复用同一个 KeySet 应用核心。
6. 为过期、取消、重复投递、私钥混入、符号链接和并发修改建立负例测试。

### 3.2 非目标

- 本阶段不修改 P0 已有 `command_id`、ACK 字段和既有终态含义。
- 不把健康状态或告警状态直接改造成任务状态。
- 不实现任意 Shell、远程 Runbook、备份恢复 CLI 或 SQLite 迁移。
- 不在离线状态自动执行关机和升级，除非后续专项设计明确授权且有二次确认。
- 不把内存 Broker 的现有缓冲区当作可靠消息队列。
- 不保存或备份任何私钥内容。

## 4. 离线任务模型

### 4.1 状态与跨层映射

业务状态与协议状态必须分开。服务端内部建议保留现有 Command 状态，并新增投递记录：

| 业务事实 | Command 状态 | Delivery 状态 | Agent 行为 |
| --- | --- | --- | --- |
| 已创建，尚未选择投递 | `queued` | `pending` | 不执行 |
| 已取得投递租约 | `dispatching` | `leased` | 等待发送 |
| 已加入在线连接 | `dispatched` | `sent` | 只能按幂等键执行一次 |
| Agent 明确收到 | `accepted` | `accepted` | 执行或报告失败 |
| 完成成功 | `succeeded` | `completed` | 记录最终 ACK 摘要 |
| 完成失败 | `failed` | `completed` | 记录错误码，不自动重放副作用 |
| 接受/完成截止时间到期 | `timed_out` | `expired` | 过期任务不得执行 |
| 管理员取消 | `canceled` | `canceled` | 设备晚到时必须拒绝 |
| 服务端重启发现旧在途记录 | 保持原终态或转 `interrupted` | `recovery_pending` | 由恢复器重新判断，不直接重投 |

新增 Delivery 记录至少包含：`delivery_id`、`command_id`、`device_id`、`attempt`、`lease_until`、`sent_at`、`accepted_at`、`completed_at`、`last_event_id`、`status` 和错误摘要。所有记录以 `command_id + device_id` 隔离，不允许跨设备复用。

### 4.2 TTL 与任务策略

每个 Command 在创建时冻结 `delivery_ttl` 和 `finish_deadline`。服务端时间是唯一过期依据，设备时间仅用于诊断。

初始策略建议：

| Kind | 离线排队 | 默认投递 TTL | 风险规则 |
| --- | --- | --- | --- |
| `ssh_keys` | 允许 | 24 小时 | 同一设备保留最新有效 KeySet，旧未投递计划可合并 |
| `github_credentials_sync` | 允许 | 1 小时 | 重连时重新校验凭据版本和授权 |
| `github_credentials_revoke` | 允许 | 24 小时 | 吊销优先于同类同步 |
| `shutdown` | 禁止默认排队 | 5 分钟 | 离线创建后必须过期，禁止晚到执行 |
| `upgrade` | 禁止默认排队 | 15 分钟 | 必须重新确认版本、平台、哈希和在线状态 |

这些数值是首版候选值，实施前必须通过真实设备和现有升级链观察确认，不得直接当作最终产品参数。

### 4.3 投递与重连流程

```text
创建 Command
  ↓
持久化 Command + Delivery(pending)
  ↓
设备在线？──否──→ 等待重连或 TTL 到期
  │
  是
  ↓
原子取得租约
  ↓
发送带 command_id/delivery_id/event_id 的事件
  ↓
收到 accepted ACK？──否──→ 租约到期后有限重试
  │
  是
  ↓
执行完成 ACK
  ↓
CAS 更新终态；晚到 ACK 只进入审计记录
```

重连时 Agent 必须先发送自身已持久化的最近执行 ID/幂等键摘要，服务端再返回：

- 可继续投递的有效任务；
- 已完成但 Agent 未确认的结果；
- 已取消或已过期任务的拒绝结果；
- 需要全量重新同步的标记。

恢复流程每次异步 I/O 返回后都必须重新校验任务版本、设备身份、租约和 TTL，避免在途竞态覆盖新状态。

## 5. SSE 事件恢复

### 5.1 事件契约

每个持久化或可恢复事件必须具有稳定 `event_id`，建议由服务端单调递增序列或 `device_id + sequence` 组成。事件至少包含：

```json
{
  "id": "device-123:00000042",
  "type": "command",
  "command_id": "...",
  "delivery_id": "...",
  "data": {}
}
```

现有 `broker.Event.ID` 字段可以作为协议承载字段，但不能继续使用空 ID 或仅用当前时间戳推断顺序。

### 5.2 `Last-Event-ID` 规则

- Agent 首次连接不带 `Last-Event-ID`：执行当前设备状态同步，再接收新事件。
- 带有仍在保留窗口内的 ID：补发该 ID 之后的事件，并保持事件顺序。
- ID 不存在、已被清理或序列不连续：返回 `resync_required`，Agent 执行幂等的全量状态同步。
- 补发期间产生的新事件必须进入同一有序队列，不得插入旧事件之前。
- 任务执行不能只依赖 SSE 补发；Command/Delivery 恢复仍是最终事实来源。

事件保留窗口、最大事件数和缓冲区满行为必须配置化，并在满载测试中证明不会静默宣称成功。

## 6. SSH 同步安全模型

### 6.1 KeySet 解析与校验

KeySet 应先解析成结构化条目，再生成目标文件。每个条目必须校验：

- 算法在明确白名单内；
- 公钥主体可被 OpenSSH 解析器验证；
- 不含私钥头、PEM、PuTTY 标记或换行嵌入内容；
- 算法与 Key Body 组成唯一身份；
- 注释只作为展示字段，不参与身份判断；
- 设备 ID 经过注释字符规范化，不得改变 key/options 语义。

解析失败必须返回错误并保持原文件、备份和投影状态不变。

### 6.2 托管区与用户内容

托管区必须满足：

- 只有一对 `BEGIN/END` 标记；
- 标记顺序正确且不嵌套；
- 托管区外原有 key、options、注释和空行按契约保留；
- 托管区内只写入规范化后的 KeySet；
- 缺标记、多标记、嵌套、非法行或外部文件变更均安全失败。

### 6.3 原子写入与并发

统一应用核心应使用：

1. `Lstat` 检查目标不是不允许的符号链接；
2. 读取并记录文件 inode/大小/摘要；
3. 解析、校验并生成新内容；
4. 在同一文件系统创建权限受控的临时文件；
5. 写入、`fsync` 文件并同步目录；
6. 再次确认源文件未被外部修改；
7. 写入不含私钥的备份并校验备份摘要；
8. 原子替换并复读验证权限、摘要和托管区。

单进程设备锁仍需保留；若部署允许多进程 Agent，必须增加跨进程锁或明确单写者约束。任何一步失败均不得发布成功 ACK。

### 6.4 应用入口统一

SSE `key_sync`、SSH `homeagent-agent apply-keys` 和本地离线应用必须调用同一个 KeySet 应用核心。入口差异只允许存在于：

- 身份认证；
- 输入来源；
- 结果回执协议；
- 日志上下文。

不能让不同入口各自实现托管区替换、去重和权限处理。

## 7. 健康告警的 P1 边界

现有 `internal/health` 与 `internal/alerting` 已完成健康快照、历史、Webhook、去重、静默和恢复。本方案只规定它们与新增能力的接口边界：

- 健康评估消费 Command 的终态和事实快照，不直接修改 Command 状态；
- 离线任务的 `expired`、`canceled`、`failed` 可形成健康原因，但必须区分“任务失败”和“设备离线”；
- 告警状态先落库，再发送通知；通知失败不能回滚健康状态；
- SSH 同步失败应使用稳定 `reason_code` 和脱敏错误摘要；
- 服务端重启后不得因为空内存状态生成虚假的恢复通知；
- Webhook 投递记录与 Command/Health/Alert 各自使用独立 ID，不混用状态字段。

## 8. 实施拆分

### 阶段 A：离线任务契约

- 新增 Delivery 数据模型和 Repository 端口；
- 为现有文件仓库增加 schema version 迁移策略；
- 增加 TTL、租约、CAS 和重连恢复测试；
- 明确高风险任务默认不离线排队。

### 阶段 B：SSE 恢复

- 扩展 Broker 事件序号和有限历史；
- 增加 `Last-Event-ID` 解析、补发和 `resync_required`；
- 增加缓冲区满、序列断裂和重连竞态测试；
- Agent 保存并上报最近事件 ID。

### 阶段 C：SSH 安全核心

- 引入严格 KeySet parser/validator；
- 重写托管区应用为可验证的纯函数加原子文件适配器；
- 增加权限、备份、符号链接和外部修改检查；
- 统一 SSE、SSH 和离线入口。

### 阶段 D：跨层接入与验收

- 将 Delivery 终态接入健康原因投影；
- 验证告警去重、恢复和重启行为；
- 完成上一正式版本到候选版本的真实 Agent/Server 兼容验收；
- 更新路线图状态和实施证据。

## 9. 测试策略与验收证据

### 9.1 必须有的负例

- 重复幂等键但请求摘要不同：拒绝且无新任务；
- 任务已取消或过期后晚到 ACK：只记录晚到 ACK，不执行副作用；
- 设备身份或租约版本不匹配：拒绝更新；
- `Last-Event-ID` 不存在或过期：返回重新同步，不伪造补发成功；
- 缓冲区满：任务不能被标记为已投递成功；
- 私钥、非法算法、截断公钥：拒绝且原文件字节不变；
- 多个/嵌套/缺失托管区：拒绝且不产生备份或替换副作用；
- 目标是符号链接、文件在校验后被外部修改：拒绝替换；
- 并发应用不同 KeySet：只允许一个版本按 CAS 成功，另一个显式冲突；
- 告警通知失败：健康和告警事实仍已落库，不能重复创建告警。

### 9.2 真实协议与跨版本验收

必须使用真实本地 TCP 端口验证 SSE、ACK 和 Webhook 协议；fixture 必须注明来源和与真实协议的差异。涉及升级时，必须通过上一正式版本的真实用户入口运行 Server/Agent 双向兼容、重连、过期任务和回滚路径。

### 9.3 完成标准

P1 离线任务完成的直接证据：

- 服务端重启后任务和 Delivery 状态可恢复；
- 重连恢复不重复执行，过期/取消任务不执行；
- SSE 事件可补发或明确进入全量同步；
- 全量 `-race`、真实端口协议和 Diff Coverage 门禁通过。

P1 SSH 加固完成的直接证据：

- 所有入口复用同一 KeySet 应用核心；
- 校验、并发或写入失败时原 SSH 文件字节不变；
- 重复 KeySet 幂等，托管区外内容保留；
- 备份不含私钥，上一正式版本升级和恢复演练通过。
