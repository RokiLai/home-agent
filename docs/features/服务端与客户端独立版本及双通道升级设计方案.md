# 服务端与客户端独立版本及双通道升级设计方案

## 2. 背景与直接证据

HomeAgent 当前由 Server 和 Agent 两类生命周期不同的组件组成。Agent 分布在路由器、macOS、Linux 和 Windows 设备上，迭代及安全修复更频繁；Server 通常由单一实例托管，升级频率较低。二者继续共用版本会把任一组件的发布误表达为全系统同时升级。

当前代码和发布链存在以下直接事实：

1. `internal/version/version.go` 只有一个 `defaultVersion`、可注入变量 `Version` 和读取函数 `Get()`，Server 与 Agent 共用。
2. `.github/workflows/release.yml` 从该共享版本源读取一个版本，构建全部 Server/Agent 资产，并用同一个 `v*` 标签创建 GitHub Release。
3. `internal/githubrelease/client.go` 使用 GitHub `GET /repos/{owner}/{repo}/releases/latest`，该接口只能返回仓库级最新 Release，不能区分 Server 与 Agent。
4. `GET /api/v1/system/version-check` 当前只返回一组 `current_version/latest_version/has_update`。
5. `POST /api/v1/system/upgrade` 和 Server CLI 自升级使用仓库级最新 Release；设备升级也从同一版本空间解析 Agent 资产。
6. `internal/health` 的 Agent 版本规则需要“推荐 Agent 版本”，不能使用 Server 最新版本代替。
7. 当前 Web 静态代码中没有调用 `/api/v1/system/version-check` 或 `/api/v1/system/upgrade` 的入口；已有能力只能由 API 或 CLI 显式触发。
8. 已发布的历史 `v0.6.13` 同时包含 Server 和 Agent 资产，必须保留为兼容基线，不得删除或重写。

## 3. 目标与非目标

### 3.1 目标

1. Server 与 Agent 分别拥有独立、可链接器注入的版本来源。
2. 同一 GitHub 仓库使用 `server-v*` 与 `agent-v*` 两条 Release 通道。
3. Server 同时检测自身最新版本和 Agent 最新推荐版本，并独立缓存、展示错误与更新时间。
4. 管理员能够从控制台检查 Server 更新、确认后执行 Server 自升级。
5. 服务端根据最新 Agent Release、设备版本、平台资产和在线状态提示单设备或批量升级。
6. Agent 不后台查询 GitHub；只执行服务端冻结并下发的目标版本、URL 和 SHA256，同时保持本地独立验证。
7. 兼容现有无组件前缀的 `v*` Release 和 API 消费方，迁移失败时安全停止，不误报最新或自动安装。

### 3.2 非目标

- 不实现无人确认的 Server 或 Agent 自动安装。
- 不让 Agent 定时请求 GitHub API 或自行决定目标版本。
- 不把 GitHub 可达等同于 Release 可用；资产、SHA256 和目标平台必须分别验证。
- 不删除、覆盖或重新标记历史 `v*` Release。
- 不在本设计任务中修改 Go 代码、GitHub Actions、Web 界面或生产环境。
- 不引入新的第三方依赖或独立更新服务。

## 4. 核心决策

### 4.1 内部版本与外部标签分离

内部组件版本保持标准形式 `vMAJOR.MINOR.PATCH`，GitHub 标签增加组件命名空间：

| 组件 | 内部版本示例 | GitHub 标签示例 | 资产前缀 |
| --- | --- | --- | --- |
| Server | `v0.6.15` | `server-v0.6.15` | `homeagent-server-` |
| Agent | `v0.6.15` | `agent-v0.6.15` | `homeagent-agent-` |

组件前缀只属于发布通道，不进入协议中的版本比较值。迁移前设备 Facts 和 Server 版本接口继续上报当前 `v0.6.13`，bridge 后分别上报各自内部 `v*`，避免现有 SemVer 比较器处理非数字组件名。

首个成功发布的迁移版本固定为 `v0.6.15`（`v0.6.14` 候选因发布门禁失败，从未形成 Release）。它先作为最后一个 legacy `v0.6.15` Release 发布，使当前 `v0.6.13` Server/Agent 能通过既有真实入口升级到理解双通道的桥接版本；验证通过后，同一合并提交分别创建 `server-v0.6.15` 与 `agent-v0.6.15` 基线 Release。三个 Release 中同名组件资产必须逐字节 SHA256 相同。此后两个内部版本独立递增，不重置 Server 版本，也不要求二者保持相等。

### 4.2 版本来源

实现阶段将共享版本源拆分为两个明确入口：

```text
ServerVersion / GetServer()
AgentVersion  / GetAgent()
```

要求：

- 每个组件只能有一个默认版本字面量；
- 两个变量都保留 `-ldflags -X` 注入能力；
- `homeagent-server version`、Server API 和 Server 自升级只读取 Server 版本；
- `homeagent-agent version/info`、Facts、升级 ACK 和健康策略只读取 Agent 版本；
- 质量门禁根据修改的可执行逻辑决定必须提升哪个组件版本；同时修改两类组件时必须分别提升。

旧 `Version/Get()` 不得长期保留为含糊入口。迁移必须一次性列出全部调用点并改为组件明确入口；若为兼容临时保留，必须标记废弃且只存在于一个有截止版本的迁移阶段。

### 4.3 发布通道

将单一 Release 工作流拆分为两个独立工作流：

```text
Server 发布：读取 ServerVersion → 构建 Server 矩阵 → 创建 server-v*
Agent 发布：读取 AgentVersion  → 构建 Agent 矩阵  → 创建 agent-v*
```

触发契约：

- 保留 `dev → main` PR 合并作为正式发布入口；
- Server 工作流只在 Server 版本源发生变化时运行；
- Agent 工作流只在 Agent 版本源发生变化时运行；
- 同一 PR 同时提升两个版本时允许两个工作流独立运行、独立成功或失败；不得根据其中一个成功推断整体成功；
- 发布前必须运行适用质量门禁，不能继续只构建、不测试；
- 工作流先创建 draft Release，上传全部资产并核验名称、数量、大小和 SHA256 后才发布；
- 同一标签与目标提交的未发布 draft 允许幂等续传或删除后重建；标签指向其他提交、资产同名但摘要不同或 Release 已公开时必须安全失败，绝不覆盖公开历史资产；
- 每个资产必须同时发布 `.sha256`，并验证文件名、摘要内容和 GitHub 返回的上传状态；
- Server Release 不包含 Agent 资产，Agent Release 不包含 Server 资产。

## 5. GitHub 双通道发现协议

### 5.1 为什么不能使用 `/releases/latest`

GitHub 的仓库级 Latest Release 没有组件维度。任意一次 Agent 发布都可能覆盖 Server 的“latest”，反之亦然。因此双通道启用后，版本发现不得再以 `/releases/latest` 作为权威来源。

### 5.2 发现规则

Server 使用 GitHub Releases 列表接口，分别筛选：

```text
server-v<SemVer>
agent-v<SemVer>
```

每个通道独立执行以下规则：

1. 忽略 draft；默认忽略 prerelease，除非未来增加显式预发布通道。
2. 标签必须严格匹配组件前缀和规范 SemVer；单个非法标签只产生诊断告警并跳过，不导致整个通道失败；只有响应结构、分页或候选集合无法可靠解析时才使通道失败。
3. 去除组件前缀后按 SemVer 取最大值，不能依赖 GitHub 返回顺序或发布时间代表版本大小。
4. 必须处理分页；每页固定 100 条，最多扫描 10 页。GitHub 明确返回末页前完成；达到第 10 页仍存在下一页时返回 `status=error, error_code=incomplete`，不得把当前最大值宣称为最新。
5. 选定 Release 后，按组件和目标平台核验二进制资产与 `.sha256` 同时存在。
6. SHA256 文本必须严格解析为 64 位十六进制摘要，并与目标资产名称匹配。
7. HTTP 超时、限流、非 2xx、JSON 非法、分页不完整、候选集合中没有任何合法组件标签或资产缺失均产生结构化错误。

### 5.3 独立持久化快照与刷新调度

Server 与 Agent 通道分别维护缓存，不共享“最后成功”：

| 字段 | 含义 |
| --- | --- |
| `status` | 通道状态全集：`unknown/checking/available/stale/error` |
| `current_version` | 本机 Server 版本；Agent 通道为空 |
| `latest_version` | 最近一次可信 GitHub 结果 |
| `checked_at` | 本次检查完成时间 |
| `last_success_at` | 最近一次成功时间 |
| `stale` | 当前展示是否来自过期缓存 |
| `error_code/error_message` | 脱敏后的失败原因；`incomplete`、`migration_required`、`rate_limited`、`github_unavailable`、`invalid_response`、`artifact_manifest_incomplete` 均为 error code，不是 status |
| `release_url` | 对应组件 Release 页面 |
| `release_id/tag/commitish` | 冻结的 Release 身份 |
| `assets` | 按受支持平台记录 asset ID、名称、大小和 SHA256 |
| `retry_at` | 失败后的最早重试时间 |

两个快照以全局唯一组件键 `server`、`agent` 原子写入 Server 数据目录，包含 schema version；不得写入 Token 或原始响应。启动时先恢复快照，再异步刷新。调度参数固定为：

- `request_cache_ttl=10m`：10 分钟内的普通读取复用结果；
- `check_interval=6h`：成功后下一次后台检查间隔；
- `max_stale_age=24h`：最后成功超过 6 小时标记 `stale`，超过 24 小时转 `unknown`；
- 失败重试为 5 分钟、15 分钟、30 分钟、60 分钟，之后保持 60 分钟上限并加入小于 20% 抖动；
- 同一组件所有后台、页面和 API 刷新使用 singleflight；不同组件允许并行；
- GitHub 返回限流时尊重 `Retry-After` 或 rate-limit reset，且不得早于本地退避时间。

定时检查只更新版本快照和提示，不执行安装。没有可信快照时为 `unknown`；检查失败保留 24 小时内最近可信数据并标记 `stale`，不得返回 `has_update=false` 冒充已是最新。

状态转换如下：

| 当前状态 | 事件 | 下一状态 | 数据处理 |
| --- | --- | --- | --- |
| `unknown` | 开始检查 | `checking` | 保留空结果 |
| `available/stale/error` | 开始检查 | `checking` | 保留最近可信结果供并发读取 |
| `checking` | 完整成功 | `available` | 原子替换快照，清空错误与退避 |
| `checking` | 失败且最近成功不超过 24h | `stale` | 保留可信结果，写错误和 `retry_at` |
| `checking` | 失败且无可信结果或已超过 24h | `error` | 不提供 latest，写错误和 `retry_at` |
| `available` | 距 `last_success_at` 超过 6h | `stale` | 保留可信结果，设置 `stale=true`，后台检查或退避不变 |
| `stale/error` | 时间跨过 24h 且未恢复 | `unknown` | latest 不再参与判断，保留审计时间 |

`checking` 是内部持久化状态，但读 API 不把一次刷新暂时变成不可判定：存在最近可信结果时仍返回该结果及原 `update_state`，同时返回 `refreshing=true`；结果已超过 6 小时则还返回 `stale=true`。不存在可信结果时返回 `status=checking, update_state=unknown`。检查成功或失败后才原子写入最终状态。快照或 `dual_channel_ready` 落盘失败视为本次检查失败：保留旧文件和内存中的最近可信快照，返回 `error_code=persistence_failed`；首次落盘失败时不得启用双通道或创建升级操作。

## 6. 服务端检测与升级契约

### 6.1 版本快照 API

新增 `GET /api/v2/system/version-status` 作为双通道权威接口，避免旧布尔字段无法表达 unknown/error 的兼容矛盾：

```json
{
  "server": {
    "status": "available",
    "current_version": "v0.6.15",
    "latest_version": "v0.6.15",
    "update_state": "update_available",
    "checked_at": "2026-09-11T04:00:00Z",
    "last_success_at": "2026-09-11T04:00:00Z",
    "stale": false,
    "release_url": "https://github.com/RokiLai/home-agent/releases/tag/server-v0.6.15"
  },
  "agent": {
    "status": "available",
    "latest_version": "v0.6.15",
    "checked_at": "2026-09-11T04:00:00Z",
    "last_success_at": "2026-09-11T04:00:00Z",
    "stale": false,
    "release_url": "https://github.com/RokiLai/home-agent/releases/tag/agent-v0.6.15",
    "device_summary": {
      "current": 2,
      "update_available": 1,
      "offline": 0,
      "artifact_unavailable": 0,
      "upgrade_in_progress": 0,
      "unknown": 0
    }
  }
}
```

通道 `status` 只表达 GitHub 快照可用性。Server 的 `update_state=current|update_available|unknown` 由当前 Server 与最新 Server 版本派生；Agent 是否需更新只能按设备聚合，Agent 通道本身不返回含糊的 `has_update`。

现有 `GET /api/v1/system/version-check` 在 bridge 中保持原字段结构，但数据源改为 Server 通道快照，顶层版本值不包含 `server-` 前缀；它仅供旧 UI/调用方兼容，不再使用仓库级 `/releases/latest`，并附加 `deprecated=true` 与 v2 路径。双通道基线建立后它仍可查询但不参与新 UI；删除或改变其既有字段必须另建 API 退役任务。它在 Server 通道错误且没有可信快照时维持历史 `200 + has_update=false + error` 行为，这是明确保留的旧接口局限，新实现和健康规则严禁消费该布尔值。

普通 v2 查询使用现有 `instance.settings.read`，只读取缓存并按 TTL 触发 singleflight 普通刷新。`refresh=true` 或 `force=true` 需要 `instance.settings.manage`，按用户和实例限频为每分钟一次，并同时强制刷新两个通道。可用 `component=server|agent` 只刷新一个通道；非法值返回 400。页面普通读取权限与 Owner 手动强刷入口必须保持一致。

### 6.2 Server 自升级

现有 `POST /api/v1/system/upgrade` 只允许选择 `server-v*` Release：

1. 使用不超过 10 分钟的冻结 Server Release 快照确定 Release ID、tag、commitish、目标版本、平台 asset ID/大小和 SHA256；过期则先刷新，刷新失败不升级；
2. 拒绝 Agent 标签、无前缀历史标签和错误资产前缀；
3. 下载当前 `GOOS/GOARCH` 的 Server 资产；
4. 校验 SHA256、执行 `version` 冒烟并验证输出等于内部目标版本；
5. 创建全局唯一 operation ID 和持久化升级记录，按 `prepared → replacing → restarting → verifying → succeeded` 流转；
6. 替换前保存可恢复旧二进制及摘要，原子替换并由现有服务管理器重启；
7. 新进程必须在 60 秒内加载同一 operation，验证运行版本、目标二进制摘要和健康端口后标记 `succeeded`；失败由独立恢复脚本把旧二进制原子恢复并重启，记录 `rolled_back`；恢复也失败则为 `failed/manual_recovery_required`；
8. 控制台通过 operation ID 查询重启后的持久化状态，只有 `succeeded` 显示完成。

执行权限继续使用 `instance.settings.manage`，并限制实例 Owner。检查更新不等于授权升级；定时任务严禁调用升级接口。同一时间只允许一个非终态 Server 升级 operation，所有状态转换必须 CAS，重启或请求重放不得重复替换。

创建接口成功返回 `202` 和 `{operation_id,status:"prepared",target_version}`；同一 Owner 在目标版本相同且已有非终态操作时返回同一 operation，目标不同则返回 `409 upgrade_in_progress`。新增 `GET /api/v2/system/server-upgrades/{operation_id}`，Owner 可查询 `status/target_version/created_at/updated_at/error_code/rollback_status`；不存在返回 404，非 Owner 返回 403。查询无副作用，终态永久保持幂等，控制台在重启断线后使用同一 ID 轮询收敛。

恢复能力作为安装时一并部署、与候选二进制分离的固定 supervisor helper，由现有服务管理器启动而非新进程自行调用。升级记录和旧二进制先 fsync，再进入 `replacing`；helper 观察服务退出及 60 秒验证租约。各阶段恢复规则固定为：`prepared` 崩溃只清理临时文件；`replacing` 启动时根据记录的当前/候选摘要完成替换或恢复旧文件；`restarting/verifying` 超时恢复旧二进制并重启；`succeeded` 不再回滚；`rolled_back/failed` 只允许人工重试。实现前必须针对项目实际使用的 systemd、launchd 及 OpenWrt procd 分别确认 helper 安装位置、权限、启动命令和断电原子性；任一受支持服务管理器没有可验证恢复主体时不得开放 Server 自升级。

## 7. Agent 检测、提示与升级契约

### 7.1 集中检测

Server 先按标签选定最高 Agent Release，不因部分资产缺失静默降级到旧版本。正式 Agent Release 必须包含当前发布矩阵中的 Linux `amd64/arm64/arm/mips/mipsle`、Darwin `amd64/arm64`、Windows `amd64/arm64` 二进制及各自 `.sha256`；缺少任一必需资产使通道进入 `status=error, error_code=artifact_manifest_incomplete`。未来增删受支持平台必须先修改发布矩阵和兼容契约。每台设备的提示由以下事实独立聚合：

```text
设备 AgentVersion
+ 设备 OS/Arch
+ Agent Release 最新可信版本
+ 对应资产及 SHA256 可用性
+ 设备 connected/last_seen 健康状态
+ 是否已有非终态 UpgradePlan
→ current / update_available / offline / artifact_unavailable / upgrade_in_progress / unknown
```

状态按 `upgrade_in_progress > offline > unknown > artifact_unavailable > update_available > current` 的顺序取第一个命中值，确保每台设备只计入一个桶。`last_upgrade_failed` 是独立附加标志，来源于该设备最近一个终态 UpgradePlan，不参与互斥计数。不得只根据版本号更大就显示“可升级”。批量结果必须由每台设备的独立状态聚合。

### 7.2 Agent 执行边界

Agent 不调用 GitHub Releases API，也不后台自行决定升级。Server 下发时冻结：

- 内部目标版本 `v*`；
- `agent-v*` Release 标识；
- 与设备 OS/Arch 匹配的资产 URL；
- SHA256；
- UpgradePlan/Command 标识及超时策略。

Agent 仍必须独立验证 HTTP 状态、下载超时、SHA256、候选二进制版本、OS/Arch、冒烟结果和原子替换条件。任何验证失败均清理临时文件、保留原二进制并回报失败。下载 GitHub 资产不得复用 SSE 的无限总超时；现有单制品 120 秒预算继续生效。

单设备与批量升级继续使用现有 `devices.upgrade` 权限。控制台提交前必须确认目标 Agent 版本、Release、设备数量、离线/不可升级排除数量及重启影响；单设备可使用一次确认，批量操作必须二次确认。离线设备默认返回 `skipped(device_offline)`，不排队。服务端为每台设备独立创建 Plan/Command，HTTP 聚合结果逐项返回 `dispatched/skipped/failed`，不得因请求受理或部分成功宣称整体成功。

升级请求只接受服务端版本快照 ID 和设备 ID 列表；拒绝调用方自带 `target_version`、下载 URL 或 SHA256，防止绕过冻结快照。响应顶层为 `overall_status=all_dispatched|partial|none_dispatched` 及三个精确计数，并为每个设备返回 `device_id/result/reason_code/plan_id`；HTTP 202 表示至少一台已投递，全部跳过或失败使用 409 并仍返回逐项结果，鉴权或请求结构错误分别使用 403/400。

### 7.3 健康规则

`agent_version_outdated` 只比较设备 Agent 版本与 Agent 通道推荐版本。Server 通道失败不得让设备降级；Agent 通道为 `unknown/error/stale` 时不得新触发“版本落后”，已有规则是否维持需按最近可信快照和过期阈值明确处理：

- 缓存仍在允许陈旧窗口内：保留最近可信判断并标记依据陈旧；
- 超过陈旧窗口：版本规则转 `unknown`，不得误报恢复或最新；
- 新鲜 Agent 快照恢复后重新求值。

## 8. 控制台交互

## 9. 状态与失败矩阵

| 场景 | Server 通道 | Agent 通道/设备提示 | 副作用 |
| --- | --- | --- | --- |
| GitHub 两通道均成功 | 通道 `available`，派生 `update_state` | 通道 `available`，按设备派生提示 | 仅更新快照 |
| Server 查询失败、Agent 成功 | `stale/error` | Agent 提示正常计算 | 不影响设备升级判断 |
| Agent 查询失败、Server 成功 | Server 提示正常 | `stale/error/unknown` | 不创建无冻结目标的 Agent 升级 |
| GitHub 限流 | 保留各自最近可信缓存并记录重试时间 | 同左 | 不忙等，不自动安装 |
| 单个标签非法 | 诊断告警并忽略 | 诊断告警并忽略 | 非法版本不参与排序 |
| 扫描分页不完整 | `error/incomplete` | `error/incomplete` | 不宣称最新 |
| Release 存在但必需平台资产缺失 | `error/artifact_manifest_incomplete` | 整个 Agent 通道不可用 | 不创建 Command/Plan，不静默回退 |
| SHA256 缺失或非法 | `error/artifact_manifest_incomplete` | 整个正式 Agent Release 不可用 | 不下发空哈希，不回退旧版 |
| Server 已是最新 | `available`，派生 `update_state=current` | 不相关 | 不替换、不重启 |

| 下载或验证失败 | 原 Server 保持运行或恢复为旧版 | 原 Agent 保持运行 | 清理临时文件并形成失败终态 |

## 10. 兼容迁移

### 10.1 历史 Release

历史 `v*` Release 只作为迁移基线，不继续参与双通道“最新”排序。唯一 bootstrap 顺序：

1. 阶段 A bridge PR 实现双通道读取和独立内部版本入口，但暂时保留统一工作流；将 Server 与 Agent 内部版本同时设为 `v0.6.15`，由统一工作流发布最后一个 legacy `v0.6.15`，包含完整 Server/Agent 资产；
2. 从当前正式 `v0.6.13` 分别通过真实 Server 自升级入口和真实设备入口升级至 bridge `v0.6.15`；
3. 在阶段 B 开始前完成迁移覆盖率门禁：所有已登记且在线的 `v0.6.13` Server/Agent 已升级，离线设备已被管理员明确豁免并记录；未满足时禁止公开任何带组件前缀的 Release，保证旧 `/releases/latest` 始终仍指向 legacy `v0.6.15`；
4. 阶段 B 发布切换 PR 将统一工作流替换为双工作流；一次性 bootstrap job 从已公开 legacy `v0.6.15` 按 asset ID 下载原始资产，分别创建 `server-v0.6.15` 与 `agent-v0.6.15` draft，不重新构建；验证新 draft 中所有资产 SHA256 与 legacy 逐字节相同后同时发布；
5. bridge Server 检测到两条组件通道基线后原子写入 `dual_channel_ready=true`，从此 latest 只读取组件标签；该标记持久化且不可因暂时查询失败回退；
6. 后续 Server 与 Agent 独立递增；legacy 发布工作流禁用，不再产生无前缀 `v*`；
7. 历史恢复只允许离线运维 CLI 使用显式 `component`、完整 tag、资产 URL 和 SHA256，不属于普通升级 API，也不参与 latest fallback。

bridge Server 在 `dual_channel_ready=false` 且某条基线缺失时返回 `status=error, error_code=migration_required`，附固定 bridge `v0.6.15` 身份；不得动态选择“最近历史版本”，也不得把另一组件 Release 当作回退。普通 Server 自升级只接受 `server-v*`；普通 Agent 升级只接受 `agent-v*`。离线历史恢复 CLI 必须二次确认，且不得由 Web API 调用。

### 10.2 API 与配置

- 保留现有 GitHub 仓库与镜像配置；两个通道默认使用同一仓库和镜像前缀。
- 现有 v1 版本检查端点维持 legacy 行为；新 UI、健康和升级决策只使用 v2 双通道端点。
- 现有设备 Facts 的 `agent_version` 字段不改名。
- 现有升级负载的 `target_version` 仍为内部 `v*`，新增 Release 通道信息只能作为追加字段。
- 不直接修改现有公开接口的字段类型或删除字段。

## 11. 安全与可观测性

- GitHub 响应、Release 元数据和 SHA256 属于外部输入，必须限制响应大小、严格解析并设置超时。
- `.sha256` 响应上限 4 KiB，只接受 `<64位十六进制><一个或两个空格><精确资产文件名>` 加可选单个 LF；摘要比较忽略十六进制大小写，文件名必须逐字节匹配且禁止路径分隔符、控制字符或解码后变化。
- Release 说明不得未经转义直接插入 HTML。
- 日志记录组件、检查状态、HTTP 状态、Release 标签和请求 ID；不得记录 Token、Cookie、带凭据 query 的 URL 或完整响应正文。
- Server/Agent 升级事件分别使用组件明确的 reason code，不能共用含糊的 `upgrade_failed` 而无法区分主体。
- 版本检查指标至少包括成功/失败次数、延迟、缓存命中、限流、最近成功时间和各通道检测结果。
- 服务端升级必须保留可恢复旧二进制；Agent 延续原子替换和失败清理契约。
- GitHub 仓库写权限、GitHub TLS 和 Release 资产是当前信任根；同一 Release 中的 `.sha256` 只能检测传输损坏，不能抵抗仓库或 Release 与摘要同时被篡改。实施不得宣称具备发布者密码学签名；引入签名清单属于独立安全任务。
- 升级操作冻结的 Release/asset 快照最长使用 10 分钟；下载前按 asset ID、名称和大小重新取元数据，下载后以冻结 SHA256 校验。Release 被删除、资产身份变化或大小变化时安全失败，不重新解析到另一个 Release。

## 12. 测试与验收策略

### 12.1 单元与组件测试

1. 两个默认版本来源唯一、链接器注入互不影响。
2. Server/Agent CLI、Facts、ACK 和 API 分别读取正确版本源。
3. 标签筛选覆盖乱序、非法 SemVer、draft、prerelease、重复标签及跨组件标签。
4. 分页覆盖跨页最大版本、空页、循环/异常分页和达到安全上限的反例。
5. 两个缓存相互隔离；单通道失败不污染另一通道。
6. v1 接口保持 legacy 响应，新 v2 接口分别覆盖 available/stale/error/unknown、Server 派生 update_state 和 Agent 设备聚合。
7. Server 自升级拒绝 Agent Release/资产，Agent 升级拒绝 Server Release/资产。
8. 平台资产或 SHA256 缺失时不创建 Command/Plan。
9. 健康规则只使用 Agent 推荐版本，并覆盖陈旧与错误状态。
10. 发布工作流只构建自身组件；版本未提升、公开标签已存在、draft 摘要冲突或测试失败时安全停止；同提交同摘要 draft 可重试完成。
11. Server 升级 operation 覆盖正常重启、验证超时、自动回滚、回滚失败、服务进程重启和重复请求。
12. 强制刷新覆盖权限拒绝、每分钟限频、singleflight、两个组件并行和 GitHub rate-limit reset。

### 12.2 真实 GitHub 协议验证

实施前后必须用真实 GitHub 请求记录：

- Releases 列表完整分页、响应头、限流字段和 ETag 行为；
- `server-v*`、`agent-v*` 和历史 `v*` 的真实排序及过滤结果；
- Release 页面、二进制资产和 `.sha256` 的完整重定向/响应链；
- 资产不存在、标签不存在、限流和超时反例；
- fixture 来源、采集时间、脱敏方式及与真实 GitHub 的差异。

Mock 只能基于上述真实观察构造，不能根据实现反向生成。

2026-09-11 的实施期真实观察记录：

- 对 `GET https://api.github.com/repos/RokiLai/home-agent/releases?per_page=2&page=1` 的匿名只读请求返回 HTTP/2 200，`Link` 同时给出 `rel="next"` 与 `rel="last"`，并返回 `ETag`、`X-RateLimit-Limit/Remaining/Reset`；响应 Release 包含 `id/tag_name/target_commitish/draft/prerelease/assets`，资产包含 `id/name/size/digest/browser_download_url`。
- 对历史 `v0.6.13` 的 `homeagent-agent-darwin-amd64.sha256` 真实下载先由 `github.com` 返回 302，再由 `release-assets.githubusercontent.com` 返回 200；最终 `Content-Type` 为 `application/octet-stream`，正文为 64 位摘要、两个空格、精确资产名和单个 LF。
- 测试替身据此保留列表分页 `Link`、组件混排、draft/prerelease、资产身份和 sidecar 正反例；已知差异是替身不模拟 GitHub CDN 的带签名临时查询参数、Azure Blob 响应头和真实限流时钟。
- 关键反例已覆盖：跨组件更高版本不得遮蔽目标通道、10 页后仍有 next 必须失败、缺少任一必需 Agent 资产必须失败、纯摘要或文件名不匹配的 sidecar 必须失败、调用方自带版本/URL/SHA256 的 v2 批量请求必须拒绝。

### 12.3 发布与跨版本验收

发布后必须通过真实用户入口分别执行：

1. 上一正式 Server → 首个 `server-v*` 候选，验证检查、确认、下载、校验、替换、重启、版本收敛和失败回滚；
2. 上一正式 Agent → 首个 `agent-v*` 候选，至少覆盖 OpenWrt arm64、macOS arm64 及当前实际使用的平台；
3. 全新安装解析正确组件通道；
4. 就地升级不改变设备身份、Token、服务地址和 SSH 配置；
5. 旧软链接重装按仓库路径迁移规范完成；
6. Server 检测 Agent 新版但 Server 自身无需升级的路径；
7. Server 有新版但所有 Agent 已是最新的路径；
8. 两条通道同时发布、其中一条失败时不得聚合为整体成功。

所有代码变更仍须通过变更范围、架构依赖、模块测试、真实端口与协议的全量 `-race` 回归、`git diff --check` 和不低于 60% 的 Diff Coverage。界面变更必须用真实 API 数据验证“响应 → 解析 → 状态 → 渲染 → 交互回调”。

当前仅完成 bridge 候选实现与自动化验证；`v0.6.14` 发布门禁失败且未形成 Release，修复候选提升为 `v0.6.15`。不得跳过 §10.1 的迁移覆盖率门禁直接启用阶段 B 工作流。最后一个 legacy `v0.6.15` 尚未发布，上一正式版本真实升级、双通道 bootstrap、独立恢复监督器安装和发布后真实服务冒烟均未执行，因此验收阶段仍为“未执行”。
