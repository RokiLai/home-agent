## 三、目标、兼容性与依赖

目标：显式启用后，每次 macOS 更新在运行候选程序前使用同一证书和固定标识签名；任何签名失败均不替换旧程序、不重启；通过真实升级验证可移除宗卷权限是否保留。

固定标识采用 `online.rokilai.homeagent-server`，这是本方案新增签名契约，并非声称现有二进制已使用此标识。

不承诺自签证书等同 Developer ID、公证或能免除管理员提权；不修改 TCC 数据库、不重置隐私权限、不设置全局放行、不自动解锁钥匙串、不导出私钥。

不新增第三方依赖。仅使用 Go 标准库及 macOS 自带 `/usr/bin/security`、`/usr/bin/codesign`。其他平台无配置时保持原行为；其他平台显式设置签名配置则明确报不支持，避免被忽略。

## 四、配置与模块边界

新增环境变量 `HOMEAGENT_SERVER_CODESIGN_IDENTITY`：

| 值 | 行为 |
| --- | --- |
| 未设置或空白 | 保持既有升级行为，不调用签名工具 |
| 去除首尾空白后为 40 位十六进制指纹 | 启用签名，规范化为大写 |
| 其他非空值（包括证书显示名） | 拒绝升级，提示需要证书指纹 |

本机部署配置值为上述证书指纹，禁止把它硬编码为所有用户的默认值。使用指纹避免同名证书歧义。

配置在 PerformServerSelfUpgrade 的共同入口读取并冻结为本次操作的不可变快照；内部签名模块封装环境解析、命令执行和结果验证，不更改 Options、Result、函数签名、API 请求字段或现有公开状态枚举。保留现有同版本无操作逻辑，只有实际更新才验证签名环境。check-only 不需要证书或签名工具。

这使三个调用入口自动共享策略，主程序与 API 产品代码预计无须修改。新增环境变量属于需确认的运维契约。后台 launchd 和独立终端 CLI 必须分别配置；环境变量不因钥匙串创建证书而自动生效。运维手动下载覆盖程序不在此保证范围内。

## 五、执行顺序及安全约束

1. 保留原有版本决策；需要更新时解析本次签名配置，检查上下文未取消。
2. 启用签名时预检有效签名身份，必须精确匹配指纹；不得选择第一个身份，不得退回 adhoc。预检工具输出只解析身份字段，禁止日志打印完整钥匙串内容。
3. 保留现有 GitHub 下载和原始 SHA256 校验。SHA 不匹配时不执行候选文件或签名。校验通过后签名会改变文件，禁止再拿原始摘要比较签名后的文件。
4. 保留 chmod 0755。签名前用 codesign 读取当前已安装程序的身份与指定要求；已使用本方案标识和目标证书时捕获原指定要求，用于候选的身份连续性验证。当前 adhoc 允许首次迁移；已经是其他证书身份的程序拒绝静默迁移，需另行确认迁移方案。
5. 通过 exec.CommandContext 参数数组调用 `/usr/bin/codesign --force --sign <指纹> --identifier online.rokilai.homeagent-server --timestamp=none <临时文件>`。不使用 shell，不使用 --deep，不使用 -s -。保持私钥不可导出。
6. codesign 严格验证候选，确认签名不是 adhoc、标识正确、叶证书指纹匹配；提取公开证书可使用 codesign 的公开证书导出能力，文件必须写入受控临时目录并清理，不得导出私钥。使用当前签名工具的真实输出建立解析测试，禁止猜测字段。已有固定身份时，还须将旧指定要求作为 requirement 验证候选；不匹配即拒绝。
7. 执行已有候选 version 冒烟自检，之后重检候选签名和上下文。每次异步命令或 I/O 返回后检查 ctx，替换前再次确认当前程序身份和内容未被其他更新改变；发现变化则拒绝覆盖。可使用起始内容摘要进行比较，但不要声称它解决了所有跨进程原子竞态。
8. 所有签名、身份连续性和冒烟检查通过后才备份原程序并原子替换；.bak 必须保留原签名字节。随后沿用既有重启回调与状态收敛。

每个外部签名/身份检查命令设置最长 15 秒超时，并服从父上下文。后台私钥访问若需要弹窗或钥匙串被锁定，必须有限时间失败，不得无限等待、自动放宽私钥 ACL 或转为临时签名。真实无交互能力另设验收。

本任务不新增异步任务或持久化文件，沿用 operation_id 隔离 Web 操作。保留既有 Web 排他；不得顺带宣称解决旧 API 与 CLI 并发。实现前复核现有跨入口并发能力，若实现上述替换前保护仍不足以保证本任务签名/备份安全，报告证据、补充设计及 allowed_paths 并重新确认，不能擅自扩大范围。

## 六、状态和失败矩阵

| 场景 | Web 持久化状态 | CLI / 旧 API | 文件及进程约束 |
| --- | --- | --- | --- |
| 签名未启用 | 沿用现有状态 | 沿用现有行为 | 不调用签名命令 |
| 同版本且未 force | 沿用现有状态 | 不更新 | 不要求私钥可用 |
| 配置非法、非 macOS 启用、证书不存在或不受信任 | replacing → failed，upgrade_failed | 返回明确错误 | 不替换、不重启 |
| 下载或原 SHA256 失败 | replacing → failed，upgrade_failed | 返回错误 | 不运行、不签名候选，清理下载文件 |
| 签名失败、超时、取消、签名验证或旧 requirement 不匹配 | replacing → failed，upgrade_failed | 返回带阶段前缀的错误 | 原程序和既有 .bak 不变，清理全部临时文件，不调用重启 |
| 冒烟失败、候选被篡改、替换前检测到旧程序变化 | replacing → failed，upgrade_failed | 返回错误 | 不继续备份或覆盖，不重启 |
| 全部预检通过并替换 | replacing → restarting | 沿用成功结果 | 备份原签名二进制，按原流程重启 |
| 新进程启动后的成功、失败或回滚 | 沿用现有收敛枚举 | 沿用现有恢复机制 | 不新增自动清理备份或健康超时承诺 |

模块返回普通带阶段上下文的 error，由现有 OperationManager 映射；不直接把 codesign 退出码透传为业务状态，不新增 API 错误码或改变响应格式。

## 七、首次迁移与部署

首次迁移必须先交付包含本功能的 Server 版本；旧版本不会因为新增环境变量自动给下一版签名。部署前单独确认目标、版本、停机窗口、备份、回退与生产验证计划。

经部署授权后：备份当前二进制及必要配置；在 staging 路径对新版本完成签名和验证；配置 launchd 的签名指纹环境变量（以及终端 CLI 的对应环境）；受控替换并重启；首次访问真实可移除宗卷由用户允许。不得在线修改正在执行的 Mach-O 签名。

私钥访问授权若由 macOS 弹窗要求，用户手动处理；不得将“允许 codesign 使用私钥”和“允许 Server 读取可移除宗卷”混为同一权限。签名证书有效不证明后台私钥访问已验证。

回退恢复备份二进制与环境配置，再由原服务管理器启动。首次迁移回到 adhoc 版本可能再次触发权限弹窗，应事先说明。证书续期或更换需重新验证指定要求与 TCC 授权，不承诺自动延续。

## 八、测试与验收证据

先根据本方案写测试并记录失败，再实现。不可删除、跳过或弱化已有测试。平台单元测试可分层，但真实 macOS 门禁不能用脚本替身替代。

| 编号 | 验收与显式断言 | 证据 |
| --- | --- | --- |
| T01 | 空配置无签名命令；指纹规范化；非法值拒绝；非 macOS 配置拒绝；check-only 与同版本无操作兼容 | 单元测试输出 |
| T02 | SHA256 → 签名 → 严格验证/身份验证 → 冒烟 → 再验证 → 备份/替换 → 回调的顺序；SHA 失败签名调用为零 | 事件序列与调用次数断言 |
| T03 | 缺证书、不信任、命令失败、超时、取消、错误指纹/标识、adhoc、requirement 不匹配、文件变化均拒绝 | 原文件与既有 .bak 字节不变、回调零次、临时文件零残留断言 |
| T04 | 签名成功后使用签后候选、备份保留旧签名；两次真实不同版本签名身份连续 | 真实 Mach-O codesign 输出和 requirement 匹配 |
| T05 | Web v2、CLI 和仍可达旧 API 均进入共同签名策略；Web 签名错误落盘 failed/upgrade_failed，重载后可查询，排他保持 | 入口集成测试、真实 HTTP 端口及状态断言 |
| T06 | launchd 运行环境使用私钥无交互完成；钥匙串锁定/拒绝访问时有限时间失败且旧服务保留 | 独立测试环境日志；操作钥匙串状态须单独确认，禁止改日常会话来凑测试 |
| T07 | 首次授权后从真实 GitHub 下载并升级，再由实际 launchd Server 访问同一可移除宗卷资源，业务结果正确且没有再次请求授权 | 版本、路径、前后 requirement、真实业务结果及用户观察；必要时使用脱敏 TCC 日志辅助 |
| T08 | 升级新程序启动失败时真实恢复原签名二进制；不夸大现有监督器能力 | 隔离环境恢复日志、签名和服务健康结果 |

T07 是核心目标的阻断验收。若固定证书仍无法保留权限，收集实际 TCC attribution / responsible process、签名和路径证据，修订方案并重新确认；不得静默改成完全磁盘访问或宣称已解决。签名工具通过、DOM 测试或用户受理请求均不能代替权限保留证据。

编码门禁：变更范围及架构依赖检查、新模块测试、真实端口协议的全量 `go test -count=1 -race ./...`、`./scripts/check-diff-coverage.sh HEAD 60`，并运行仓库适用质量门禁。scripts/check-change-scope.sh 与 check-architecture-deps.sh 当前都会调用完整质量门禁，执行前阅读其入口，不能误称只是静态检查。证据记录真实命令、退出码、平台和失败原因，不提交认证信息。

全部文件 UTF-8 无 BOM，git diff --check 零告警；git diff --stat 加未跟踪文件检查覆盖全部修改。纯文档阶段免测试；进入编码后不得沿用此豁免。代码门禁通过后本地 dev 提交，禁止提交 main；部署及生产验证未完成不得宣称完整交付。

## 九、允许文件与组件版本

对应 `changes/macos-server-code-signing.yaml`，只允许该清单列出的文件。新增能力位于独立 signing 文件中，属于既有升级业务模块，不跨模块依赖 internal 或 infrastructure。无需修改 API 产品代码、主程序产品代码、前端、Supervisor、GitHub 工作流或 AGENTS.md；入口测试可修改已有测试文件。

## 十、审查记录与待确认事项

本轮设计自查发现并已纳入：旧 API 仍可达；现有 replacing 早于下载；Supervisor 无完整超时健康保障；CLI 不继承 launchd 配置；首次部署不能依赖旧版自动签名；证书续期和 TCC 归属不能凭经验保证。

正式设计审查仍需验证：codesign 真实工具输出与 requirement 验证方式、后台私钥访问条件、替换前并发保护是否足够、真实可移除宗卷和隔离 launchd 测试资源是否可用。可先进行只读核查；需要创建测试制品或调用私钥的实验必须在获得确认后执行。关键假设未验证时，不得开始产品实现。

待用户确认：本方案公开配置、固定标识、允许路径及测试策略。设计、实施、验收状态分别更新，不预先勾选通过。
