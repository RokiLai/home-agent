# 服务端 IPv6 自更新与 DDNS 自举方案

## 1. 状态与范围

- 设计状态：已完成设计审查并获确认。
- 实施状态：已实施；完成 `internal/servernetwork` 独立业务模块及服务端装配。
- 验收状态：单元测试、状态机与并发验证通过，全量 `-race` 回归通过。
- 当前变更清单：`changes/server-ipv6-self-update.yaml`。

本方案补充《IPv6与DDNS同步集成方案》，为服务端自身入口建立独立的地址采集和 DNS 恢复路径。普通设备继续遵循原有地址上报与路由器前缀交集规则。本文不修改既有公开接口，也不表示实现范围已经获批。

## 2. 问题与证据边界

本次只读检查观察到：本机物理接口的公网 IPv6 与公网 AAAA 记录不同；本机 HomeAgent IPv6 查询接口返回 HTTP 200，但返回地址与 DNS 中的旧地址一致。ddns-go 配置使用命令读取该接口，容器正在运行。

上述证据证明 HomeAgent 提供给 DDNS 的地址未与本机同步。尚未检查完整的 Agent 连接配置、请求失败日志和服务端状态演进，因此不能把“Agent 因服务端域名失效而无法上报”宣称为本次故障的已确认根因。

需要消除的架构风险是：客户端通过服务端公网域名上报，而该域名的新地址又依赖客户端上报。IPv6 前缀变化可能使恢复路径依赖已经失效的入口。

## 3. 目标与非目标

目标：

1. 服务端自行发现宿主机稳定公网 IPv6，并更新显式配置的服务端域名。
2. 所有客户端继续统一通过公网域名上报，不增加 localhost 特例，不检测客户端与服务端是否同机。
3. 服务端域名失效、客户端离线、路由器前缀上报过期时，自更新流程仍可独立执行。
4. DNS 更新有可恢复状态、独占管理、超时、重试和真实查询验证。

非目标：自动接管全部设备域名、自动识别同机 Agent、修改普通设备地址选择规则、自动配置路由器或防火墙、保证运营商公网入站可达、增加客户端版本或改变客户端协议。

## 4. 现有契约与扩展点

以下路径及符号已通过本地源码检查确认：

| 位置 | 现有能力及设计约束 |
|---|---|
| `cmd/homeagent-agent/ipv6_darwin.go` | `stableIPv6Addresses` 在 Agent 的 `main` 包内，不能由 Server 直接导入；可参考采集流程 |
| `internal/networkaddr` | 提供 `ParseDarwinIfconfig`、`NormalizeAndFilterCandidates`，优先复用其公开函数 |
| `internal/ddns/publisher.go` | `DNSPublisher` 提供 `GetAAAA`、`UpsertAAAA`、`DeleteAAAA`，保持签名不变 |
| `internal/ddns/service.go` | `ReconcileDevice` 依赖路由器前缀并对过期前缀停止更新，不能直接承担本机自举 |
| `cmd/homeagent-server/main.go` | 装配 Cloudflare Publisher 和设备 DDNS 服务，是新模块的装配入口 |
| `internal/api/api.go` | `getDeviceIPv6Text` 优先返回 `DesiredAddress`，其次返回首个已上报地址；不是实时本机采集接口 |
| `scripts/get-device-ipv6.sh` | 从 Server 拉取地址供外部 DDNS 使用，不负责采集或上报 |

拟新增独立业务模块 `internal/servernetwork`，仅为拟议目录，当前不创建。模块定义自身所需的采集、发布和状态存储接口，由 Server 装配已有 Publisher，避免直接依赖其他模块的私有实现或 Cloudflare 适配器。新增依赖原则上使用标准库与既有模块；如需外部依赖，必须在实施前说明必要性。

## 5. 职责与配置契约

处理链路：宿主机物理接口 → 服务端本机采集器 → 自更新协调器 → DNS Publisher → 服务商记录查询 → 公共 DNS 与入口恢复验证。

服务端记录以规范化的服务商、区域及完整域名作为唯一业务标识，不绑定 Agent `device_id`，不向设备上报状态中写入伪造快照或 revision。

拟议配置语义如下；具体字段名、配置载体和校验入口须在实施设计审查中确定，不是现有配置项：

| 配置 | 契约 |
|---|---|
| 启用开关 | 默认关闭，显式启用 |
| 物理接口 | 必填，例如宿主机实际联网接口；不自动选取虚拟网卡 |
| 受管记录列表 | 必填，逐条列举服务端入口及确需同地址的别名，不按后缀自动接管 |
| 服务商与凭据引用 | 复用服务端现有凭据管理，不记录明文凭据，不依赖自身公网入口读取 |
| 检测与重试参数 | 建议轮询 30 秒、事件防抖 3 秒、单次请求超时 10 秒、退避上限 60 秒并带抖动 |
| 状态目录 | 使用服务端持久数据目录，按记录保存配置版本、地址版本和同步结果 |

首期拟支持 macOS 原生 Server。容器内不能默认把自身接口当作宿主机接口；无法证明宿主机采集能力的部署应拒绝启用并给出具体错误。Linux、Windows 和容器宿主机采集属于后续明确设计范围。

## 6. 地址选择与独立恢复

启动立即采集；网络事件触发防抖采集；周期轮询兜底。不得通过自身公网 API 获取地址，也不等待 Agent 或路由器通过该入口上报。

只接受显式接口上处于 up 状态的全局单播 IPv6，排除 ULA、链路本地、回环、临时、deprecated、tentative、duplicated 和已失去 preferred 生命周期的地址。命令失败、超时或解析失败与“成功采集但没有候选”分开处理。

候选规范化、去重后，若已发布地址仍有效则保持，否则按 IPv6 数值升序选择。双前缀过渡依靠宿主机实时地址标志收敛，不依赖路由器前缀交集。该策略仅用于显式声明的服务端入口，不能推广到普通设备。

本地有效地址不等于公网可达。宿主机长期保留过时 preferred 地址、运营商阻断入站等情形不能仅凭采集排除，必须通过真实外网入口验收揭示；不把外网探测失败解释成地址无效并反复切换或删除记录。

采集失败或没有有效地址时保留最后发布记录并告警，首期不自动删除 AAAA。服务商 API 的出站解析和连接必须独立于服务端入口；若整机断网或服务商不可达，则记录失败并重试，不能承诺离线恢复 DNS。

## 7. 独占管理与迁移

同一受管记录只能有一个发布者。新模块与现有设备 DDNS 配置重叠时拒绝启用该自更新配置，不静默覆盖。Agent 仍可上报本机事实，但这些事实不驱动自更新记录。

ddns-go 是外部进程，服务端不能仅靠本地配置检测证明它已停止写入。上线前必须逐条核对受管记录，从 ddns-go 和其他发布者中移出这些记录，并保留其他设备的管理配置。此操作属于未来部署变更，本次不执行。

迁移顺序：备份相关配置和当前记录 → 核实新配置及出站服务商访问 → 停止旧发布者对目标记录写入 → 启用自更新 → 验证真实记录和入口。迁移期间保留现有 DNS 记录。回滚先停止新发布者，再恢复旧记录管理，禁止双写；旧链路的公网依赖问题在回滚后仍可能存在。

## 8. 状态、并发与持久化

以下是新模块的拟议领域状态，不直接映射成既有设备健康枚举，也不冒充当前 API 字段：

| 当前条件或事件 | 目标状态 | 动作与失败边界 |
|---|---|---|
| 未启用 | `disabled` | 不采集、不写 DNS |
| 配置非法或记录所有权冲突 | `blocked` | 禁止该配置发布，输出具体原因 |
| 采集失败或无候选 | `waiting_address` | 区分原因，保留已发布值，等待下次采集 |
| 新候选或重启待核验 | `pending` | 先持久化期望值和版本，再准备发布 |
| 开始服务商请求 | `syncing` | 按记录串行，同一时刻只有一个写请求 |
| 写入成功，尚未查证 | `verifying` | 查询服务商记录，必要时重试读取 |
| 服务商查询与当前期望一致 | `synced` | 持久化已应用值；仅代表服务商记录收敛 |
| 超时、拒绝、查询不符或存储失败 | `failed` | 保留证据与最后已确认值，有界退避重试 |
| 周期查询发现外部改写 | `pending` | 告警并重新协调，不能长期相信本地缓存 |

每条记录保存配置版本、期望地址及版本、已确认地址及版本、状态、最近成功时间、错误类别和下次重试时间，原子落盘。首次持久化失败不得发起 DNS 写入；写入后落盘失败不能标记成功，重启后通过服务商查询恢复事实。

网络事件和轮询合并处理，不为每个事件创建无限任务。异步请求返回后重新检查配置版本、启用状态和期望版本；旧请求成功不能将新版本标记为已同步。DNS 已被旧请求写入时，立即按最新状态再次协调。

多条记录独立保存和汇总结果，部分成功不能展示为全部成功。停止流程取消在途任务并等待退出；记录移交需等待旧发布者退出，不能仅依赖取消信号阻止已经到达服务商的写入。多实例部署首期不支持共享记录，必须有部署级单实例约束。

`synced` 不等于公共缓存刷新或 HTTPS 可达。日志应分别记录采集、发布、服务商查证、公共解析和入口恢复证据；当前不新增控制台页面或公开状态接口，后续如需展示须另行定义完整映射契约。

## 9. 测试与真实验收计划

所有下列项目均未执行。实施需先形成独立变更清单和测试，再编写逻辑；本次文档变更不运行代码测试。

1. 地址采集：稳定地址、临时地址、失效标志、ULA、虚拟接口、多地址排序、无地址、命令失败和解析错误；使用真实宿主机输出制作注明来源及差异的 fixture。
2. 状态机：启动、事件防抖、轮询、双前缀 A→A+B→B、失败重试、空候选保留记录、服务商外部改写和部分成功。
3. 并发与持久化：A 请求在途时出现 B、配置禁用或变更、写成功但落盘失败、进程重启和重复事件；证明旧结果不覆盖新状态。
4. 所有权：内部记录重叠拒绝，外部 ddns-go 迁移后无双写，回滚不产生并发发布。
5. 外部协议：实施前通过真实请求确认 DNS 服务商查询、更新、认证失败、限流和超时行为，记录完整响应及重定向链；mock 不得根据实现反向构造。反例至少覆盖服务商写入响应成功但后续查询不一致，以及普通 DNS 被本地代理映射。
6. 核心恢复：在授权测试环境中让入口 AAAA 指向旧地址，确认客户端经公网域名上报失败；保持 Server 运行且服务商出站可用，触发真实宿主机地址变化，验证 Server 独立发布新地址、公共解析刷新、真实客户端经同一公网域名恢复上报。
7. 前缀依赖反例：路由器前缀上报过期且客户端全部离线时，仍完成第 6 项，证明不存在隐藏循环依赖。
8. 公网入口：从独立外部网络检查 AAAA、TLS、实际 API 请求和客户端状态更新，不以局域网回环访问替代。若启用 CDN 代理，应以服务商记录核实源站值，不能要求公共 AAAA 等于宿主机地址；代理模式须在实施前确认。

建议采集检测目标为 30 秒内，事件监听正常时为防抖后触发。整体恢复时间记录采集、写入、服务商查证、DNS 缓存及客户端重连的分段耗时，不预先承诺固定公网恢复时限；量化门槛须基于实际 TTL、负缓存和客户端退避配置在实施前定稿。

实施交付必须完成变更范围、架构依赖、新模块测试、全量真实端口 `-race` 回归和 Diff Coverage 不低于 60%。如涉及安装或升级，追加上一正式版本到候选版本的真实用户入口验收及发布后真实服务冒烟，不能用模拟升级替代。

外部假设审计需逐项保存：服务商及关键假设、真实请求结果、完整响应与重定向链、测试替身来源及差异、关键反例、适用的上一正式版本升级结果。证据不得包含凭据。
