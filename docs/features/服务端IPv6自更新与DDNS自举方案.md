本方案补充《IPv6与DDNS同步集成方案》，为服务端自身入口建立独立的地址采集和 DNS 恢复路径。普通设备继续遵循原有地址上报与路由器前缀交集规则。第 1–10 节记录基础契约；第 11 节自动探测与域名候选优化已完成代码实施和本地验收，生产 DNS 与入口恢复验收仍须按本文门禁执行。

## 2. 问题与证据边界

本次只读检查观察到：本机物理接口的公网 IPv6 与公网 AAAA 记录不同；本机 HomeAgent IPv6 查询接口返回 HTTP 200，但返回地址与 DNS 中的旧地址一致。ddns-go 配置使用命令读取该接口，容器正在运行。

上述证据证明 HomeAgent 提供给 DDNS 的地址未与本机同步。尚未检查完整的 Agent 连接配置、请求失败日志和服务端状态演进，因此不能把“Agent 因服务端域名失效而无法上报”宣称为本次故障的已确认根因。

需要消除的架构风险是：客户端通过服务端公网域名上报，而该域名的新地址又依赖客户端上报。IPv6 前缀变化可能使恢复路径依赖已经失效的入口。

## 3. 目标与非目标

目标：

1. 服务端自行发现宿主机稳定公网 IPv6，并更新显式配置的服务端域名。
2. 所有客户端继续统一通过公网域名上报，不增加 localhost 特例，不检测客户端与服务端是否同机。
3. 服务端域名失效、客户端离线、路由器前缀上报过期时，自更新流程仍可独立执行。
4. DNS 更新有可恢复状态、独占管理、超时、重试和真实查询验证。

非目标：自动接管全部设备域名、自动识别同机 Agent、修改普通设备地址选择规则、自动配置路由器或防火墙、保证运营商公网入站可达、增加客户端版本或改变客户端协议。

## 4. 现有契约与扩展点

以下路径及符号已通过本地源码检查确认：

| 位置 | 现有能力及设计约束 |
|---|---|
| `cmd/homeagent-agent/ipv6_darwin.go` | `stableIPv6Addresses` 在 Agent 的 `main` 包内，不能由 Server 直接导入；可参考采集流程 |
| `internal/networkaddr` | 提供 `ParseDarwinIfconfig`、`NormalizeAndFilterCandidates`，优先复用其公开函数 |
| `internal/ddns/publisher.go` | `DNSPublisher` 提供 `GetAAAA`、`UpsertAAAA`、`DeleteAAAA`，保持签名不变 |
| `internal/ddns/service.go` | `ReconcileDevice` 依赖路由器前缀并对过期前缀停止更新，不能直接承担本机自举 |
| `cmd/homeagent-server/main.go` | 装配 Cloudflare Publisher 和设备 DDNS 服务，是新模块的装配入口 |
| `internal/api/api.go` | `getDeviceIPv6Text` 优先返回 `DesiredAddress`，其次返回首个已上报地址；不是实时本机采集接口 |
| `scripts/get-device-ipv6.sh` | 从 Server 拉取地址供外部 DDNS 使用，不负责采集或上报 |

已实施独立业务模块 `internal/servernetwork`。模块定义自身所需的采集、发布和状态存储接口，由 Server 装配已有 Publisher，避免直接依赖其他模块的私有实现或 Cloudflare 适配器。自动探测优化原则上使用标准库与既有模块；如需新增外部依赖，必须在实施前说明必要性。

## 5. 职责与配置契约

处理链路：宿主机物理接口 → 服务端本机采集器 → 自更新协调器 → DNS Publisher → 服务商记录查询 → 公共 DNS 与入口恢复验证。

服务端记录以规范化的服务商、区域及完整域名作为唯一业务标识，不绑定 Agent `device_id`，不向设备上报状态中写入伪造快照或 revision。

当前及优化后的配置语义如下；自动探测新字段及迁移详见第 11.3 节：

| 配置 | 契约 |
|---|---|
| 启用开关 | 默认关闭，显式启用 |
| 物理接口 | 必填，例如宿主机实际联网接口；当前实现不自动选取虚拟网卡 |
| 受管记录列表 | 必填，逐条列举服务端入口及确需同地址的别名，不按后缀自动接管 |
| 服务商与凭据引用 | 复用服务端现有凭据管理，不记录明文凭据，不依赖自身公网入口读取 |
| 检测与重试参数 | 建议轮询 30 秒、事件防抖 3 秒、单次请求超时 10 秒、退避上限 60 秒并带抖动 |
| 状态目录 | 使用服务端持久数据目录，按记录保存配置版本、地址版本和同步结果 |

首期拟支持 macOS 原生 Server。容器内不能默认把自身接口当作宿主机接口；无法证明宿主机采集能力的部署应拒绝启用并给出具体错误。Linux、Windows 和容器宿主机采集属于后续明确设计范围。

## 6. 地址选择与独立恢复

启动立即采集；网络事件触发防抖采集；周期轮询兜底。不得通过自身公网 API 获取地址，也不等待 Agent 或路由器通过该入口上报。

当前只接受显式接口上处于 up 状态的全局单播 IPv6，排除 ULA、链路本地、回环、临时、deprecated、tentative、duplicated 和已失去 preferred 生命周期的地址。命令失败、超时或解析失败与“成功采集但没有候选”分开处理。自动模式的接口间选择见第 11 节，尚未实施。

候选规范化、去重后，若已发布地址仍有效则保持，否则按 IPv6 数值升序选择。双前缀过渡依靠宿主机实时地址标志收敛，不依赖路由器前缀交集。该策略仅用于显式声明的服务端入口，不能推广到普通设备。

本地有效地址不等于公网可达。宿主机长期保留过时 preferred 地址、运营商阻断入站等情形不能仅凭采集排除，必须通过真实外网入口验收揭示；不把外网探测失败解释成地址无效并反复切换或删除记录。

采集失败或没有有效地址时保留最后发布记录并告警，首期不自动删除 AAAA。服务商 API 的出站解析和连接必须独立于服务端入口；若整机断网或服务商不可达，则记录失败并重试，不能承诺离线恢复 DNS。

## 7. 独占管理与迁移

同一受管记录只能有一个发布者。新模块与现有设备 DDNS 配置重叠时拒绝启用该自更新配置，不静默覆盖。Agent 仍可上报本机事实，但这些事实不驱动自更新记录。

ddns-go 是外部进程，服务端不能仅靠本地配置检测证明它已停止写入。上线前必须逐条核对受管记录，从 ddns-go 和其他发布者中移出这些记录，并保留其他设备的管理配置。此操作属于未来部署变更，本次不执行。

迁移顺序：备份相关配置和当前记录 → 核实新配置及出站服务商访问 → 停止旧发布者对目标记录写入 → 启用自更新 → 验证真实记录和入口。迁移期间保留现有 DNS 记录。回滚先停止新发布者，再恢复旧记录管理，禁止双写；旧链路的公网依赖问题在回滚后仍可能存在。

## 8. 状态、并发与持久化

以下是已实施的基础自举领域状态，不直接映射成设备健康枚举：

| 当前条件或事件 | 目标状态 | 动作与失败边界 |
|---|---|---|
| 未启用 | `disabled` | 不采集、不写 DNS |
| 配置非法或记录所有权冲突 | `blocked` | 禁止该配置发布，输出具体原因 |
| 采集失败或无候选 | `waiting_address` | 区分原因，保留已发布值，等待下次采集 |
| 新候选或重启待核验 | `pending` | 先持久化期望值和版本，再准备发布 |
| 开始服务商请求 | `syncing` | 按记录串行，同一时刻只有一个写请求 |
| 写入成功，尚未查证 | `verifying` | 查询服务商记录，必要时重试读取 |
| 服务商查询与当前期望一致 | `synced` | 持久化已应用值；仅代表服务商记录收敛 |
| 超时、拒绝、查询不符或存储失败 | `failed` | 保留证据与最后已确认值，有界退避重试 |
| 周期查询发现外部改写 | `pending` | 告警并重新协调，不能长期相信本地缓存 |

每条记录保存配置版本、期望地址及版本、已确认地址及版本、状态、最近成功时间、错误类别和下次重试时间，原子落盘。首次持久化失败不得发起 DNS 写入；写入后落盘失败不能标记成功，重启后通过服务商查询恢复事实。

网络事件和轮询合并处理，不为每个事件创建无限任务。异步请求返回后重新检查配置版本、启用状态和期望版本；旧请求成功不能将新版本标记为已同步。DNS 已被旧请求写入时，立即按最新状态再次协调。

多条记录独立保存和汇总结果，部分成功不能展示为全部成功。停止流程取消在途任务并等待退出；记录移交需等待旧发布者退出，不能仅依赖取消信号阻止已经到达服务商的写入。多实例部署首期不支持共享记录，必须有部署级单实例约束。

`synced` 不等于公共缓存刷新或 HTTPS 可达。日志应分别记录采集、发布、服务商查证、公共解析和入口恢复证据。现有控制台和 `GET/PUT /api/v1/server/network` 已展示聚合状态；自动探测的新状态必须按第 11.4 与 11.8 节分层，不得与 DNS 记录状态混合。

## 11. 自动探测与受管域名候选优化

### 11.1 现状证据与设计决策

当前前端 `serverNetworkInterfaceInput` 与 `serverNetworkRecordsInput` 都是手工输入，且前端与 `PUT /api/v1/server/network` 在启用时均拒绝空接口和空记录。`networkaddr.GenericProvider.GetAddresses` 已经支持在接口为空或 `auto` 时扫描全部 up 且非 loopback 的接口，Darwin Provider 也支持同样语义；现有限制主要来自配置契约、API 校验和前端交互，而不是缺少基础扫描能力。

本次决定由服务端自动解析当前实际承载默认 IPv6 出站流量的接口，并在第一阶段原样复用 macOS 客户端现有 IPv6 过滤与排序契约，从该接口自动选出稳定公网 IPv6。网卡和地址都不是用户配置项；即使宿主机存在多个接口或多个 IPv6，页面也只展示自动解析结果与诊断信息，不要求用户选择。无法可靠确定时安全失败并保留既有 AAAA，不以人工选择代替解析。DNS 记录代表外部写入权限和管理责任，域名仍必须经用户明确确认后才能进入保存与发布链路。

### 11.2 功能边界

本轮优化包含：

1. 扫描宿主机活动接口及其稳定公网 IPv6；
2. 根据当前 IPv6 默认路由确定有效物理接口；
3. 复用客户端规则自动过滤、排序并确定唯一有效地址；
4. 从已保存记录和服务端公网 URL 生成域名候选；
5. 保存前进行无 DNS 写入的配置预检；
6. 在界面分开展示探测、预检、发布和查证状态。

第一阶段支持范围仅为运行于 macOS 宿主机网络命名空间的原生 Server。Linux、Windows、容器和 VPN 默认路由场景需要分别验证真实路由与地址协议后另行扩展。本轮不包含：扫描并默认接管 Cloudflare Zone 全部记录、自动配置路由器或防火墙、允许用户强制指定网卡或地址、追溯虚拟默认路由的底层物理接口、在容器内猜测宿主机接口，以及未经用户确认的 DNS 写入。

### 11.3 配置与兼容契约

持久化配置拟扩展为：

```json
{
  "enabled": true,
  "records": ["homeagent.example.com"]
}
```

| 字段 | 契约 |
|---|---|
| `records` | 用户确认的完整域名列表，规范化、去重并按稳定顺序保存 |

解析出的 `interface/address` 属于运行状态而非期望配置，写入状态存储并携带探测时间、默认路由标识和配置版本，用于重启恢复、诊断及防止旧异步结果覆盖；它们不得作为用户可编辑配置持久化。

兼容规则：

- 旧配置中的非空 `interface` 仅作为迁移期诊断信息，不再约束选址；实际结果始终由当前默认 IPv6 路由和地址过滤规则产生；
- 已启用旧配置升级后先执行两次间隔 3 秒且结果一致的自动解析；结果与旧接口不同时也不要求用户选择，而是在第二次确认后按新地址调和；确认前保留既有 AAAA；
- 历史或损坏配置出现 `enabled=true` 但 `interface` 为空时仍可自动探测，不再因缺少人工接口配置而阻塞；
- 旧字段在读取时兼容，在下一次成功保存时从期望配置中移除；旧客户端提交的 `interface` 与当前解析结果一致时兼容接受，不一致时返回 `interface_is_read_only`，不得用它覆盖解析结果；
- 配置或运行状态持久化失败时安全失败，保留旧文件、旧内存状态和既有 AAAA，不发起新 DNS 写入。

配置版本契约固定为：缺少版本的旧配置在内存中解释为版本 1；启动探测和运行状态更新不改变配置版本；只有期望配置成功原子落盘才递增一次。首次以新结构保存并移除旧 `interface` 也属于一次配置写入，从 1 递增至 2。落盘失败时磁盘、内存期望配置及版本均保持旧值，临时探测结果不得冒充新配置版本；令牌和在途任务始终绑定写入前版本。

### 11.4 接口与地址自动解析规则

在现有 `GET /api/v1/server/network` 与 `PUT /api/v1/server/network` 之外，拟新增两个只读预检端点：

```text
GET  /api/v1/server/network/candidates
POST /api/v1/server/network/validate
```

`GET .../candidates` 只扫描本机，不读写 DNS。成功返回 HTTP 200 及 `detection_id/detected_at/expires_at/status/resolved_interface/resolved_address/candidates/errors`；探测失败仍返回 HTTP 200 及 `status=no_default_route/unsupported_route_interface/no_address/error` 和结构化错误，身份或权限失败分别使用 401/403。`detection_id` 是不透明随机标识，绑定当次规范化默认路由标识、候选集和当前配置版本，60 秒后过期，不包含接口命令原始输出或凭据。

候选仅用于诊断，以接口为聚合单位，每项结构固定为 `interface/is_default_route/addresses/excluded_summary/reasons`，不提供可选择标记。第一阶段只复用 macOS 客户端真实链路：接口必须 up、非 loopback 且未命中现有 `isVirtualInterface`；通过 `ifconfig` 解析地址标志，再交给 `networkaddr.NormalizeAndFilterCandidates` 排除 temporary、deprecated、生命周期已过期、无效地址、IPv4 映射、loopback、link-local、multicast、unspecified 与 ULA，最后规范化、去重并按 IPv6 数值排序。Linux 的 global/tentative/dadfailed 和 Windows 的 Preferred/random-suffix 属于各自客户端 Provider 契约，不得在 macOS 第一阶段伪称已复用或已验证。

自动解析顺序为：

1. 在 macOS 执行等价于 `/sbin/route -n get -inet6 default` 的无 DNS 查询，以内核返回的单个 `interface` 作为实际选路结果；规范化路由标识固定为 `interface + gateway`。命令无结果、字段缺失或超时为 `no_default_route/error`，不再自行枚举并比较路由 metric；
2. 验证该接口 up、非 loopback 且未命中客户端 `isVirtualInterface` 语义；若实际默认路由是 VPN、隧道、桥接或容器虚拟接口，返回 `unsupported_route_interface` 并保留既有 AAAA，不猜测其底层物理接口；
3. 只采集该接口地址，并完全复用上述客户端过滤、规范化、去重和 IPv6 数值升序规则；实施时应把共用逻辑下沉至 `internal/networkaddr`，服务端不得复制一套不同规则；
4. 若上次已发布地址仍在当前合格集中则继续使用，避免无意义 DNS 抖动；否则自动取数值升序第一项，与现有 Collector 契约一致；
5. 默认路由接口或选中地址发生变化时，第一次完整采集结果只保存在内存待确认状态；从该次采集完成时起等待 3 秒后启动第二次完整采集，两次规范化路由标识与选中地址必须一致，并在异步 I/O 返回后重新校验路由、地址和配置版本，才允许发布新 AAAA；进程重启会丢弃待确认状态并重新开始；
6. 默认路由缺失、默认路由是虚拟接口、接口不可见或没有合格地址时停止写入并保留既有 AAAA，只暴露结构化诊断，不退回人工选择。

接口探测状态为 `detecting/ready/no_default_route/unsupported_route_interface/no_address/error`。它与现有 DNS 记录的 `disabled/blocked/waiting_address/pending/syncing/verifying/synced/failed` 严格分层，不直接传透或混合。

### 11.5 域名候选与所有权

第一阶段的候选来源仅限：

1. 已保存的 `records`；
2. 已配置服务端公网 URL 中经 URL 解析确认的 DNS 主机名。

IP 字面量、`localhost`、无点单标签、非法 IDNA 与空值不能成为候选。候选只用于展示，默认不勾选新发现的域名；用户必须逐条确认。Cloudflare Zone 记录枚举留给第二阶段，实施前需要单独验证分页、权限、限流、代理模式及响应脱敏契约。

`GET .../candidates` 同时返回 `record_candidates`，每项固定为 `record/source/saved/selected/rejected/error_code`。`source` 枚举为 `saved/server_url`；已保存且仍合法的记录使用 `saved=true, selected=true`，仅从 Server URL 发现的新候选使用 `selected=false`。同一规范化域名有多个来源时合并为一项并按 `saved` 优先；不合法条目可以 `rejected=true` 返回脱敏的 `error_code`，但不得被选中。字段缺失、空列表和新候选默认选中都是契约失败。

每个选中域名在启用前必须通过现有 `ConflictChecker` 的内部记录冲突检查。该检查只能证明 HomeAgent 内部未发现重叠管理，不能证明用户对外部 DNS 记录的权属，也不能证明外部 `ddns-go` 已停止写入。页面必须在最终确认中要求用户声明有权管理选中记录并已排除外部双写，但不得把该声明表达为系统已自动证明。

### 11.6 保存前预检与写入顺序

`POST .../validate` 需要现有设置管理权限，接收 `detection_id/records`，必须严格只读且总超时为 10 秒。它独立聚合：探测未过期、默认路由和自动解析结果未变化、已解析出稳定公网 IPv6、域名规范化、内部所有权无冲突、DNS 服务商凭据可读每个目标记录、当前 AAAA 与预计变化。任一记录失败都使整体 `validation_status=invalid`，同时在 `record_results` 中保留每条的 `valid/error_code/current_aaaa/planned_aaaa`，不能以空列表、`has_update=false` 或默认成功代替。

预检成功返回 HTTP 200、`validation_status=valid`、`validation_token`、`validated_at`、`expires_at` 和逐记录计划。`validation_token` 为服务端内存保存的 256 位密码安全随机单次令牌，绑定当前用户、`detection_id`、规范化表单摘要、当前配置版本和探测地址，60 秒后按服务端单调时钟过期，进程重启后全部失效。每个用户最多保留 10 个未过期令牌，超出时先清理已过期再拒绝新预检，不淘汰未过期令牌。

业务验证失败仍返回 HTTP 200 及 `validation_status=invalid`，仅包括 `stale_detection/no_default_route/unsupported_route_interface/no_address/invalid_record/ownership_conflict`。非法 JSON 或结构缺失返回 400，身份/权限失败返回 401/403；Provider 无法查询、超时或服务端无法产生可验证计划时返回 503 及 `provider_unavailable/provider_timeout/validation_unavailable`。只读预检不读写持久化存储，因此不定义 `persistence_unavailable`。

现有 `PUT /api/v1/server/network` 拟扩展请求为 `enabled/records/config_version/validation_token/external_writer_confirmed`。`enabled=true` 的首次启用，以及已启用状态下修改记录，必须携带未过期令牌且 `external_writer_confirmed=true`。网卡和地址不在请求契约中。兼容旧客户端时可额外接收 `interface`；在启用路径它只能为空或等于令牌绑定的自动解析结果，否则返回 HTTP 400 `interface_is_read_only`。带 `config_version` 的 `enabled=false` 请求允许保存域名草稿或禁用当前配置，不需要令牌，且绝不写 DNS；其版本必须与服务端当前版本一致，否则返回 HTTP 409 `config_conflict`。

这里的旧客户端兼容仅指旧请求字段可以解析，并不绕过新增安全门禁：旧页面不携带版本、令牌和外部发布者确认时，启用或修改记录返回 HTTP 409 `validation_required`。为保留紧急停用能力，缺少 `config_version` 的 `enabled=false` 请求只把当前配置原子切换为禁用并递增版本，忽略且不持久化请求中的 `records/interface`，因此不会用旧页面覆盖并发配置；它不需要令牌且不写 DNS。升级后由新版页面完成探测和预检；不承诺旧页面继续执行启用或修改操作。

令牌在通过身份、JSON 结构、表单摘要和 `config_version` 比对后，于最终重探测前以 CAS 原子消耗。同一令牌的并发请求只有一个能消耗成功，其余返回 HTTP 409 `stale_validation`；消耗后无论重探测、持久化、请求取消或 DNS 发布结果如何都不恢复令牌。用户可重新执行预检取得新令牌。

PUT 成功返回 HTTP 200 及 `config_version/enabled/resolved_interface/resolved_address/records/status/record_statuses`；解析字段是只读运行状态。此时 `status` 可为 `disabled/pending/syncing/verifying/synced/failed`，不因配置已受理就固定返回 `synced`。结构或域名非法返回 400，身份/权限失败返回 401/403，版本或令牌过期返回 409，配置持久化失败返回 500 `persistence_failed` 且无 DNS 副作用。

用户确认后的写入顺序固定为：

```text
校验未过期 validation_token 与表单摘要
  -> 重新校验默认路由、自动解析地址、所有权和服务商可读性
  -> 原子保存新配置版本
  -> 进入 pending
  -> 逐记录更新 DNS
  -> 查询服务商确认
  -> 持久化每条记录结果
  -> 独立聚合页面状态
```

预检返回后必须核对配置版本、默认路由和探测上下文。用户在请求在途期间修改域名，或系统默认路由、解析接口、解析地址发生变化时，旧结果失效，不得覆盖新表单或发起 DNS 写入。最终重校验或配置持久化在 DNS 写入前失败时，保留旧持久化配置和运行状态，消耗该令牌并返回 `stale_validation` 或具体失败；不需要对新配置做回滚，因为它尚未落盘。配置已原子落盘后的 DNS 失败则依现有状态机保留新配置并进入逐记录 `failed` 重试，不回滚为旧配置。

配置集合变化的 DNS 副作用固定为：

| 变化 | 旧记录 | 新记录 | 在途任务 |
|---|---|---|---|
| 禁用配置 | 保留现有 AAAA，本地标记 `disabled` | 不适用 | 通过配置版本失效化，等待已返回 I/O 完成后不再重试 |
| 移除受管域名 | 保留 AAAA，状态标记 `disabled` 作为审计，不自动删除 | 其他记录正常调和 | 被移除记录的返回结果不得覆盖 `disabled` |
| 新增受管域名 | 不变 | 预检通过并持久化后从 `pending` 开始 | 按记录隔离 |
| 默认路由变化但解析地址不变 | 不重写 DNS | 不适用 | 更新诊断状态，旧配置版本任务返回后重新校验 |
| 默认路由或公网地址稳定变化 | 保留同一域名记录 | 两次解析一致后按新地址进入 `pending`，不先删除 AAAA | 旧地址请求返回后不得覆盖新状态，必要时立即按新地址再调和 |

移除记录或禁用后的所有权移交必须等待协调器确认旧配置版本无可重试任务，再由用户启用外部发布者。保留 AAAA 只是避免入口中断，不表示 HomeAgent 继续拥有该记录的写入权。

### 11.7 页面交互与布局契约

删除“物理网络接口”输入框和任何地址选择器，改为只读“当前网络解析”卡片，展示实际默认路由接口、自动选中的稳定公网 IPv6、探测时间、状态和简短筛选依据，并提供“重新探测”。存在多个地址时仍只显示系统按客户端规则自动确定的结果；详细诊断可展示排除原因计数，但不得要求用户从候选中选择。没有合格地址时显示 `no_address`，保留上次发布地址用于说明，并明确当前不会更新 DNS。

“受管域名”改为候选勾选列表与“手动添加”入口。新候选默认未勾选，已保存记录保持选中。页面顺序为启用开关、网络自动解析结果、域名确认、配置预检摘要、当前同步状态与主操作按钮。桌面和移动容器都必须保持上述信息层级，错误文本不得遮挡或挤出对应候选。

主操作分为“验证配置”和“保存并启用”。只有当最新预检结果与当前表单版本一致且全部必需项通过时，“保存并启用”才可交互。页面不得在 `PUT` 返回成功但记录尚未查证时显示“已同步”。

### 11.8 状态与失败矩阵

| 条件 | 探测/预检结果 | 是否可保存启用 | DNS 副作用 |
|---|---|---|---|
| 无合格接口 | `no_address` | 否 | 无 |
| 默认路由接口解析成功且有合格地址 | `ready` | 域名预检通过后可 | 预检阶段无 |
| 默认路由落在虚拟接口 | `unsupported_route_interface` | 否 | 保留既有 AAAA，不猜测底层物理接口 |
| 默认路由接口临时无合格地址 | `no_address` | 否 | 保留既有 AAAA，不删除 |
| 域名内部所有权冲突 | `ownership_conflict` | 否 | 无 |
| DNS 凭据或查询失败 | `provider_unavailable` | 否 | 无 |
| 部分记录写入失败 | 按记录保存 `synced/failed` | 已保存配置保留 | 成功和失败记录独立，不谎报整体成功 |
| 预检返回前表单改变 | `stale_validation` | 否 | 无 |

前端交互状态限定为 `idle/detecting/validating/ready_to_save/saving/error`，只表示页面请求进度；接口探测使用第 11.4 节枚举，预检使用 `valid/invalid`，DNS 记录继续使用第 8 节枚举。映射规则为：探测或预检失败只进入页面 `error`，不改写持久化 DNS 状态；成功保存后才由协调器把记录转为 `pending`。

### 11.9 实施分阶段

第一阶段只实施默认 IPv6 路由解析、复用客户端地址筛选、旧接口字段兼容迁移、已有配置与 Server URL 域名候选、严格只读预检与页面交互。第二阶段如需增加 Cloudflare Zone 候选枚举，必须另行设计审查和真实协议验证，不得在第一阶段顺手引入。

实施前预计需修改的现有公开契约包括 `PersistedConfig`、`serverNetworkReq`、`GET/PUT /api/v1/server/network` 的响应与校验、探测 Provider 的候选元数据以及设置页面。旧字段必须保持向后兼容；新增端点不复用设备地址 API，也不将新状态直接塞入现有 DNS 记录状态枚举。

### 11.10 测试与验收契约

实施必须测试先行，并显式覆盖：

1. 单接口和多接口下都由真实默认 IPv6 路由自动确定接口，不依赖枚举顺序；
2. 同一接口多个 IPv6 时优先保留仍有效的已发布地址，否则按客户端数值排序自动取第一项；
3. down、loopback、ULA、链路本地、temporary、deprecated、tentative 和 duplicated 反例；
4. VPN、隧道、桥接和容器接口不能覆盖实际物理默认路由，容器无法观察宿主机网络命名空间时安全失败；
5. 默认路由或地址变化需两次一致观察，失效时不删除 AAAA、不残留脏配置；
6. 旧接口字段兼容读取但不能覆盖自动解析结果，持久化失败安全拒绝；
7. 域名来源、规范化、默认未勾选与内外部所有权提示；
8. 预检绝无 DNS 写入，服务商失败、所有权冲突与过期返回不得误通过；
9. 保存前后的配置版本重校验、请求重叠与旧异步结果丢弃；
10. 多域名部分失败的独立状态聚合，不得用任务受理推断整体成功；
11. 真实 API 契约数据的“响应 → 解析 → 状态 → 渲染 → 事件回调”完整链路；
12. 真实浏览器布局下的桌面与移动容器溢出、遮挡、点击命中、焦点可见性与状态可读性；
13. macOS 真实接口、默认路由与地址标志采集，fixture 标注真实来源及与当前环境的差异；
14. 在授权环境中从独立外网验证权威 AAAA、公共解析、TLS 和实际 HomeAgent 入口。

本设计的核心成功标准为：任何受支持的宿主机都无需输入或选择网卡及 IPv6；多个接口和多个地址由默认路由与客户端同源规则自动解析，无法可靠解析时安全停止而非要求用户选择；域名有可追溯候选来源且未经确认绝不写入；预检、保存、DNS 发布和服务商查证的状态不混合；任何失败都不产生未经稳定确认的切换、记录删除或虚假成功。

量化验收门槛为：本机接口探测在第一阶段受支持的 macOS 原生宿主机上 3 秒内返回成功或结构化失败；只读预检在 10 秒总超时内返回；页面收到探测或预检响应后下一次浏览器绘制前必须展示最新表单版本对应的状态。上述时间项分别以 Go Benchmark/带可控时钟的超时测试和真实浏览器性能记录验收，不使用静态 DOM 检查代替。

外部双写验收必须先读取实际 `ddns-go` 或其他发布器的轮询间隔与目标记录，确认目标已从外部配置移除，再在不少于两个实际轮询周期且不少于 5 分钟的窗口内，对照外部进程日志、DNS 服务商审计事件和权威记录。任一证据源不可用或观测到非 HomeAgent 写入时，验收为阻塞而不是通过。
