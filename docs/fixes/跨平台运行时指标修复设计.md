## 2. 背景与直接证据

P1 设备健康与告警需求引入了最小运行 Facts，包括运行时间、负载、CPU、内存和磁盘。当前不同平台的采集实现不完整，导致管理端看到的指标因 Agent 所在操作系统而不同。

已确认的代码证据：

- `cmd/homeagent-agent/runtime_unix.go` 的 Linux 分支从 `/proc/uptime` 读取运行时间，并从 `/proc/meminfo` 读取内存总量与可用量。
- 同一文件的 macOS 分支当前采集内存和负载，但未写入 `uptime_seconds`。
- `cmd/homeagent-agent/runtime_windows.go` 当前仅设置 `disk_mount` 为 `C:\\`，未采集内存和运行时间。
- `internal/device/device.go` 中的 `uptime_seconds`、`memory_total_bytes` 和 `memory_available_bytes` 使用 `omitempty`；未采集时零值不会进入 Facts JSON。
- `cmd/homeagent-agent/main.go` 将平台采集结果编码到现有 Facts 请求；`internal/api/api.go` 校验并保存 runtime；`internal/ui/static/js/devices/actions.js` 读取并显示这些字段。因此字段完全缺失的首要原因位于平台采集端。
- UI 当前会把缺失内存换算并显示为 `0 / 0 MiB`，这是同一用户现象链上的独立展示缺陷，本修复必须同时处理。

因此当前现象为：Linux 路由器能够显示运行时间，macOS 和 Windows 显示 `-`；Windows 同时缺少内存指标。

## 3. 修复目标与边界

### 3.1 目标

1. Windows Agent 上报真实的物理内存总量与当前可用物理内存。
2. Windows Agent 上报真实的系统运行时间。
3. macOS Agent 上报真实的系统运行时间。
4. 保持 Linux 现有运行时间和内存采集行为不变。
5. 采集失败时安全降级为字段缺失，不伪造数值，也不阻断其他 Facts 上报。
6. 缺失的内存值在 UI 中显示为未知，而不是伪装成 `0 / 0 MiB`。
7. 通过平台单元测试、交叉编译检查和真实系统验收证明各平台契约。

### 3.2 非目标

- 不在本修复中新增温度、交换内存、进程内存、网络流量或历史峰值指标。
- 不改变现有 Facts API 路由或 JSON 字段名称。
- 不修改服务端健康状态枚举、告警阈值或 UI 布局；允许修正既有指标组件的缺失值渲染逻辑。
- 不将 Windows 的瞬时 CPU 使用率定义为 Unix load average。
- 不借本修复重构无关的平台采集逻辑。

## 4. 公开契约与数据语义

现有 `runtime` 对象和字段名保持兼容：

```json
{
  "runtime": {
    "observed_at": "2026-08-26T10:00:00Z",
    "uptime_seconds": 86400,
    "memory_total_bytes": 17179869184,
    "memory_available_bytes": 4294967296
  }
}
```

字段契约：

| 字段 | 语义 | 有效范围 | 失败行为 |
|---|---|---|---|
| `uptime_seconds` | 操作系统自最近一次启动起经过的整秒数 | 必须大于 0；采样时不足 1 秒或结果为 0 均按缺失处理 | 无法可靠获取时省略，不使用 Agent 进程运行时间替代 |
| `memory_total_bytes` | 操作系统报告的物理内存总字节数 | 大于 0 | 获取失败时与 available 一并省略 |
| `memory_available_bytes` | 当前可供系统使用的物理内存字节数 | `0 < available <= total`；受现有 `omitempty` 契约限制，0 统一视为未知 | 获取失败、值为 0 或违反范围约束时与 total 一并省略 |

本次新增的 Windows 内存 total 与 available 必须来自同一次 `GlobalMemoryStatusEx` 调用。Linux 保持读取同一份 `/proc/meminfo` 内容的现有行为。macOS 当前可用内存估值并非本次缺失修复的目标，不将其作为 Windows 新实现的契约依据；后续若要修正其精度，须建立独立需求和真实内存语义设计。

`observed_at` 仍表示 Agent 开始创建本次运行指标快照的时间，不作为系统启动时间或服务端离线判断的权威时钟。本修复不改变其现有赋值时点。

## 5. 平台采集方案

### 5.1 Windows

内存采集使用 Windows 原生系统 API `GlobalMemoryStatusEx`：

- `ullTotalPhys` 映射到 `memory_total_bytes`。
- `ullAvailPhys` 映射到 `memory_available_bytes`。
- 调用失败、总量为零、可用量为零或可用量大于总量时，本次省略两个内存字段。

运行时间使用项目现有 `golang.org/x/sys/windows.DurationSinceBoot()`，其内部调用 Windows `GetTickCount64`；返回的 duration 取整为秒后映射到 `uptime_seconds`：

- 使用 64 位接口避免旧 32 位计数器约 49.7 天回绕问题。
- 不使用墙上时钟减启动时间推算，避免系统时间校准造成负数或跳变。
- `DurationSinceBoot` 不返回常规调用错误；若换算结果小于 1 秒，则省略 `uptime_seconds`，但保留其他成功采集的指标。

Windows uptime 不新增依赖。`golang.org/x/sys/windows` 当前未公开 `GlobalMemoryStatusEx` 包装，内存采集应基于同一现有依赖提供的 `NewLazySystemDLL("kernel32.dll")` 和 `NewProc("GlobalMemoryStatusEx")` 建立最小窄接口。自定义 `MEMORYSTATUSEX` 必须严格保持官方字段顺序：两个 32 位字段后跟七个 64 位字段，预期结构大小为 64 字节；实现必须先把 `dwLength` 设置为实际结构大小，再调用一次原生函数并校验返回值。若发现必须新增外部依赖，须先说明必要性并重新确认。

审查期间已在 Windows 11 专业版 Build 26200、AMD64 实机运行独立 Go 探针，使用与候选实现相同的 `x/sys/windows` 调用路径：

- 探针 SHA-256：`4a67a6c5e2ef20ad2a72b9babf350acc688552dc52a202f1ff0714cfd8defad0`。
- `MEMORYSTATUSEX` 实际大小和调用前 `dwLength` 均为 64 字节。
- `GlobalMemoryStatusEx` 返回成功；`ullTotalPhys=33495388160`，与同一主机 CIM `TotalVisibleMemorySize * 1024=33495388160` 完全一致。
- `ullAvailPhys=17510576128`；与调用前后 5 秒内 CIM 可用内存读数的最大差为 11694080 字节，约占总内存 0.035%，低于 5% 验收容差。
- `windows.DurationSinceBoot()` 返回 285067 秒；由 CIM `LastBootUpTime` 与探针采样时间独立计算的整秒值同为 285067。
- 探针退出码为 0，上传前后 SHA-256 一致；验证后远端及本地临时目录均已删除。

该证据确认原生 API、Go ABI、字段语义和普通进程调用路径。目标 HomeAgent 服务当前以 `LocalSystem` 运行，但探针没有注入或重启现有服务；`LocalSystem` 下候选 Agent 自主采集与真实 HTTP 上报属于实现后的服务级验收，不能由独立探针替代。

### 5.2 macOS

运行时间通过项目现有 `golang.org/x/sys/unix.SysctlTimeval("kern.boottime")` 结构化读取内核启动时间，再以当前系统时间与启动时间之差计算整秒数：

- 使用 `Timeval` 的秒与微秒值，不依赖面向人工展示的本地化 CLI 文本格式。
- 当前时间早于或等于启动时间、返回结构无效或调用失败时省略字段。
- 若系统时钟在运行期间被大幅调整，下一次采样仍以当前内核启动时间重新计算；不得持久化并累加上一次结果。

审查期间已在 macOS 26.5.2（Build 25F84）真实读取 `kern.boottime`：返回 `sec=1786345335, usec=890434`，对应 2026-08-10 15:02:15；同一时刻系统 `uptime` 约为 16 天 5 小时，两者一致。沙箱内 CLI 调用被限制，沙箱外无特权调用成功，因此实现不得依赖 `exec.Command("sysctl", ...)`，应直接使用现有结构化系统调用。实施后仍须在真实 Agent 守护进程入口验证权限与返回值。

由于 `runtime_unix.go` 同时以 `darwin || linux` 构建，禁止在该文件直接引用仅 Darwin 提供的 `unix.SysctlTimeval`。应在 `runtime_sysctl_darwin.go` 增加结构化启动时间窄接口，并在 `runtime_sysctl_linux.go` 提供同签名的不支持实现；`runtime_unix.go` 只在 Darwin 分支调用公共窄接口。这样保持现有文件边界并保证 Linux 编译。

### 5.3 Linux

保留读取 `/proc/uptime` 和 `/proc/meminfo` 的现有行为。本次只补充回归测试，确保跨平台抽象调整不会破坏 Linux：

- `/proc/uptime` 首字段只有解析为正整数秒数时才进入公开 Facts；小于 1 秒截断为 0 时按缺失处理。
- `MemTotal` 和 `MemAvailable` 转换为字节。
- 文件缺失、字段缺失或内容非法时安全省略对应指标。

## 6. 状态、失败与上报路径

采集与上报链保持如下边界：

1. Agent 创建带 `observed_at` 和逻辑 CPU 数的运行快照。
2. 平台采集函数分别填充其能够可靠获取的字段。
3. 每个指标组独立失败：运行时间失败不得清除有效内存，内存失败不得清除有效运行时间。
4. Agent 将有效快照放入现有 `runtime` 对象并发送至 `PUT /api/v1/devices/{id}/facts`。
5. 服务端继续执行非负值及 `available <= total` 校验，并整体替换本次 runtime 快照。
6. UI 只有在 total 与 available 同时存在且满足范围约束时才展示内存用量和比例；否则整个内存项显示 `-`，不得渲染为 `0 / 0 MiB` 或 `0%` 的有效指标。

采集错误不得造成以下副作用：

- 不得阻断 hostname、地址、Agent 版本等静态 Facts 上报。
- 不得沿用上一轮旧运行值冒充当前采样。
- 不得因局部采集失败进入旧 Server 协议降级模式。
- 不得写入负 uptime、零 total 配合非零 available，或 available 大于 total 的脏状态。

## 7. 兼容性与版本策略

- JSON API 仅填充既有可选字段，不新增或重命名公开字段，旧 Server 的协议兼容路径保持不变。
- 新 Agent 对旧 Server 的 runtime 降级行为保持现有契约；本修复不得扩大对任意 HTTP 4xx 的盲目降级。
- 旧 Agent 继续允许省略这些字段，Server 不得因字段缺失将设备自动判定为 degraded。
- 维护者已确认当前 Windows 实际部署的 `v0.6.2` 为本任务上一正式版本基线；候选客户端与服务端版本冻结为下一补丁版 `v0.6.3`。
- 本修复会修改客户端可执行行为，实施时必须将 `internal/version/version.go` 从 `v0.6.2` 升级为 `v0.6.3`；不得改用未审查的其他版本号。
- 若进入发布，必须按项目发布验收规则验证“上一正式版本 → 候选版本”的真实升级路径。

跨版本 Facts 矩阵：

| 方向与平台 | v0.6.2 既有行为 | v0.6.3 预期 | 兼容判定 |
|---|---|---|---|
| v0.6.2 Windows Agent → v0.6.3 Server | 上报 `runtime`，包含采样时间、逻辑 CPU 和盘符；内存与 uptime 缺失 | 首次 Facts 返回 HTTP 200；Registry 保留实际字段，缺失内存/uptime 维持 unknown，不得误报 degraded | 向后兼容 |
| v0.6.2 macOS Agent → v0.6.3 Server | 上报内存估值和负载，uptime 缺失 | 首次 Facts 返回 HTTP 200；uptime 维持 unknown，不影响其他健康规则 | 向后兼容 |
| v0.6.2 Linux Agent → v0.6.3 Server | 已上报 uptime、内存和负载 | 首次 Facts 返回 HTTP 200，逐字段值保持，无行为回归 | 向后兼容 |
| v0.6.3 Windows Agent → v0.6.2 Server | 新填充既有 `uptime_seconds`、`memory_total_bytes`、`memory_available_bytes` | v0.6.2 Server 已定义并接受这些字段，首次 Facts 应返回 HTTP 200，不应触发 legacy 降级 | 向前兼容 |
| v0.6.3 macOS Agent → v0.6.2 Server | 新填充既有 `uptime_seconds` | 首次 Facts 应返回 HTTP 200，不应触发 legacy 降级 | 向前兼容 |
| v0.6.3 Linux Agent → v0.6.2 Server | payload 字段集合与 v0.6.2 相同 | 首次 Facts 应返回 HTTP 200，逐字段值保持 | 向前兼容 |

上述“首次 HTTP 200”必须通过由 Git 历史提交 `38c5e0c`（源码版本 `v0.6.2`）构建的真实 Server/Agent 二进制和真实 HTTP 端口验证，不得用当前源码仅注入旧版本字符串来伪造基线。若真实结果出现拒绝或降级，不得修改测试迎合实现，必须停止并重新审查协议假设。

## 8. 测试策略

测试必须先于实现，并从本设计契约推导。

### 8.1 平台单元测试

Windows：

- 原生 API 返回有效内存快照时，显式断言 total 和 available 的字节值。
- 在 Windows amd64 和仓库实际发布的其他 Windows 架构上断言 `MEMORYSTATUSEX` 字段偏移、总大小为 64 字节，且 `dwLength` 在调用前为 64。
- `DurationSinceBoot` 窄包装返回已知 duration 时，显式断言整秒转换。
- 反例：available 大于 total 时两个内存字段均不写入。
- 反例：内存 API 失败但 uptime 成功时，仅 uptime 存在。
- 反例：uptime 小于 1 秒但内存成功时，仅省略 uptime，内存仍存在。
- 覆盖 64 位 uptime 超过 49.7 天的值，防止错误退回 32 位计数器。

macOS：

- 给定有效启动时间时，显式断言计算后的 uptime。
- 反例：启动时间晚于或等于当前时间时省略 uptime。
- 反例：系统调用失败或结构无效时省略 uptime，其他指标不受影响。

Linux：

- 保留并补齐有效 `/proc/uptime`、零值、非法内容和文件读取失败的回归测试，并显式断言零值不进入编码后的 Facts JSON。
- 验证内存采集行为没有因公共抽象调整而改变。

平台 API 应通过窄接口注入可控替身。fixture 必须基于真实平台调用观察构造，并在测试中注明来源、结构和与真实系统的差异，不得根据实现反向构造。

### 8.2 协议链测试

- 使用真实 HTTP 端口验证 Agent 采集结果经过 JSON 编码、Facts 请求、服务端解析和 Registry 持久化后仍保持原值。
- 验证字段缺失不会被服务端补零或沿用旧值。
- 验证非法内存关系被服务端拒绝，且 Registry 不留下部分更新或脏状态。
- 验证 UI 将缺失、零值或非法内存快照显示为 `-`，将有效 Windows 内存显示为用量与比例；uptime 的公开有效域为正整数，不要求区分零值与缺失。
- 扩展现有 `internal/ui/testdata/browser-layout.test.mjs`，由 `internal/ui/embed_test.go` 通过真实 `httptest` 端口启动页面，并使用真实 HTTP API 契约数据验证“响应 → 解析 → 状态 → 健康详情弹窗渲染 → 点击交互”完整路径；必须断言 Windows/macOS uptime 可见、Windows 内存可见、缺失内存显示为 `-`，Console 无未捕获异常且操作入口可点击。

### 8.3 真实平台验收

候选 Agent 必须分别在 Windows、macOS 和 Linux 上通过真实用户入口启动并自主上报，不得只依赖交叉编译或 mock：

| 平台 | 必验指标 | 对照来源 |
|---|---|---|
| Windows | uptime、物理内存总量、可用内存 | Windows 原生系统工具或同一系统 API 的独立读取结果 |
| macOS | uptime | `sysctl kern.boottime` 等独立系统证据 |
| Linux | uptime、内存 | `/proc/uptime`、`/proc/meminfo` |

验收容差固定如下：

- 在 Agent 上报前后各读取一次平台独立 uptime，Agent 上报值必须位于两次独立读数构成的闭区间内，允许整秒截断额外产生 1 秒误差。
- 从 Agent 启动到 Server/UI 可见的等待上限为 45 秒，超过即判定失败。
- Windows 物理内存总量必须与独立系统读数一致；可用内存必须满足 `0 < available <= total`，并与上报后 5 秒内取得的独立读数相差不超过物理内存总量的 5%。

### 8.4 跨版本安装与升级验收

基线版本固定为 `v0.6.2`，候选版本固定为 `v0.6.3`。必须覆盖：

1. 全新安装 v0.6.3：通过真实安装入口启动 Agent，确认 Windows/macOS/Linux 对应运行指标自主上报。
2. 就地升级 v0.6.2 → v0.6.3：通过 Web 管理入口调用认证后的 `POST /api/v1/devices/{id}/upgrade`（批量时使用对应 upgrade-all API）下发真实控制命令并完成原子替换，新进程必须自主上报候选版本和新增 Facts。当前 `homeagent-server upgrade` CLI 仅解析并打印 payload，不会下发命令，不得作为升级验收入口。
3. 双向协议：分别执行 v0.6.2 Agent → v0.6.3 Server、v0.6.3 Agent → v0.6.2 Server，覆盖 Windows、macOS、Linux 的第 7 节矩阵。

本任务不改变受管二进制或运行时数据路径，因此旧软链接迁移验收不适用；若实施中出现任何路径变更，必须停止、补充路径迁移设计和三类全路径回归后重新确认。

发布后还须从公开服务使用上一正式版本执行真实升级冒烟；任何真实服务失败均阻断发布完成声明。
