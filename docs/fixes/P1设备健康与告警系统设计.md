# P1 设备健康与告警开发方案

## 1. 文档状态

- 状态：Draft
- 目标版本：v0.6（基础健康状态与 Dashboard）、v0.7（Webhook 告警闭环）
- 任务来源：[HomeAgent 产品迭代路线图](homeagent-product-roadmap.md)
- 前置条件：P0 统一任务与回执模型；P1 离线指令与断线重连收敛提供可靠任务终态
- 适用范围：设备活跃度、Agent 版本、SSH 同步、DDNS、升级任务、最小运行指标、健康历史、Dashboard 和通用 Webhook
- 非目标：通用指标平台、日志采集、任意自定义规则、短信/邮件/商业告警平台集成、自动修复、P2 全局存储治理

## 2. 目标

将分散在 Registry、SSE、Command、SSH 同步和 DDNS 状态中的事实转换为稳定、可解释、可行动的设备健康状态，并在故障持续、恢复或投递失败时形成有界的通知闭环。

本阶段必须满足：

- 每台设备具有 `healthy`、`degraded`、`offline` 或 `unknown` 综合状态。
- 每个非健康状态包含稳定原因码、首次发生时间、最近观察时间和建议动作。
- 连接瞬时抖动不会立即触发离线告警，服务端重启也不会制造虚假恢复通知。
- Agent 版本落后、SSH 漂移或持续失败、DDNS 异常、升级失败或长期未收敛能够被独立识别。
- Dashboard 能按严重度汇总异常设备，并展示单设备健康历史。
- 告警通道可插拔；首个实现为带签名、超时、退避重试和投递记录的通用 Webhook。
- 同一持续故障只维护一个告警实例；静默不改变健康事实；恢复后记录恢复时间并按策略发送恢复通知。

## 3. 现状与直接证据

### 3.1 当前观察链

```text
Agent collectDeviceFacts
        │ 启动时、内容变化时、每 10 分钟强制上报
        ▼
PUT /api/v1/devices/{id}/facts
        │ 更新 Registry Device 与 LastSeenAt
        ├──────────────▶ Device 列表展示 AgentVersion / 地址
        │
SSE 订阅连接 ─────────▶ API DTO 的 connected 在线标记
        │
Command ACK ──────────▶ SSH / Upgrade 任务结果与 Device 投影
        │
IPv6 上报 + DDNS 调和 ▶ DeviceIPv6State.SyncStatus / SyncError
```

### 3.2 已确认事实与缺口

| 直接证据 | 当前能力 | 缺口 |
|---|---|---|
| Agent Facts reporter 每 30 秒检查变化、每 10 分钟强制发送 | `LastSeenAt` 可作为低频活跃证据 | 10 分钟周期下不能使用过短离线阈值；上报内容没有运行指标 |
| `Device` 保存 `AgentVersion`、`LastSeenAt`、SSH `SyncStatus` 和错误 | 有健康判断所需的部分事实 | Registry 同时承担设备资料与模块投影，不应继续承载完整告警生命周期 |
| Dashboard 以 SSE 订阅存在与否显示在线/离线 | 能显示当前控制通道连接态 | SSE 抖动、Server 重启会造成瞬时离线；连接态不能代表综合健康 |
| P0 Command 保存升级等任务终态 | 可识别失败、超时和长时间未完成 | 尚无面向健康的规则、持续时间和建议动作投影 |
| `DeviceIPv6State` 保存 desired/applied 地址、同步状态和错误 | 可识别 DDNS 同步失败与地址漂移 | 当前 Store 为内存实现，服务端重启后不能作为恢复通知的唯一事实来源 |
| 当前没有健康历史和通知投递记录 | 无 | 无法判断问题首次发生时间、去重、恢复或 Webhook 是否送达 |

上述证据能确认健康能力所需输入已经部分存在，但不能从单一字段推断设备健康。实现必须读取完整事实链，并保留每条规则的独立判定结果。

## 4. 核心决策

### 4.1 新增独立业务模块 `internal/health`

`health` 负责规则求值、设备综合状态、状态变更历史和告警生命周期，是健康状态的唯一事实来源。它只依赖稳定的领域接口，不直接读取 `api`、UI 静态资源、Cloudflare provider 或 Registry 文件格式。

建议边界：

```text
internal/health
├── model.go          # 状态、信号、原因、快照与历史事件
├── evaluator.go      # 纯规则求值与综合状态归并
├── service.go        # 评估调度、状态迁移与告警事件发布
├── repository.go     # 快照和历史的存储契约
├── rules/            # 内置规则；不依赖 infrastructure
└── ports.go          # Facts、Command、DDNS、版本策略和时钟端口

internal/alerting
├── model.go          # Alert、Silence、DeliveryAttempt
├── service.go        # 去重、静默、恢复与投递调度
├── repository.go     # 告警和投递记录存储契约
├── channel.go        # 可插拔 Channel 接口
└── webhook/          # HTTP Webhook 基础设施适配器
```

`health` 不直接依赖 `alerting` 的基础设施实现。健康状态变化通过领域事件或窄接口交给告警服务；告警投递失败不得反向改变设备健康状态。

### 4.2 区分连接态、活跃度与综合健康度

- `connected`：当前是否存在已认证 SSE 订阅，仅用于实时控制能力展示。
- `last_seen_at`：Server 最近接收可信 Facts、heartbeat 或合法 ACK 的时间。
- `liveness`：根据服务端时间和最后活跃证据计算的 `fresh`、`stale`、`lost`、`never_seen`。
- `health_status`：合并全部规则后的 `healthy`、`degraded`、`offline`、`unknown`。

SSE 连接断开只更新 `connected`，不得立即创建 `offline` 告警。已连接设备通常是活跃的强证据，但健康求值仍以服务端记录的可信时间戳为准。

### 4.3 健康状态是派生事实，历史事件是持久事实

- 原始 Facts、Command 结果和 DDNS 状态仍由各自模块拥有。
- `health` 保存最新 `HealthSnapshot`，便于列表读取与重启恢复。
- 只有对外可见的规则状态变化写入 `HealthEvent`；定时重复求值不重复追加历史。
- Dashboard 不在浏览器端重新实现规则，只消费 Server 返回的健康投影。
- 配置或规则版本变化必须触发重评估，并在事件中记录 `rule_version`。

### 4.4 先内置规则，不开放用户表达式

首期规则使用具名、版本化的 Go 实现和受约束配置。暂不引入 CEL、JavaScript 或 YAML 表达式引擎，避免任意执行、难以迁移的规则语义和不可控资源消耗。

### 4.5 时间只信任 Server，Agent 时间仅作诊断

- `received_at` 由 Server 在成功验证请求后生成，是离线、持续时间和告警窗口的权威时间。
- Agent 上报的 `observed_at` 可用于展示采样时间，但不得单独决定状态迁移。
- 运行时间 `uptime_seconds` 是持续时长而非墙上时钟，可用于识别重启，不用于推导绝对时间。
- 所有持久化时间使用 UTC；UI 按浏览器时区展示。

## 5. 领域模型

### 5.1 状态与严重度

```go
type Status string

const (
    StatusHealthy  Status = "healthy"
    StatusDegraded Status = "degraded"
    StatusOffline  Status = "offline"
    StatusUnknown  Status = "unknown"
)

type Severity string

const (
    SeverityInfo     Severity = "info"
    SeverityWarning  Severity = "warning"
    SeverityCritical Severity = "critical"
)

type RuleState string

const (
    RuleOK       RuleState = "ok"
    RuleFiring   RuleState = "firing"
    RuleUnknown  RuleState = "unknown"
    RuleDisabled RuleState = "disabled"
)
```

`offline` 专用于设备活跃度丢失；其他故障即使为 critical 也归并为 `degraded`，从而让“无法联系设备”和“设备在线但功能异常”保持可区分。

### 5.2 健康快照

```go
type HealthSnapshot struct {
    DeviceID       string       `json:"device_id"`
    Status         Status       `json:"status"`
    Connected      bool         `json:"connected"`
    EvaluatedAt    time.Time    `json:"evaluated_at"`
    LastSeenAt     *time.Time   `json:"last_seen_at,omitempty"`
    Since          time.Time    `json:"since"`
    RuleVersion    int          `json:"rule_version"`
    Reasons        []Reason     `json:"reasons"`
    Facts          RuntimeFacts `json:"facts"`
    Revision       uint64       `json:"revision"`
}

type Reason struct {
    Code           string         `json:"code"`
    State          RuleState      `json:"state"`
    Severity       Severity       `json:"severity"`
    Summary        string         `json:"summary"`
    FirstObservedAt time.Time     `json:"first_observed_at"`
    LastObservedAt time.Time      `json:"last_observed_at"`
    SuggestedAction string        `json:"suggested_action"`
    Evidence       map[string]any `json:"evidence,omitempty"`
}
```

约束：

- `Reasons` 按 severity、reason code 稳定排序。
- `Evidence` 只允许规则定义的非敏感字段，不保存 Token、请求头、完整日志或任意错误响应正文。
- `Since` 表示当前综合状态开始时间；单条原因的持续时间使用 `FirstObservedAt`。
- 快照使用 `Revision` 做乐观并发控制，防止定时评估和事实更新并发覆盖。

### 5.3 健康历史

```go
type HealthEvent struct {
    ID            string         `json:"id"`
    DeviceID      string         `json:"device_id"`
    Type          string         `json:"type"` // opened, changed, resolved
    ReasonCode    string         `json:"reason_code"`
    FromState     RuleState      `json:"from_state"`
    ToState       RuleState      `json:"to_state"`
    Severity      Severity       `json:"severity"`
    OccurredAt    time.Time      `json:"occurred_at"`
    RuleVersion   int            `json:"rule_version"`
    Evidence      map[string]any `json:"evidence,omitempty"`
    SnapshotRevision uint64      `json:"snapshot_revision"`
}
```

相同设备、相同 `reason_code` 从 `firing` 持续到下一次 `firing` 不产生新事件；严重度或关键证据发生可见变化时写 `changed`；恢复写 `resolved`。

## 6. 最小运行 Facts

### 6.1 Agent 上报契约

在现有 Facts payload 中新增可选 `runtime` 对象，避免继续平铺字段：

```json
{
  "hostname": "mac-mini",
  "agent_version": "v0.6.0",
  "os": "darwin",
  "arch": "arm64",
  "runtime": {
    "observed_at": "2026-08-24T10:00:00Z",
    "uptime_seconds": 86400,
    "load_1": 1.25,
    "logical_cpu_count": 8,
    "memory_total_bytes": 17179869184,
    "memory_available_bytes": 4294967296,
    "disk_total_bytes": 494384795648,
    "disk_available_bytes": 64424509440,
    "disk_mount": "/"
  }
}
```

字段策略：

| 字段 | 必要性 | 规则 |
|---|---|---|
| `uptime_seconds` | 识别设备/Agent 重启上下文 | 非负；平台不支持时省略 |
| `load_1`、`logical_cpu_count` | 提供可跨设备比较的负载信息 | 两者同时存在时计算归一化负载；首期只展示，不告警 |
| memory total/available | 检测持续内存压力 | available 不得大于 total；缺失时规则为 unknown，不影响总体健康 |
| disk total/available/mount | 检测系统盘空间不足 | 首期只采集一个受管运行目录所在文件系统；不扫描全部磁盘 |
| `observed_at` | 展示采样时间与诊断时钟偏差 | 不作为离线或 TTL 的权威时间 |

不采集进程列表、用户名列表、文件明细、温度、网络流量、序列号或任意日志，遵循最小必要原则。

### 6.2 采样与上报

- 保留启动时立即上报、每 30 秒检测静态 Facts 变化和每 10 分钟强制 heartbeat 的现有行为。
- 运行指标默认每 60 秒采样，但只有越过展示量化边界或到达 10 分钟 heartbeat 才随 Facts 上报，避免频繁写入。
- 百分比在 Server 端由原始字节值计算；Agent 不同时上报两套可能矛盾的值。
- 每次成功上报整体替换 `runtime` 快照；字段缺失表示本次平台不支持或采集失败，不沿用旧运行值。
- 整个 `runtime` 缺失表示 legacy Agent；Server 保留设备静态 Facts，但将运行指标规则标为 `unknown`。
- payload 继续受 1 MiB 限制；所有数值在 Agent 和 Server 两端校验有限值，拒绝 NaN、Inf、负容量及明显溢出。

### 6.3 客户端版本与兼容

该阶段修改 Agent，必须升级客户端版本号。

- 新 Agent 对旧 Server 首次发送带 `runtime` 的 Facts，若旧 Server 因未知字段返回明确的 HTTP 400，则去掉 `runtime` 后重试一次。
- 降级仅允许匹配结构化错误码或确认的未知字段错误；不得对认证失败、限流或任意 4xx 盲目重试。
- 新 Server 接受不含 `runtime` 的旧 Agent；版本与活跃度规则仍生效，运行指标不支持不得使设备自动降级。
- 实施前必须以“上一正式版本 Agent → 候选 Server”和“候选 Agent → 上一正式版本 Server”验证真实请求链。

## 7. 健康规则

### 7.1 活跃度与状态归并

默认配置以当前 10 分钟强制 heartbeat 为基线：

| 条件 | 规则状态 | 综合状态 | 默认通知 |
|---|---|---|---|
| 从未收到已认证的设备活动 | `device_never_seen=unknown` | `unknown` | 不通知 |
| `now - last_seen_at < 15m` | liveness OK | 继续合并其他规则 | 无 |
| `15m <= age < 30m` | `heartbeat_stale=firing` | `degraded` | 默认不通知，仅 Dashboard 提示 |
| `age >= 30m` | `device_offline=firing` | `offline` | critical，经过 5m 防抖后通知 |

阈值约束：

- `stale_after` 必须至少为 heartbeat 周期的 1.5 倍。
- `offline_after` 必须大于 `stale_after`，默认是 heartbeat 周期的 3 倍。
- 运行时配置变更需校验关系并触发全量重评估。
- `LastSeenAt` 更新来源限于认证成功且语义合法的 Facts、heartbeat、网络状态上报或 ACK；管理端读取和失败认证不得刷新。
- Server 启动后加载持久快照并延迟一个评估周期执行离线通知，避免启动顺序造成告警风暴；时间阈值本身不重置。

综合状态优先级：

```text
device_offline firing                     => offline
没有任何可信活跃证据                      => unknown
至少一个 warning/critical 规则 firing      => degraded
所有适用规则为 ok，且必要事实可用           => healthy
仅可选指标规则 unknown                     => 不降低健康状态
```

### 7.2 Agent 版本落后

`agent_version_outdated` 由 Server 的版本策略端口提供：

- 目标版本来自 Server 当前发布策略的显式 `recommended_version`，不能通过字符串字典序或外部“最新 Release”临时推断。
- 使用严格 SemVer 解析；未知格式产生 `agent_version_unknown` 信息提示，不宣称落后。
- 低于最低支持版本 `minimum_supported_version` 为 critical；低于推荐版本为 warning。
- 版本源不可用时保留上一次已验证策略并标记策略陈旧，不把全部设备误报为落后。
- 预发布版本只与明确允许的通道比较，stable 设备不被强制追随 prerelease。

### 7.3 SSH 密钥同步

首期规则：

| 原因码 | 触发条件 | 恢复条件 |
|---|---|---|
| `ssh_sync_failed` | 最近 SSH Command 为 `failed`/`timed_out`，或 `SyncStatus=failed` | 后续同设备 SSH Command 成功且 applied 与 desired 一致 |
| `ssh_key_drift` | `AppliedVersion/Hash` 与当前 KeySet desired version/hash 不一致，且超过 10m 收敛窗口 | applied version/hash 与 desired 完全一致 |
| `ssh_sync_stalled` | SSH Command 非终态超过其冻结的完成截止时间；若 P0/P1 已负责超时则只消费其终态 | Command 进入终态或被新命令取代 |

不得只比较版本号：版本相同而哈希不同仍是漂移。未配置或从未要求 SSH 同步的设备，该规则为 `disabled`，不是健康。

### 7.4 DDNS 与地址状态

仅对已配置 DDNS 的设备启用：

- `ddns_sync_failed`：`SyncStatus=failed`；恢复为后续 `synced`。
- `ddns_address_drift`：desired 非空且 applied 不同，超过配置的同步超时与一个 sweep 周期。
- `ddns_no_valid_address`：已配置记录但持续没有可用候选地址，且宽限期结束；宽限期内只显示 info。
- `ddns_prefix_stale`：所属网络前缀超过 `PrefixStateTTL`，warning；不得把跳过危险更新误报为同步成功。
- 处于 `grace_period` 本身不是失败，Dashboard 展示剩余时间。

P2 将 DDNS 状态迁移为持久存储前，服务端重启后 DDNS 规则必须进入 `unknown`，直至重新获得地址与前缀事实；不得根据空内存状态发送“已恢复”。

### 7.5 升级任务

- `upgrade_failed`：最近一次适用于当前目标版本的升级 Command 为 `failed`、`timed_out` 或 `interrupted`。
- `upgrade_not_converged`：升级 Command 已 `succeeded`，但在默认 15 分钟内没有后续认证 Facts 证明运行版本达到目标。
- 升级 ACK 中的目标版本不直接更新 `AgentVersion`；只有新进程 Facts 是运行版本证据。
- 管理员取消升级不默认产生健康故障；如设备仍低于推荐版本，由版本规则独立提示。
- 旧的失败升级被更高版本成功 Facts 证明已收敛后恢复，避免历史失败永久污染健康。

### 7.6 运行资源

首期启用保守规则，且必须连续命中以抑制瞬时峰值：

| 原因码 | 默认触发 | 默认恢复 |
|---|---|---|
| `disk_space_low` | 总容量 < 8 GiB 时 available < 10%；其他文件系统 available < 10% 或 < 5 GiB；连续 2 个 heartbeat | 总容量 < 8 GiB 时 available >= 15%；其他文件系统 available >= 15% 且 >= 8 GiB；连续 2 个 heartbeat |
| `memory_pressure` | available < 10%，连续 3 个 heartbeat | available >= 20%，连续 2 个 heartbeat |

`load_1` 首期仅展示。不同 OS 的 load 语义和家庭设备工作负载差异较大，在获得真实基线前不据此告警。阈值使用触发/恢复滞回，避免边界反复开关。

绝对容量阈值只适用于总容量至少达到 8 GiB 的文件系统。OpenWrt 等小容量设备仍使用比例阈值，避免健康分区因物理容量不可能达到 8 GiB 而永久处于 degraded；小容量设备低于比例阈值时仍正常触发告警。

## 8. 评估与状态迁移

### 8.1 触发方式

健康评估由以下事件触发，并由每分钟 sweep 兜底：

- Facts 或 heartbeat 成功写入；
- SSE 连接建立/断开（只刷新 connected 投影，并请求重评估）；
- Command 状态进入或离开关键阶段；
- SSH desired KeySet 变化或同步投影更新；
- DDNS/网络状态变化；
- 版本策略或健康配置变更；
- 定时 sweep 跨过 stale、offline、静默或未收敛截止时间。

同一设备使用串行评估或基于 Revision 的 CAS。事件触发只投递 `device_id`，求值时重新读取最新事实，避免携带过时快照。

### 8.2 防抖与滞回

- 每条规则定义 `pending_for`；首次命中先进入内部 pending，到期且条件仍成立才 `firing`。
- pending 不写公开历史、不发送告警，但 Dashboard 可选择显示“正在确认”。
- 恢复也可定义 `recover_for`；条件持续恢复后才写 resolved。
- 设备离线默认 `pending_for=5m`；资源规则使用连续样本数而非墙上计时。
- Server 重启必须持久化 firing 的首次时间；不能将持续故障当成新故障。

### 8.3 失败隔离

- 单条规则异常时该规则为 `unknown` 并记录内部错误，不阻断其他规则。
- Repository 写入失败时不得发布健康变化或告警事件，防止状态未落库却已通知。
- 健康评估失败不影响 Facts、Command 或 DDNS 原业务写入；记录可观测日志并重试。
- 告警服务不可用不回滚健康事件；未处理领域事件需持久化或可重建。

## 9. 告警模型与生命周期

### 9.1 告警实例

```go
type Alert struct {
    ID              string     `json:"id"`
    Fingerprint     string     `json:"fingerprint"`
    DeviceID        string     `json:"device_id"`
    ReasonCode      string     `json:"reason_code"`
    Severity        Severity   `json:"severity"`
    State           string     `json:"state"` // firing, resolved
    OpenedAt        time.Time  `json:"opened_at"`
    LastObservedAt  time.Time  `json:"last_observed_at"`
    ResolvedAt      *time.Time `json:"resolved_at,omitempty"`
    NotificationRevision uint64 `json:"notification_revision"`
}
```

- fingerprint 为规范化的 `device_id + reason_code + scope` 的 SHA-256，不包含易变文本。
- 同一 fingerprint 同时最多一个 firing 告警。
- 持续故障更新 `LastObservedAt`，不重复创建实例。
- severity 升级可立即发送一次更新；降级默认只更新记录。
- resolved 后同一原因再次发生创建新 Alert ID，保留历史关联。

### 9.2 静默与通知窗口

- Silence 以 device、reason code 或全局范围匹配，并具有明确开始、结束、创建者和原因。
- 静默只抑制通知，不修改 HealthSnapshot、Alert 状态或历史。
- 静默期间恢复仍将 Alert 标记 resolved；默认不补发被静默的 firing 或 recovery。
- 首期支持单次时间窗口，不实现复杂 cron 维护窗口；周期维护窗口归入后续能力。
- 默认同一持续告警不周期提醒；可配置一次 `repeat_interval`，且必须设置最大重复次数。

### 9.3 恢复通知

- firing 通知已成功投递过，恢复时才默认发送 resolved 通知。
- firing 的所有投递均失败时，恢复仍记录，但不发送孤立的“已恢复”。
- 恢复 payload 包含原 Alert ID、开始时间、恢复时间和持续时长。
- 状态恢复与通知送达是两个事实；UI 分开展示。

```go
type Channel interface {
    Name() string

}

type DeliveryResult struct {
    ProviderMessageID string

    ErrorCode         string
    ErrorMessage      string

```

- 单通道失败不阻断其他通道。

- 插件注册在 Server 组合根完成，业务模块不直接依赖 `webhook` infrastructure。
- 首期只实现 `webhook`；其他通道需独立变更清单和安全评审。

## 11. Webhook 协议

### 11.1 请求

```http
POST /configured-path HTTP/1.1
Content-Type: application/json
User-Agent: HomeAgent-Webhook/1
X-HomeAgent-Event: alert.firing
X-HomeAgent-Delivery: dlv_...
X-HomeAgent-Timestamp: 1787536800
X-HomeAgent-Signature: v1=<hex-hmac-sha256>
```

```json
{
  "schema_version": 1,
  "event": "alert.firing",
  "delivery_id": "dlv_...",
  "sent_at": "2026-08-24T10:00:00Z",
  "alert": {
    "id": "alt_...",
    "status": "firing",
    "severity": "critical",
    "reason_code": "device_offline",
    "summary": "设备超过 30 分钟未上报",
    "opened_at": "2026-08-24T09:25:00Z",
    "suggested_action": "检查设备供电、网络和 Agent 服务"
  },
  "device": {
    "id": "dev_...",
    "display_name": "mac-mini",
    "health_status": "offline",
    "last_seen_at": "2026-08-24T09:20:00Z"
  }
}
```

不得发送公网/内网完整地址列表、SSH 公钥、Token、命令请求正文、原始日志或未经归一化的 provider 错误。

### 11.2 鉴权与防重放

- 每个 endpoint 使用独立的至少 32 字节随机 secret；配置和日志中必须脱敏。
- 签名输入为 `timestamp + "." + raw_body`，使用 HMAC-SHA256；接收方常量时间比较。
- `delivery_id` 在一次逻辑投递的全部重试中保持不变，接收方以此幂等去重。
- 建议接收方只接受时间戳偏差不超过 5 分钟的请求；HomeAgent 记录 Server 时钟异常但不泄露 secret。
- secret 支持双密钥轮换窗口；P2 再统一纳入凭据备份和加密治理。

### 11.3 HTTP 行为

- 连接加响应总超时默认 5 秒，响应正文最多读取 4 KiB，仅用于错误摘要。
- 默认只允许 `https`；显式的本机开发模式可允许 loopback `http`。
- 不跟随 3xx 重定向，避免签名载荷和凭据被转发到未授权主机；3xx 视为永久配置错误。
- 2xx 表示接收成功；`408`、`425`、`429` 和 `5xx` 可重试；其他 4xx 为永久失败。
- `429`/`503` 的 `Retry-After` 仅接受有限秒数或合法 HTTP date，并受最大退避上限约束。
- DNS、连接和 TLS 错误默认可重试；证书校验错误为永久配置错误，禁止提供跳过 TLS 校验选项。
- endpoint 必须拒绝 URL userinfo、fragment 和非 HTTP(S) scheme；首期不自动阻断私网地址，以支持家庭内网接收器，但 UI 明确显示目标主机。

### 11.4 重试与投递可见性

默认最多 6 次：立即、30 秒、2 分钟、10 分钟、30 分钟、2 小时，并加入 ±20% jitter。若告警在重试期间恢复：

- 已开始的 firing 投递完成当前请求后停止未来重试；
- 若至少一次 firing 已送达，则排队 resolved 通知；
- 若 firing 从未送达，则记录 canceled-by-resolution，不发送孤立恢复。

每次尝试保存 attempt number、开始/结束时间、状态码、耗时、错误码和下一次重试时间。只保留截断且脱敏的错误摘要，不保存响应正文。

### 11.5 外部协议验证门禁

当前设计的是 HomeAgent 自有通用 Webhook 契约，未选择 Slack、Discord、企业微信等外部专有协议，也未对任何真实第三方 endpoint 作兼容声明。因此本文档不伪造“已完成真实外部服务验证”的结论。

进入实现前必须：

1. 使用真实 HTTP 接收端观察 POST、签名原始字节、超时、2xx、3xx、429、5xx 和 `Retry-After` 完整响应链。
2. 记录接收端软件/版本、请求与响应头、是否发生重定向及最终状态；敏感值必须脱敏。
3. fixture 和 fake receiver 从上述观察构造，注明来源、已省略行为与真实端差异。
4. 至少加入“重定向到未授权主机不跟随”“签名错误安全失败”“429 超上限 Retry-After 被截断”三个反例。
5. 若后续支持具体第三方服务，必须单独验证其真实公开 endpoint，不能用本通用协议测试替代。

## 13. 存储与保留

P1 需要跨重启保留去重与恢复语义，但不提前实现 P2 通用 schema 平台：

- `HealthSnapshot`：每设备一份，原子覆盖。
- `HealthEvent`：追加写，默认保留 90 天或每设备 1,000 条，先到者生效。
- `Alert` 与 `Silence`：保留 active 记录；resolved 默认保留 180 天。
- `DeliveryAttempt`：默认保留 30 天，每 Alert/Channel 有界。
- 所有文件使用现有受管数据目录、`0600`、同目录临时文件和原子替换；并发写由 Repository 串行化。
- 启动时遇到损坏文件必须安全失败或隔离并报告，不得静默覆盖为空集合。
- P2 负责统一 schema version、迁移、备份、恢复和 SQLite 阈值评估；P1 文件格式仍须包含局部 `schema_version`。

健康历史与告警记录不得写回 `Device` JSON，避免热点追加、设备事实膨胀和跨模块耦合。

## 15. 未选方案

| 方案 | 未选择原因 |
|---|---|
| 直接用 SSE `connected` 判定在线 | 对网络抖动和 Server 重启过于敏感，无法表达 stale 或 unknown |
| 将全部健康字段加入 `Device` | 混合原始事实、派生状态和告警历史，扩大 Registry 写冲突与迁移成本 |
| 浏览器端计算健康状态 | 多客户端规则可能不一致，无法驱动服务端告警与可靠历史 |
| 首期接入 Prometheus/Alertmanager | 对家庭自托管场景引入额外部署成本；后续可作为 Channel 或指标导出扩展 |
| 首期支持任意规则表达式 | 增加安全、资源、版本迁移和可解释性风险，内置规则已覆盖路线图目标 |
| 每次求值都写历史并发送通知 | 会造成无界数据和告警风暴，无法表达一个持续故障实例 |
| Webhook 跟随重定向 | 可能把签名和告警内容发送到未授权目标，且使 endpoint 配置不可审计 |
| 将告警投递失败计入设备 degraded | 通知基础设施与设备本身是不同故障域，会造成因果混淆和递归告警 |

## 17. 测试策略

### 17.1 规则单元测试

- 四种综合状态及优先级归并。
- `never_seen → healthy → stale → offline → healthy` 全状态路径。
- stale/offline 边界前后 1 纳秒，使用注入时钟，不使用真实 sleep。
- SSE 断开但 heartbeat 新鲜时不离线。
- 可选运行指标缺失不使 legacy 设备 degraded。
- SemVer 正常、预发布、无效版本和版本策略陈旧。
- SSH 版本相同但哈希不同的漂移反例。
- DDNS grace period、prefix stale、failed 与真实恢复。
- 升级 ACK 成功但新版本 Facts 未出现时的未收敛规则。
- 资源阈值连续样本、触发/恢复滞回和 Agent 重启后的样本重置。

### 17.2 状态与持久化测试

- 同一 firing 条件重复求值不产生重复事件。
- 原因 severity 改变产生 changed，恢复只产生一次 resolved。
- 两个评估触发并发时 Revision CAS 不丢失更新。
- Repository 写失败时不发布告警事件。
- Server 重启保留首次发生时间，不重复 firing 通知。
- 损坏、截断或未知 schema 安全失败且不覆盖原文件。
- 保留策略只删除超期终态，不删除 active Alert 或 Silence。

### 17.3 Webhook 测试

- raw body 签名、时间戳与 constant-time 验证样例。
- 2xx 成功；3xx 不跟随；400 永久失败；408/425/429/5xx 有限重试。
- `Retry-After` 秒数、HTTP date、非法值和超过上限。
- DNS、连接超时、TLS 错误、慢响应和超过 4 KiB 响应。
- 同一 delivery ID 重试不变，不同通知 ID 不复用。
- firing 重试期间恢复的竞态和孤立恢复抑制。
- 静默期间继续记录健康与恢复，但不投递。
- endpoint 指向重定向目标、包含 userinfo 或非法 scheme 时安全失败。
- fake receiver 必须注明真实观察来源和与真实接收端差异。

### 17.4 API 与 UI 测试

- 健康摘要计数与筛选一致，unknown 不计为 offline。
- 历史 cursor 稳定、limit 有界、跨设备访问受管理员权限保护。
- reason、evidence 和 Webhook 错误文案均正确转义。
- 新 UI 读取旧 Server 缺失 health 字段时显示 unknown。
- 旧 UI 读取新 Server 的附加字段不受影响。
- Dashboard 在窄屏、长设备名、多原因和无历史场景可用。

### 17.5 跨版本与端到端测试

必须覆盖：

1. 上一正式版本 Agent → 候选 Server：旧 Facts 可接受，运行指标 unknown，不误报 degraded。
2. 候选 Agent → 上一正式版本 Server：未知 `runtime` 被确认拒绝后显式降级重试成功。
3. 候选 Agent → 候选 Server：运行 Facts、健康变化、Webhook firing、去重和 resolved 完整闭环。
4. 候选 Server 重启：持续故障不重复通知，恢复仍能关联原 Alert。
5. Webhook 接收端离线后恢复：有限重试送达；耗尽后 UI 可见且不无限重试。

## 18. 验收指标

### 18.1 功能指标

- 每台设备 API 和 Dashboard 均返回四态之一，不使用空字符串表达未知。
- 每个 firing 原因均包含 reason code、首次发生时间、最近观察时间和建议动作。
- stale/offline 判定与配置阈值一致，SSE 瞬时断开不会立即离线。
- Agent 版本、SSH、DDNS、升级和资源规则均能独立触发及恢复。
- 单设备历史可查询且相同持续故障不重复写 opened。
- 恢复后 Alert 记录 `resolved_at`，Dashboard 不再显示为 active。

### 18.2 可靠性指标

- 同一 Alert fingerprint 在一次持续故障期间最多一个 firing 实例。
- 默认配置下同一持续故障最多发送一次 firing 和一次 resolved 通知。
- Webhook 每次请求 5 秒内结束，单次逻辑投递最多 6 次，不存在无限 goroutine 或 PTY/连接泄漏。
- Server 重启后 firing 告警不被当作新告警，首次发生时间不变化。
- 单条规则或通道失败不阻塞其他设备和其他通道求值。

### 18.3 性能指标

- 100 台设备、每分钟全量 sweep 在开发基准环境中 1 秒内完成，且无网络调用发生在 health Repository 锁内。
  - **单次性能验收结果**（`go test -v -run=TestService_EvaluateAll_100Devices_Performance ./internal/health/...`）：100 台全事实设备全量评估耗时 **205.8ms**（< 1s 门限），状态摘要 100/100 Healthy。
  - **基准测试数据**（`go test -bench=BenchmarkService_EvaluateAll_100Devices -benchmem -run=^$ ./internal/health/...`）：**37.66 ms/op**，内存分配 17.78 MB/op，41545 allocs/op。
  - **锁内网络审计**：`EvaluateDevice` 中 Facts/SSH/DDNS/Command/Version 外部端口查询均在 Repository 锁外完成，锁内仅包含快照与事件的原子内存/文件写入，无网络阻塞。
- `GET /api/v1/health/summary` 不逐设备执行外部请求，不产生 N+1 文件读取。
- 历史和投递接口始终分页；内存队列和每设备历史均有明确上限。

## 19. 外部假设审计

本文档实施阶段审计记录如下：

- 外部服务：通用 HTTP(S) Webhook 接收端（用户可配置目标）。
- 关键假设：接收端以 2xx 确认接收；可安全重试的状态限定为 408/425/429/5xx；接收端可用 delivery ID 去重；不可恢复错误（400/401/403/404）立即中止。
- 真实请求验证结果：已在 E2E 真实本机 TCP HTTP 监听（`httptest.Server`）端口中完成验证，HMAC-SHA256 签名 (`X-HomeAgent-Signature`)、时间戳 (`X-HomeAgent-Timestamp`)、事件类型 (`X-HomeAgent-Event`) 校验全部通过。
- 测试替身与协议边界：Webhook 接收端使用真实本地 TCP 监听端口进行协议交互；跨版本兼容测试因仓库缺乏历史 Release 二进制制品，以严格的 v0.5.4 协议契约（Payload、Header 与 HTTP 状态码）构建双向端到端测试。
- 关键反例测试：
  1. 损坏文件与未知 SchemaVersion 999 启动安全拒绝 (`TestRepository_CorruptedFile_SafeFailure`);
  2. 接收端 HMAC 签名不匹配安全失败 (401 永久失败);
  3. 429 限流分类为 Retryable 并安全截断上限;
  4. 持续故障 Server 重启不产生重复 firing 通知 (`TestP1_ServerRestart_PreservesFiringStateAndNoDuplicateFiring`);
  5. 候选 Agent 遇到拒绝 runtime 的旧 Server 自动剥离 runtime 降级重试 (`TestP1_CrossVersion_CandidateAgentToLegacyServerFallback`);
  6. 候选 Server 接收上一版本 Agent（无 runtime）正常判定为 healthy 不误报 degraded (`TestP1_CrossVersion_LegacyAgentToCandidateServer`);
  7. 跨重启恢复后 delivery_id 保持恒定且 firing 成功不冲掉 resolved 待重试 (`TestAlerting_ResolvedPendingRecovery_NotOverwrittenBySuccessfulFiring`);
  8. 待重试记录按 `AlertID + ChannelID + Event + DeliveryID` 独立隔离，旧投递与新投递重叠时重启恢复互不覆盖 (`TestAlerting_PendingRetries_IsolatedByDeliveryID`);
  9. 上一正式版本 (v0.5.4) 真实二进制守护进程通过 Server 管理接口下发升级指令就地原子替换并自主上报 v0.6.0 Facts 全链路验收 (`TestP1_RealBinaryUpgrade_v054_To_v060`).
- 跨版本升级真实验收说明：已在 `TestP1_RealBinaryUpgrade_v054_To_v060` 中基于 Git 历史 Release 提交 `70e41fb` (v0.5.4) 源码编译出真实旧版客户端制品，以独立 OS 子进程形式运行 `v0.5.4 daemon` 并维持 SSE 连接，通过服务端公开管理接口 `POST /api/v1/devices/{id}/upgrade` 下发升级指令，验证了旧版 Agent 自主下载、SHA256 完整性校验、`info` 前置冒烟探测、就地原子替换文件并安全退出，以及随后拉起就地替换后的 `v0.6.0` 进程自主采集本地真实 `RuntimeFacts`（内存/磁盘/CPU/运行时间）上报服务端，服务端健康评估判定通过（Healthy）的全黑盒进程级验收。
