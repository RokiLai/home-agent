## 2. 问题背景与根因分析

### 2.1 现场证据与用户现象
- 用户在设备或服务端管理界面为 `hk-vps.rokilai.online` 保存域名绑定：
  1. 预检接口 `POST /api/v1/devices/{id}/domain-bindings/preflight` 返回 200，`available: true`；
  2. 随后提交创建请求 `POST /api/v1/devices/{id}/domain-bindings`（或 `/api/v1/server/domain-bindings`），持续返回 HTTP 409 `{"error":"conflict"}`；
  3. 数据库和控制面中实际并不存在该域名绑定记录。
- 用户感知为：域名明明预检可用且无冲突，点击确认保存却总是失败提示冲突，且无法通过重复点击或等待自愈。

### 2.2 根因执行链分析
通过代码追踪发现：
1. **控制平面全局版本与业务领域绑定的粒度错配**：
   - 当前创建绑定接口入参要求携带 `expected_revision`（前端取自域名面板上的 `dataset.revision`，即上次加载列表时返回的控制平面全局快照版本 `snapshot.Revision`）。
   - 服务端底层 `ControlPlaneService.CreateDomainBinding(ctx, expectedControlRevision, binding)` 校验 `snapshot.Revision != expectedControlRevision`；若不一致则直接返回 `store.ErrRevisionConflict`。
   - 域名服务层 `domainbinding.Service.Create` 将 `store.ErrRevisionConflict` 转换为 `ErrBindingRevisionConflict`；
   - API 层 `writeDomainBindingError` 将 `ErrBindingRevisionConflict` 与 `ErrFQDNConflict` 同样映射为 HTTP 409 `{"error":"conflict"}`。
2. **后台无关更新高频推进全局版本**：
   - 多个后台事件会持续推进同一个 `ControlPlaneSnapshot.Revision`：
     - 设备 Facts 上报周期性写入（`Registry.writeLocked() -> ReplaceRegistryState` 每次写入自增全局 revision）；
     - 域名协调器（`Coordinator`）的调和观察与任务执行（`TransitionDomainBinding`、`QueueReconcileTask`、`RecordObservation`、`CompleteReconcileTask` 等）；
     - 设备上线离线状态变更、授权变更等。
   - 全局 revision 处于持续单调递增状态。
3. **前端状态缓存与刷新缺失**：
   - 设备详情页（`internal/ui/static/js/devices/actions.js`）与系统设置页（`internal/ui/static/js/settings.js`）仅在初始打开或调用 `loadDeviceDomainBindings` / `loadServerDomainBindings` 时更新一次 `panel.dataset.revision`。
   - 在用户查看页面、输入域名、点击预检、弹出确认框这一交互过程中（往往耗时数秒至数分钟），全局 revision 早已被设备上报或域名调和推进多次。
   - 保存时提交了已过期的全局 revision，直接触发 409；且在保存失败后，前端并未刷新任何版本号，导致后续再次点击保存仍然携带相同的陈旧 revision，陷入死锁式的持续 409。
4. **混淆了 FQDN 业务冲突与存储并发冲突**：
   - HTTP 409 笼统返回 `{"error":"conflict"}`，前端直接弹窗 `保存设备域名失败` 或 `保存域名失败`，用户无法区分是域名已被他人抢占（业务冲突），还是版本落后/底层并发写冲突。

## 3. 目标与非目标

### 3.1 目标
1. **根除无关后台更新对创建绑定的误阻断**：
   - 设备 Facts 上报、设备属性更新、其他无关域名的调和状态推进，不得导致新域名创建失败。
   - 创建新域名绑定属于“新增实体”，对尚未存在的资源无需强依赖全库全局快照版本，而应当基于领域原子唯一性保证并发安全。
2. **严格区分业务冲突与存储并发冲突**：
   - 业务冲突：FQDN 已存在（未删除）或已被抢占，属于客户端业务错误（HTTP 409 `{"error":"fqdn_conflict"}` 或保持兼容的语义化区分）。
   - 存储并发冲突：底层并发写冲突（CAS 失败），由服务端透明在有限次数内重试，如果持续冲突则返回明确可区分的错误码，不能混淆为 FQDN 冲突。
3. **双端链路一致性与健壮性**：
   - 统一修复设备端（`POST /api/v1/devices/{id}/domain-bindings`）与服务端自身（`POST /api/v1/server/domain-bindings`）两条创建保存链路。
   - 前端生命周期与交互闭环：提交防抖、防重复点击、网络异常恢复、保存失败或预检后被占用的准确提示与状态刷新。
4. **保持既有安全与权限契约**：
   - 严格保留对域名 FQDN 格式、后缀合法性、Owner/Admin 权限校验；
   - 维持单域名原子唯一性（同 FQDN 无论并发多少次，最终仅能成功创建一个活跃绑定）。

### 3.2 非目标
1. 不废弃已有单个绑定存量修改（enable / disable / delete）的绑定级乐观测版本控制（`binding.Revision`），已有基于特定绑定 revision 的状态转移机制保持健壮。
2. 不修改 Cloudflare 发布器的交互契约与调和策略。
3. 不变更域名归属权限（Owner 管理机制）。

## 4. 架构与并发控制设计

### 4.1 核心矛盾：为什么创建不应校验全局 Revision
- 全局 Revision 是针对整个控制平面快照（包含全部设备、全部令牌、全部任务、全部绑定）的单调递增计数器。
- 修改已有绑定（如禁用某个 binding），校验该 binding 的版本（`binding.Revision`）是合理的乐观并发控制，防止两个管理员覆盖修改同一个绑定。
- 但**创建全新绑定**时，新实体在系统中尚不存在；创建操作的真正前置条件是：
  1. 权限合法（当前用户有权为该设备/服务端绑定域名）；
  2. 业务唯一性满足（系统中不存在同名未删除的 FQDN）；
  3. 参数与观察结果合法。
- 因此，创建绑定在底层持久化时，应当是原子事务性或 CAS 安全的插入操作：
  - 在底层 `ControlPlaneService.update` 乐观循环中加载最新快照；
  - 检查快照中是否已存在同名活跃 FQDN（若存在则终止并返回 `ErrFQDNConflict`）；
  - 若不存在，则分配 ID 并写入快照；
  - 提交快照（若发生并发底层 Revision 变化，由 `update` 自动在短时间内重试 CAS 重新加载最新快照判断，最大 4 次重试）；
  - 从而彻底解耦“全局 revision 递增”与“新域名创建”。

### 4.2 接口公开契约与兼容策略
#### 4.2.1 `expected_revision` 字段的兼容性
- 请求体：
  `POST /api/v1/devices/{id}/domain-bindings` 及 `POST /api/v1/server/domain-bindings`
  ```json
  {
    "fqdn": "hk-vps.rokilai.online",
    "expected_revision": 1234, // 可选 / 忽略或仅作为兼容参数
    "existing_record": true
  }
  ```
- **兼容策略**：
  - 后端创建接口将 `expected_revision` 标记为可选（Optional）。如果前端传来或不传，服务端创建流程均不再因客户端提供的全局 revision 过期而直接拒绝创建。
  - 对于创建操作，并发控制交给后端的 CAS 循环及 FQDN 唯一性校验。
  - 既有单元测试与调用方无需破坏性修改请求结构体，保持完全向后兼容。

#### 4.2.2 错误码契约细化
现有 API 层对所有冲突一律输出 `{"error":"conflict"}`，前端无法给出精准反馈。细化为：
- `ErrFQDNConflict`（FQDN 业务冲突：已存在同名绑定或被其他资源占用）：
  - HTTP 409
  - 响应体：`{"error":"fqdn_already_exists"}`（向后兼容：为避免现有只认 `conflict` 的脚本受到影响，提供 `{"error":"fqdn_already_exists","code":"conflict"}` 或维持 409，但由前端精准识别 `fqdn_already_exists`，若为 `conflict` 也优雅展示）。
- `ErrBindingRevisionConflict`（仅针对已有绑定的状态变更：enable/disable/delete 时绑定的 revision 发生变化）：
  - HTTP 409
  - 响应体：`{"error":"revision_conflict"}`。
- 业务明确区分后，前端可以在 FQDN 冲突时提示“该域名已被其他绑定占用”，在版本并发冲突时提示“数据已在其他端被修改，已自动刷新，请重试”。

### 4.3 状态矩阵与失败路径

| 场景 | 输入/并发状态 | 服务端行为 | HTTP 状态码 | 客户端行为 / UI 表现 |
|---|---|---|---|---|
| 正常创建 | FQDN 未占用，无并发冲突 | 原子写入绑定，初始化状态为 `enabled`（或存量记录 `observing`） | 201 Created | 清空输入框，刷新域名列表，Toast 成功提示 |
| 后台并发更新 | 创建期间设备上报 Facts，全局 revision 自增 | 服务端 CAS 重试机制在最新快照中再次校验 FQDN，成功提交 | 201 Created | 用户无感知，创建直接成功 |
| 并发重复创建相同 FQDN | 两个请求同时用同 FQDN 创建 | 互斥提交，第一个请求成功，第二个请求检测到已存在 FQDN 返回 `ErrFQDNConflict` | 1st: 201<br>2nd: 409 `fqdn_already_exists` | 1st 成功显示；2nd 提示“该域名已被绑定或已存在”，刷新列表无脏数据 |
| 预检后被占用 | 预检时可用，但用户确认期间被其他端抢先创建 | 创建时服务端快照唯一性校验失败，拒绝写入 | 409 `fqdn_already_exists` | 提示“域名已被抢先占用，请更换域名”，刷新列表 |
| 用户连续双击/快速多次点击 | 快速触发两次保存按钮 | 前端提交按钮处于禁用/加载中（Pending 锁）拦截重复点击 | 仅发出 1 次请求 | 防抖与按钮禁用，无重复请求 |
| 网络异常 / 超时 | 请求未到达或响应超时 | 前端捕获网络异常 | Network Error | 按钮恢复可用，提示网络失败，并自动调用 `load` 刷新当前真实列表确认是否已创建 |
| 权限不足 | 用户非 Owner 且无设备更新权限 | 鉴权拦截拒绝 | 403 Forbidden | 提示权限不足 |

## 5. 前端交互与生命周期改进

### 5.1 设备端与服务端保存流程统一
修改 `internal/ui/static/js/devices/actions.js` 中的 `createDeviceDomainBinding` 以及 `internal/ui/static/js/settings.js` 中的 `createServerDomainBinding`：
1. **防止重复点击（In-Flight Guard）**：
   - 点击“预检并添加”或“确认保存”后，设置按钮状态为 `disabled`，防止快速重复提交。
2. **预检与保存解耦**：
   - 预检只用于 DNS 外部探针及输入格式校验，不作为后端创建的唯一性锁定依据。
   - 创建请求直接提交目标 FQDN，后端具备权威唯一性保护。
3. **失败时的自动刷新与精准报错**：
   - 无论创建成功还是失败，均重新调用 `loadDeviceDomainBindings(deviceId)` 或 `loadServerDomainBindings()`，确保 DOM 状态与服务端实时对齐。
   - 解析响应中具体的 `data.error`：
     - 若为 `fqdn_already_exists` 或 `conflict`：提示“域名已被占用或已存在，请检查列表”。
     - 若为其他网络或服务端错误：展示友好错误提示。
4. **成功后的输入框清理**：
   - 只有在 201 Created 成功返回后才清空输入框。

## 6. 测试与验证策略（测试先行）

依据项目规则，测试必须源自设计契约，并在实现前准备好对应测试断言：

### 6.1 后端单元测试与并发测试（Go）
1. **后台持续更新期间创建绑定成功**：
   - 模拟后台高频推进控制面全局 revision（例如并发协程不断向 Registry / ControlPlane 写入 Facts 更新）。
   - 同时发起新域名创建请求，断言创建正常返回 201 Created，绝不返回 409，最终绑定正确持久化。
2. **并发相同 FQDN 创建原子排他性（负例与无脏状态断言）**：
   - 多个 goroutine 同时发起相同 FQDN 的创建请求。
   - 断言：恰好有且仅有 1 个请求返回成功（201 Created），其余请求均返回冲突（409），且数据库/存储中的绑定列表仅有一条记录，无多余未完成或脏数据残留。
3. **已存在活跃域名与已删除墓碑域名的区分**：
   - 已存在活跃域名创建返回冲突；
   - 已标记为 `deleted` 墓碑的域名允许被重新创建成功（验证历史复用契约不被破坏）。
4. **状态转移操作的 revision 强校验保留**：
   - 针对 enable、disable、delete 操作，验证基于 `binding.Revision` 的并发保护仍然生效（如果传入错误的 binding revision 必须正确拒绝并返回 409）。

## 8. 实施与生产验证计划（供部署前审查参考）
1. **目标**：修复设备与服务端域名绑定保存时由于全局 revision 推进导致的 409 假冲突。
2. **版本升级**：升级修改的 Server 组件版本（根据既有版本推进）。
3. **影响范围**：仅影响服务端与设备域名绑定的创建与并发处理，不影响已有绑定的调和、DNS 记录及设备数据。
4. **回退方式**：保留发布制品与旧版二进制，出现异常可通过 Supervisor 或 LaunchAgent 回滚旧版。
5. **生产验证计划**：
   - 在生产环境打开设备详情页或设置页；
   - 针对 `hk-vps.rokilai.online` 或测试子域名发起绑定保存；
   - 验证在后台上报正常运行期间一次性保存成功，状态达到 `observing` 或 `enabled`。
