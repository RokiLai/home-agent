## 2. 背景、现象与证据边界

### 2.1 用户现象

v0.6.3 全平台 Agent 升级后，路由器和普通设备仍在线并持续上报 Facts，但 Windows 与两台 macOS 设备在健康页面显示 `degraded`。当前持久化健康快照显示三台设备唯一的 firing reason 均为：

```text
code: ddns_prefix_stale
summary: 网络前缀已过期陈旧
```

路由器 `xiaoqiang-7d87e3ec` 自身保持 `healthy`，且四台设备均已重新连接并报告 `agent_version=v0.6.3`。历史 `upgrade_failed`、`upgrade_not_converged` 和 `agent_version_outdated` 事件已经在后续成功升级后 resolved，因此不构成当前异常原因。

### 2.2 已确认的代码证据

- `cmd/homeagent-agent/main.go:startRouterPrefixReporter` 使用进程内 `atomic.Uint64` 生成 `PUT /api/v1/devices/{id}/network-prefixes` 的 `revision`；Agent 每次启动均从 0 重新开始。
- 同文件 `startIPv6Reporter` 对普通设备 `PUT /api/v1/devices/{id}/network-state` 使用相同的进程内计数方式，因此缺陷不只影响路由器。
- 路由器前缀每 30 秒检查一次；内容变化时上报，内容未变化时每 10 分钟强制上报一次心跳。
- `internal/prefixstate/service.go` 和 `internal/devicestate/service.go` 均拒绝小于 Server 当前值的 revision；相同 revision 仅在内容相同时作为幂等请求接受并刷新 `LastSeenAt`。
- `internal/api/api.go` 将旧 revision 和相同 revision 不同内容统一返回 HTTP 409；当前响应是纯文本，没有稳定的错误码和 `current_revision` 字段。
- `cmd/homeagent-server/main.go` 当前为 device state 和 prefix state 创建内存 Store。Server 重启会清空当前 revision，而只重启 Agent 不会清空 Server 当前 revision。
- `internal/health/evaluator.go` 在 DDNS 已启用且 `PrefixStale=true` 时产生 `ddns_prefix_stale` warning；当前 `PrefixStateTTL` 为 15 分钟。
- v0.6.3 升级时序显示路由器 Agent 在 23:28:36 重启，三台 DDNS 设备约在 23:43 起触发 `ddns_prefix_stale`，与“前缀心跳连续 15 分钟未被接受”的路径一致。

### 2.3 尚未直接证实的部分

路由器环境没有可用的 `logread`，尚未取得路由器收到 HTTP 409 的直接日志。因此“升级重启导致 revision 回退，继而使前缀心跳被拒绝”是与代码和时序完全吻合的高可信候选根因，不在本设计中伪装为已取得 HTTP 层直接证据。

实施前必须通过可控真实端口复现以下旧行为因果链，作为根因确认门禁：

1. Server 先接受 revision `N`；
2. 模拟 Agent 重启，从 revision `1` 上报相同前缀；
3. 真实 HTTP 响应为 409，Server `LastSeenAt` 不刷新；
4. 评估时间推进超过 15 分钟后，DDNS 设备出现 `ddns_prefix_stale`；

若上述 1–4 不成立，必须停止实现并重新审查根因，不得以当前方案直接修改生产逻辑。应用候选修复后的对照复测属于实施后回归，见第 9.4 节，不作为实施前置条件。

根因门禁已于 2026-08-27 使用当前 v0.6.3 源码和 Go overlay 临时诊断测试完成，overlay 与测试源仅位于 `/tmp`，未修改仓库生产代码。执行命令：

```text
GOCACHE=/tmp/homeagent-go-build-cache go test -overlay=/tmp/runtime_revision_root_cause_overlay.json ./internal/api -run '^TestRuntimeRevisionRootCauseGate$' -count=3 -v
```

三次独立运行均得到相同结果：真实 `httptest` TCP Server 先接受 revision 9；随后 revision 1 返回 HTTP 409；冲突前后 `LastSeenAt` 完全相等；注入 `LastSeenAt + 16m` 后 `GetActivePrefixes` 返回 stale，健康评估结果为 `degraded` 且唯一目标 reason 为 firing 的 `ddns_prefix_stale`。测试总结果 `PASS`，`ok homeagent/internal/api`。该证据确认“低 revision 拒绝 → 心跳时间不刷新 → TTL 超时 → 用户异常”的完整因果链。

## 3. 目标与非目标

### 3.1 目标

1. Agent 正常重启、自升级和设备重启后，网络状态上报 revision 保持单调递增。
2. 同时覆盖普通设备 IPv6 地址和路由器 IPv6 前缀两条上报链路。
3. 同一逻辑快照的普通传输重试复用同一 revision；仅合格 HTTP 409 可为该快照生成唯一一次后继 revision，后继请求的全部普通传输重试复用新 revision。
4. revision 状态丢失、损坏或从旧备份恢复后，Agent 能通过受限的 409 协商追赶 Server 当前 revision。
5. revision 持久化失败时安全停止对应网络状态上报，不发送无法保证顺序的新快照，也不影响 Facts、SSE、SSH key 等其他模块。
6. 保持现有 DDNS 前缀 TTL、地址选择规则和健康状态枚举不变。

### 3.2 非目标

- 不将 device state 或 prefix state 的 Server 内存 Store 迁移为持久化 Store。
- 不引入 instance ID、Server lease、generation 或分布式共识协议。
- 不改变 IPv6 前缀发现、地址筛选、DDNS provider 或 DNS 更新逻辑。
- 不以删除、缩短或禁用 `ddns_prefix_stale` 健康规则掩盖问题。
- 不允许普通设备修改其他设备或其他网络的 revision。
- 不在本任务中支持同一设备 ID 的多个 Agent 进程并行写入；现有服务管理仍须保证单实例。

## 4. 公开协议契约

### 4.1 请求保持兼容

以下两个既有请求的字段和语义不变：

```json
{
  "network_id": "home",
  "revision": 42,
  "observed_at": "2026-08-27T00:00:00Z",
  "ipv6_addresses": []
}
```

```json
{
  "network_id": "home",
  "revision": 42,
  "observed_at": "2026-08-27T00:00:00Z",
  "prefixes": []
}
```

- `revision` 仍是正整数、在同一上报键内单调递增。
- 普通地址上报键为 `device-network-state + device_id + network_id`。
- 路由器前缀上报键为 `router-prefixes + router_device_id + network_id`。
- revision 只在同一个键内比较；不同设备、网络或上报类型互不影响。

### 4.2 HTTP 200

现有成功响应保持：

```json
{
  "accepted_revision": 42,
  "changed": false
}
```

相同 revision 且规范化后内容相同仍视为幂等成功，并刷新 Server `LastSeenAt`。内容未变化的强制心跳使用新的 revision，但 `changed=false`，不得触发不必要的 DDNS 更新。

### 4.3 HTTP 409

两个端点的 revision 冲突响应统一为 JSON：

```json
{
  "error": "revision_conflict",
  "current_revision": 57,
  "received_revision": 1
}
```

相同 revision 但内容不一致时：

```json
{
  "error": "revision_content_mismatch",
  "current_revision": 57,
  "received_revision": 57
}
```

契约要求：

- HTTP 状态始终为 409。
- `current_revision` 必须来自完成冲突判断的同一个 Server 状态快照，不得在锁释放后重新读取并拼接。
- 响应不得包含设备 Token、前缀内容或其他设备信息。
- v0.6.3 及更旧 Agent 不解析 409 body，因此从纯文本调整为 JSON 不改变其既有失败行为。
- 候选 Agent 仅在 `Content-Type` 为 JSON、错误码属于上述两个值且 revision 字段通过严格校验时执行追赶；其他 409、非 JSON、字段缺失、零值、溢出值或网络错误均按普通失败重试，不猜测 Server 状态。

## 5. Agent 持久化设计

### 5.1 文件位置与权限

新增状态目录固定放在已解析 `device.json` 的同一目录：

```text
<device-config-dir>/network-report-revisions/
```

这使自定义 `HOMEAGENT_DEVICE_CONFIG`、Windows ProgramData、macOS Application Support、Linux `/var/lib/homeagent` 以及路由器 `/data/homeagent` 自动沿用现有持久化根目录。不得将状态写入当前工作目录、可执行文件目录或 `/tmp`。

- 目录权限沿用现有设备配置目录。
- POSIX 状态目录权限必须为 `0700`，状态文件必须为 `0600`。
- Windows 状态目录和文件必须继承 `device.json` 所在受管目录的 ACL，并在实机验收中确认只有当前服务身份、`SYSTEM` 和 Administrators 可访问；不得授予普通 Users 写权限。
- 文件不包含凭据、地址或前缀，只保存 revision 元数据。
- 多级状态目录按需逐级安全创建；目录创建、权限收紧或父目录准备失败时不得创建临时文件、分配 revision 或发送请求。

### 5.2 文件格式

每个 revision key 使用独立状态文件，避免一个文件损坏或恢复时阻断另一个 reporter：

```text
network-report-revisions/
  <base64url(report-type)>/
    <base64url(device-id)>/
      <base64url(network-id)>.json
```

路径组件使用无 padding 的 RFC 4648 Base64URL 编码，编码前的三个原始组成部分还必须写入文件并在读取时逐项校验。该映射可逆且不包含路径分隔符，不允许直接拼接未经编码的输入。

单个状态文件格式：

```json
{
  "schema_version": 1,
  "report_type": "router-prefixes",
  "device_id": "router-1",
  "network_id": "home",
  "revision": 57
}
```

- 未知 `schema_version` 必须返回明确错误，不得覆盖为当前格式。
- revision 为 `uint64`，0 表示尚未分配，不得发送到 Server。
- 同一 key 的读取、分配和写入由进程内互斥锁串行化；不同 key 使用不同文件和锁，普通地址与路由器前缀 reporter 的失败、恢复和持久化互不覆盖。

### 5.3 原子写入与耐久性

每次分配 revision 必须先持久化成功，再允许构造并发送请求：

1. 在相同目录创建权限为 `0600` 的临时文件；
2. 写入完整 JSON；
3. 对临时文件执行 `Sync`；
4. 关闭临时文件；
5. 原子 rename 覆盖目标文件；
6. 在平台支持时同步父目录，提高 rename 跨崩溃的耐久性。

不得截断后原地写入。rename 前失败时必须保留原目标文件并清理本次临时文件；rename 已成功但父目录 Sync 失败时，目标文件仍必须是可解析的完整旧版本或新版本，但跨崩溃耐久性不确定，实现返回失败且不得发送本次请求。设计不承诺此时恢复为旧 revision。

Windows 原子替换必须使用项目已有且经过测试的可替换目标写入方式；如果现有 `daemon.AtomicWrite` 不能在 Windows 对已存在目标提供原子替换契约，实施前必须补充平台窄接口及真实 Windows 验证，不得假设 POSIX rename 语义。

### 5.4 分配与重试语义

- 一份新逻辑快照开始发送前调用 `Allocate(key)`，得到并持久化 `previous+1`。
- 首次启动时不存在文件，第一份快照使用 revision 1。
- “普通传输重试”专指 HTTP 超时、连接失败、5xx 或多 Server URL 切换；它们必须复用同一 payload 和 revision。
- 合格 409 不是普通传输重试，而是一次协议恢复信号；它可按第 6 节为同一业务快照生成唯一一次后继请求。后继请求发生的全部普通传输重试必须复用后继 revision。
- 前缀或地址内容发生新变化时分配新 revision。
- 10 分钟强制心跳是新的逻辑快照，分配新 revision；Server 接受后刷新 `LastSeenAt`，但相同内容返回 `changed=false`。
- 若 revision 已为 `math.MaxUint64`，分配必须失败并停止该 reporter；不得回绕到 0 或 1。

### 5.5 文件异常

| 情况 | 行为 |
|---|---|
| 文件不存在 | 首次发送前先原子写入 revision 1；若 Server 返回合格 409，再转入 `recovering` |
| JSON 截断、类型错误、key 身份不匹配或 revision 非法 | 将原文件原子移动为同目录唯一 `.corrupt-<UTC>-<random>` 证据文件；成功写入 revision 1 的新规范文件后才允许进入恢复上报 |
| 未知 schema | 安全失败，不发送对应上报，不自动降级格式 |
| 写入或 Sync 失败 | 不发送新 revision；下一周期重试持久化；其他 Agent 模块继续运行 |

损坏文件恢复必须遵守“先持久化、后发送”：只有损坏证据文件隔离成功，且新的规范文件已经原子写入 revision 1，才允许以 revision 1 上报。若 Server 无对应状态则直接接受；若 Server 返回合格 409，则按第 6 节追赶。隔离、写入或响应任一步失败均等待下一正常周期，禁止无限快速循环。每个 key 独立隔离和恢复；不得因一个 key 损坏删除或重建其他 key。

## 6. HTTP 409 自动追赶

候选 Agent 收到合格的 revision 409 后：

1. 校验 `received_revision` 必须等于本次 payload revision，`current_revision >= received_revision`，且 `max(local_revision, current_revision) < math.MaxUint64`；
2. 计算唯一的下一版本 `next_revision = max(local_revision, current_revision) + 1`；
3. 在同一 key 下原子持久化 `next_revision`；
4. 使用相同的业务快照、更新后的 `observed_at` 和新 revision 重发一次；
5. 本次逻辑上报最多执行一次追赶，第二次 409 按失败处理并等待下一正常周期。

该流程的目的仅是恢复本地状态丢失、损坏或旧备份回退。它不是多 Agent 并发仲裁协议，不得形成无上限的“revision 竞赛”。

“一次追赶”以一份逻辑快照为范围，而不是以单个 URL 为范围。若请求配置了多个 Server URL：

- 同一 payload/revision 可按现有优先级向多个候选 Server 重试。
- “当前活动 Server”定义为 `getActiveServer()` 返回的首选 URL；若为空或请求失败，按配置文件中的去重顺序尝试后续 URL。
- 首个返回合格 409 的 Server 可触发整份逻辑快照唯一一次追赶；追赶后从当前活动 Server 开始重新执行一次既有 URL 选择顺序。
- 任意 Server 的首个 2xx 结束本次逻辑上报。追赶后无论哪个 Server 再返回 409，都不得对本快照执行第二次追赶；继续尝试尚未尝试的 URL 也不得再次修改 revision，全部失败后进入 `waiting`。
- 测试必须覆盖：A 返回 409 后 B 返回 200；A 返回 409、追赶后 B 再返回 409；A 超时切换 B；两个 Server current revision 分叉。不得将多个 Server 的 revision 拼成无界竞赛。

## 7. 状态机与失败隔离

| Reporter 状态 | 触发 | 行为 | 退出条件 |
|---|---|---|---|
| `ready` | 状态文件有效，或文件不存在但 revision 1 已在发送前成功落盘 | 可分配并发送 | 持久化失败、文件异常或合格 409 |
| `recovering` | 文件不存在/损坏后的 revision 1 收到合格 409，或正常请求收到合格 409 | 执行一次有界追赶 | 200 后回到 `ready`；失败进入等待 |
| `waiting` | 写入失败、无效 409、第二次冲突或网络失败 | 不忙等；按原有 ticker/heartbeat 周期重试 | 下一周期重新读取/持久化成功 |
| `exhausted` | revision 达到 `MaxUint64` 或未知 schema | 停止该 reporter 并持续输出限频错误 | 人工迁移状态格式或修复文件 |

失败隔离要求：

- 普通地址 reporter 失败不得阻断路由器 reporter，反之亦然。
- 两个 reporter 的失败不得终止 daemon、SSE、Facts、命令执行、SSH key 或 GitHub 凭据同步。
- 失败时不得删除最后一个有效 revision 文件，不得把 Server revision 降低，也不得修改 DDNS 状态伪装恢复。
- 日志只记录 key 的非敏感类型、设备 ID、网络 ID、revision、HTTP 状态和错误码；不得记录 Token 或完整请求头。

## 8. 兼容性与版本策略

已部署正式基线为 v0.6.3，候选版本为 v0.6.4。本任务修改 Agent 可执行行为，实施时必须升级客户端版本；Server 因新增结构化 409 响应和嵌入式前端版本一致性一并构建 v0.6.4。

| 组合 | 预期行为 |
|---|---|
| v0.6.3 Agent → v0.6.4 Server | 200 契约不变；发生冲突时仍视 409 为普通失败，不会因 JSON body 崩溃 |
| v0.6.4 Agent → v0.6.3 Server | 正常持久化 revision；旧 Server 的纯文本 409 不触发自动追赶，按普通失败安全重试 |
| v0.6.4 Agent → v0.6.4 Server | 持久化、幂等重试和有界 409 追赶全部生效 |

不涉及二进制安装路径迁移，现有受管软链接目标不变；但必须验证自升级原子替换不会删除 `device.json` 同目录下的 revision 文件。

## 9. 测试策略

测试必须先于实现，且不能通过缩短 TTL、跳过冲突或删除健康断言使测试通过。

### 9.1 持久化单元测试

- 新文件首次分配为 1，第二次为 2；重建 store 后继续为 3。
- 两个不同 key 并发分配，最终两个独立文件分别保留全部递增结果，无丢失更新。
- 同一 key 并发分配得到唯一且严格递增的 revision。
- 临时文件写入、Sync、关闭和 rename 前各阶段注入失败，显式断言旧文件保持不变且没有发送回调；目录 Sync 失败时显式断言目标是完整旧文件或完整新文件、返回失败且没有发送回调，不错误承诺回退旧值。
- 文件截断、非法 JSON、未知 schema、revision 为 0/负数/非整数/溢出分别安全处理。
- 损坏文件隔离失败时不发送；隔离成功后证据文件保留，规范文件 revision 1 必须先落盘再发送；两个 key 并发损坏恢复互不覆盖。
- `MaxUint64` 不回绕且不发送。
- 文件及临时文件权限符合平台契约，失败临时文件被清理。
- 多级目录首次创建权限为 `0700`；逐级创建、权限收紧或父目录准备失败时没有状态文件、临时文件和 HTTP 副作用。

### 9.2 Reporter 单元测试

- 新逻辑快照仅分配一次 revision，五次 HTTP 重试均复用同一 payload。
- 内容变化分配新 revision；10 分钟强制心跳也分配新 revision。
- 持久化失败时 HTTP client 调用次数为 0，daemon 其他模块不受影响。
- 合格 409 只追赶一次，并以 `max(local_revision,current_revision)+1` 重发相同业务快照；`received_revision` 与本次 payload 不一致时不得追赶。
- 非 JSON 409、未知错误码、缺字段、字段非法、第二次 409 均不继续追赶。
- 本地文件是格式有效但低于 Server 的旧备份 revision 时，首个合格 409 生成唯一后继 revision 并恢复；追赶后的普通传输重试复用该新值。
- 普通地址和路由器前缀 reporter 使用隔离 key，互不覆盖。
- 多 Server 覆盖 A 409 后 B 200、A 409 后 B 再 409、A 超时切换 B 和 Server revision 分叉；显式断言每份逻辑快照最多一次追赶。

### 9.3 Server 与真实协议测试

使用真实 `httptest` TCP 端口覆盖两个端点，禁止直接调用 handler 代替协议验证：

- revision 递增返回 200 和准确 `accepted_revision`。
- 相同 revision、相同规范化内容返回 200、`changed=false` 并刷新 `LastSeenAt`。
- 旧 revision 返回结构化 409，断言 Content-Type、错误码、current/received revision。
- 相同 revision、不同内容返回独立错误码，Registry、device state、prefix state 和 DDNS 均无部分副作用。
- 409 响应不包含 Token、前缀内容或其他设备状态。
- v0.6.3 Agent 兼容替身面对 JSON 409 安全失败；v0.6.4 Agent 面对 v0.6.3 纯文本 409 不误追赶。

### 9.4 根因回归链

必须在真实端口和健康评估器上直接证明：

1. 旧行为：Server 接受高 revision 后，重启式低 revision 被拒绝，`LastSeenAt` 不刷新，超过 15 分钟产生 `ddns_prefix_stale`。
2. 新行为：持久化 store 重建后继续使用更高 revision，Server 接受，`LastSeenAt` 刷新，超过原临界时间仍不产生 stale。
3. 恢复行为：删除或回退本地状态后，第一次 409 提供 Server 当前 revision，Agent 有界追赶成功，且没有重复 DDNS 更新。

测试中的 15 分钟通过注入 evaluator 时钟推进，不得让测试真实等待。

### 9.5 真实平台与升级验收

至少覆盖：

- OpenWrt 路由器 v0.6.3 → v0.6.4：通过真实管理 API 下发升级，确认 revision 文件位于持久目录；升级前后 revision 递增，连续 16 分钟内至少一次强制前缀心跳被接受，DDNS 设备不出现 `ddns_prefix_stale`。
- macOS 或 Windows 普通 Agent v0.6.3 → v0.6.4：升级前后普通 IPv6 地址 revision 递增，状态文件保留。
- 两条 reporter 分别执行一次不替换二进制的 Agent 服务重启，重启后首个 revision 必须大于重启前最后接受值。
- OpenWrt 执行一次真实设备重启，确认 `/data/homeagent` 下状态文件保留且首个前缀 revision 继续递增。普通设备不要求为本任务重启整台 Windows/macOS 主机，避免扩大生产验收影响。
- 全新安装 v0.6.4：不存在状态文件时从 1 开始并成功上报。
- 状态文件丢失演练：备份后移走文件，确认一次 409 追赶恢复；验收后恢复或清理演练制品，不遗留人为异常状态。
- Server 重启：Server 内存状态清空后接受 Agent 的高 revision，不能要求从 1 开始。

真实验收必须记录请求时间、HTTP 状态、accepted/current revision、状态文件路径与权限、升级前后 Agent 版本、健康事件和清理结果。不得输出 Token 或状态文件目录中的其他凭据。
