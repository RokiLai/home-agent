# HomeAgent 公网认证与设备认领设计方案修改建议

## 1. 修改目标

基于当前《HomeAgent 公网部署登录认证与设备认领（Claim Token）设计方案》进行修订。

本次修改以完善现有认证设计为主，不重新设计整体架构。

### 基本原则

1. 保留现有三层凭证体系：
   - Admin Session
   - Claim Token
   - Device Token

2. 优先最小改动。

3. 不引入新的基础设施或复杂认证体系。

4. 修改时同步更新：
   - 总体架构
   - Mermaid 时序图
   - API 契约
   - 客户端设计
   - Web 控制台设计
   - 安全设计
   - 向后兼容策略
   - 实施计划
   - 测试计划

5. 修改完成后必须检查全文，避免新旧设计同时存在导致文档前后矛盾。

---

## 2. 调整 `HOMEAGENT_JOIN_TOKEN` 兼容策略

### 当前问题

旧 `HOMEAGENT_JOIN_TOKEN` 仍被定义为最高权限全局 Key。

这会破坏：

- Admin Session
- Claim Token
- Device Token

之间已经建立的权限隔离。

### 修改要求

`HOMEAGENT_JOIN_TOKEN` 不再具有管理员权限。

仅作为旧设备迁移阶段的兼容接入凭据。

推荐流程：

```text
HOMEAGENT_JOIN_TOKEN
        ↓
仅允许旧设备执行 claim / credential migration
        ↓
换取独立 Device Token
        ↓
后续通信仅使用 Device Token
```

要求：

- `HOMEAGENT_JOIN_TOKEN` 标记为 deprecated。
- 不允许访问 Admin API。
- 新设备默认不再使用。
- 后续版本可以完全移除。
- 已接入旧设备通过升级逐步迁移到 Device Token。

## 3. 统一管理员认证模型

### 当前问题

当前文档同时出现：

- Admin Token
- Session
- Bearer Token
- localStorage
- Cookie

管理员认证模型不统一。

### 修改要求

统一使用：

```text
Server-side Session + HttpOnly Cookie
```

登录流程：

```text
username + password
        ↓
POST /api/v1/auth/login
        ↓
bcrypt 校验密码
        ↓
服务端生成高强度随机 Session Token
        ↓
服务端保存 Session Token Hash
        ↓
浏览器通过 HttpOnly Cookie 保存 Session Token
```

Cookie 至少设置：

```text
HttpOnly
Secure（HTTPS 环境）
SameSite=Strict
Path=/
```

### API 调整

以下接口：

```text
GET  /api/v1/auth/me
POST /api/v1/auth/logout
```

以及所有管理员 API：

统一通过 Session Cookie 鉴权。

Web 前端不再：

```text
Authorization: Bearer <admin_token>
```

同时删除：

```text
localStorage 保存 Admin Token
```

### 注意

只修改 Admin Credential。

以下凭证仍然使用 Bearer Token：

```text
Claim Token
Device Token
```

## 4. 明确 Session 生命周期

Session 至少包含：

```text
token_hash
created_at
expires_at
last_seen_at（可选）
```

### “记住登录状态”

建议：

```text
勾选：
Session 有效期 7 天

未勾选：
使用浏览器 Session Cookie
或配置较短的服务端 Session 生命周期
```

### Logout

`POST /api/v1/auth/logout`

必须同时：

```text
服务端 revoke Session
+
浏览器删除 Cookie
```

不能只删除浏览器 Cookie。

Logout 后旧 Session Token 必须立即失效。

## 5. Claim Token 消耗必须原子化

### 当前问题

Claim Token 当前逻辑：

```text
检查 Token
↓
检查 remaining_uses
↓
remaining_uses--
↓
创建设备
```

并发情况下可能出现两个请求同时看到：

```text
remaining_uses = 1
```

导致一次性 Token 被消费两次。

### 修改要求

增加明确的原子消费语义，例如：

```go
ConsumeClaimToken(token string) error
```

该操作必须不可分割地完成：

```text
查找 Token
↓
校验 Token Hash
↓
校验 expires_at
↓
校验 remaining_uses > 0
↓
remaining_uses--
```

保证：

```text
max_uses = 1
```

时，即使两个请求同时提交：

```text
最多一个请求成功
```

### 实现约束

HomeAgent 当前按照单实例服务实现即可。

可以使用：

```go
sync.Mutex
```

或者现有存储层的原子操作。

不要因此引入：

```text
Redis
分布式锁
```

---

## 6. Device ID 与设备 Metadata 解耦

### 当前问题

当前示例：

```json
{
  "device_id": "laptop-example"
}
```

容易让实现把 hostname 当成设备身份。

### 修改要求

`device_id` 必须由服务端生成。

推荐：

```text
UUID
或
ULID
```

例如：

```json
{
  "device_id": "01K2M8XXXXXXXXXXXXXX",
  "hostname": "laptop-example"
}
```

以下字段全部只作为 metadata：

```text
hostname
mac
addresses
os
arch
ssh_user
ssh_port
```

禁止使用：

```text
hostname
MAC
IP
```

作为设备唯一身份。

必须保证：

```text
hostname 修改
IP 变化
网络接口变化
```

不会导致：

```text
device_id
```

变化。

## 7. Device Token 本地存储安全

Device Token 属于长期 Credential。

必须明确本地文件权限。

### Linux

推荐：

```text
/var/lib/homeagent/device.json

owner: root
mode: 0600
```

### macOS

如果 HomeAgent Agent 作为 system daemon：

```text
/Library/Application Support/HomeAgent/device.json

owner: root:wheel
mode: 0600
```

### Windows

推荐：

```text
%ProgramData%\HomeAgent\device.json
```

通过 ACL 仅允许：

```text
SYSTEM
Administrators
HomeAgent Service Identity
```

访问。

### 日志要求

以下内容不得输出完整 Device Token：

```text
安装日志
Agent 日志
HTTP Access Log
Debug Log
Trace
错误响应
```

## 8. Claim Token 统一通过 Authorization Header

### 当前问题

当前 `/devices/claim` 同时允许：

```text
Authorization Header
```

以及：

```json
{
  "claim_token": "..."
}
```

两种传递方式。

### 修改要求

只保留：

```http
Authorization: Bearer claim_xxx
```

删除 JSON Body 中：

```json
"claim_token": "..."
```

请求体只包含设备信息：

```json
{
  "device": {
    "hostname": "laptop-example",
    "os": "darwin",
    "arch": "arm64",
    "ssh_user": "exampleuser",
    "ssh_port": 22,
    "public_key": "ssh-ed25519 ...",
    "mac": "...",
    "addresses": ["..."]
  }
}
```

同时要求：

所有日志、中间件和 Trace 对：

```text
Authorization
```

进行脱敏。

不得记录完整 Token。

---

## 9. 服务端 Token 统一只保存 Hash

明确以下存储规则：

```text
Admin Session Token → SHA-256 Hash
Claim Token         → SHA-256 Hash
Device Token        → SHA-256 Hash
```

服务端：

```text
数据库
YAML
状态文件
```

均不得长期保存这些 Token 的明文。

Token 创建时：

```text
生成明文 Token
↓
服务端保存 SHA-256 Hash
↓
明文只向调用方返回一次
```

验证时：

```text
客户端 Token
↓
SHA-256
↓
查询 / 比较服务端 Hash
```

### 注意

管理员密码不是 Token。

管理员密码继续使用：

```text
bcrypt
```

不要修改成 SHA-256。

---

## 10. 管理员密码环境变量仅用于首次初始化

保留：

```text
HOMEAGENT_ADMIN_USERNAME
HOMEAGENT_ADMIN_PASSWORD
```

但明确它们属于：

```text
Bootstrap Credential
```

### 规则

如果持久化存储中：

```text
不存在管理员
```

则允许：

```text
HOMEAGENT_ADMIN_USERNAME
HOMEAGENT_ADMIN_PASSWORD
```

初始化管理员。

如果：

```text
管理员已经存在
```

则后续服务启动时：

```text
不得通过 HOMEAGENT_ADMIN_PASSWORD
自动覆盖已有密码
```

环境变量只负责首次初始化。

## 11. 强化 Device Token 的资源级权限约束

保留现有：

```go
auth.RequireDevice()
```

但需要明确：

Device Token 必须绑定：

```text
device_id
```

例如服务端 Token Record：

```text
token_hash
device_id
created_at
revoked_at
```

访问：

```text
/api/v1/devices/{device_id}/...
```

时不能只判断：

```text
Device Token 是否合法
```

还必须判断：

```text
token.device_id == request.device_id
```

例如：

```text
Device A Token
        ↓
/devices/A/events
        ↓
允许

Device A Token
        ↓
/devices/B/events
        ↓
403 Forbidden
```

防止 IDOR / 跨设备访问。

## 12. 补充 Credential 撤销语义

文档中明确三类 Credential 的撤销方式。

### Admin Session

```text
logout
→ revoke Session
```

### Claim Token

```text
过期
remaining_uses = 0
管理员 DELETE
```

均立即失效。

### Device Token

管理员：

```text
删除设备
或
撤销设备授权
```

时：

```text
Device Token 立即失效
```

已有 SSE 连接也应该被服务端关闭或在下一次权限检查时终止。

## 13. 调整 API 契约

最终管理员认证：

```text
POST /api/v1/auth/login
GET  /api/v1/auth/me
POST /api/v1/auth/logout
```

使用：

```text
HttpOnly Session Cookie
```

Enrollment 管理 API：

```text
POST   /api/v1/enrollment-tokens
GET    /api/v1/enrollment-tokens
DELETE /api/v1/enrollment-tokens/{id}
```

使用：

```text
Admin Session Cookie
```

设备认领：

```text
POST /api/v1/devices/claim
```

使用：

```http
Authorization: Bearer <claim_token>
```

设备 API：

```text
/api/v1/devices/{device_id}/events
以及其他 Device API
```

使用：

```http
Authorization: Bearer <device_token>
```

## 14. 更新时序图

修改 Mermaid 时序图，使其与最终认证模型一致。

管理员登录部分：

```text
Admin
  ↓
username/password
  ↓
Server
  ↓
bcrypt verify
  ↓
create session
  ↓
store session token hash
  ↓
Set-Cookie HttpOnly
  ↓
Web Console
```

设备接入部分：

```text
Admin Session
      ↓
Create Claim Token
      ↓
Claim Token
      ↓
Device / install.sh
      ↓
POST /devices/claim
      ↓
Atomic Consume Claim Token
      ↓
Generate device_id
      ↓
Generate Device Token
      ↓
Store Device Token Hash
      ↓
Return Device Token once
      ↓
Agent local secure storage
```

确保时序图中不再出现：

```text
Admin Token → localStorage
```

## 15. 补充测试场景

Phase 5 至少增加以下测试。

### Claim Token

```text
- max_uses=1 Token 第一次 claim 成功
- 第二次 claim 失败
- 两个并发请求使用同一个 max_uses=1 Token，只允许一个成功
- 已过期 Claim Token 无法使用
- 管理员手动作废后无法使用
- Claim Token 无法访问 Admin API
- Claim Token 无法访问 Device API
```

### Admin Session

```text
- 正确用户名密码登录成功
- 错误密码登录失败
- Session Cookie 可以访问 Admin API
- Session 过期后无法访问 Admin API
- logout 后 Session 立即失效
- logout 后旧 Cookie 即使再次发送也无法访问
```

### Device Token

```text
- Device Token 可以访问自身资源
- Device A Token 无法访问 Device B
- Device Token 无法访问 Admin API
- Device Token 无法创建 Claim Token
- Device 被删除/撤销后 Token 立即失效
```

### Device Identity

```text
- hostname 修改不会改变 device_id
- IP 地址变化不会改变 device_id
- 两台 hostname 相同的设备可以正常注册
```

### Credential 泄露检查

确认以下位置不会出现完整 Token：

```text
Application Log
HTTP Access Log
Trace
安装日志
错误响应
Web Console 日志
```

### 兼容性

```text
- HOMEAGENT_JOIN_TOKEN 可以完成规定的迁移流程
- HOMEAGENT_JOIN_TOKEN 无法访问 Admin API
- 新设备默认使用 Claim Token
```

## 16. 最终认证模型

最终架构统一收敛为：

```text
                     HomeAgent Server
                            │
            ┌───────────────┼───────────────┐
            │               │               │
      Admin Session     Claim Token     Device Token
            │               │               │
     HttpOnly Cookie     15min / 1次        长期
            │               │               │
      管理系统资源       仅 devices/claim   仅自身资源
                            │
                            │
                            ▼
                      Device Token
```

服务端 Credential 存储：

```text
HomeAgent Server
│
├── Admin Password
│      └── bcrypt hash
│
├── Admin Session
│      └── SHA-256(token)
│
├── Claim Token
│      └── SHA-256(token)
│
└── Device Token
       └── SHA-256(token)
```

客户端：

```text
Browser
└── Admin Session
      └── HttpOnly Secure Cookie

HomeAgent Agent
└── Device Token
      └── 0600 / Windows ACL
```

## 19. 修改完成后的自检要求

修改文档完成后，对全文执行一次一致性检查。

重点检查：

1. 是否还有 `Admin Token + localStorage` 的旧设计。
2. Admin API 是否全部统一为 Session Cookie。
3. Claim Token 是否仍只拥有 claim 权限。
4. Device Token 是否仍只拥有自身设备权限。
5. 是否还有 Claim Token 放入 JSON Body 的示例。
6. Claim Token 消耗是否明确要求原子化。
7. `device_id` 是否完全与 hostname / MAC / IP 解耦。
8. 是否还有 `HOMEAGENT_JOIN_TOKEN` 被描述为最高权限凭据。
9. 所有 Token 是否明确只在服务端保存 Hash。
10. Token 是否都有明确的创建、过期、消费、撤销机制。
11. Device Token 是否明确绑定 device_id。
12. 时序图、API 契约、安全章节、实施计划之间是否完全一致。
13. 是否避免引入本次范围之外的新架构。

如果发现旧设计残留，直接同步修正，不要同时保留两套互相冲突的认证方案。
